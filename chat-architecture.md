# gost-restreamer — архитектура подсистемы чатов

**Статус:** проектная спецификация расширения gost-restreamer.  
**Дата анализа:** 18 ноября 2026 года.  
**Основа:** `GregoryGost/gost-restreamer`, ветка `develop`, коммит [`95f5245cd704`](https://github.com/GregoryGost/gost-restreamer/commit/95f5245cd704); последний тег [`v0.1.0-dev.8+252669d05440`](https://github.com/GregoryGost/gost-restreamer/tree/v0.1.0-dev.8%2B252669d05440).  
**Путь в репозитории:** `chat-architecture.md`.  
**Самодостаточность:** документ определяет архитектуру подсистемы чатов как единую самостоятельную спецификацию.  
**Принятая авторизация:** YouTube API Key для публичного чата, Twitch Device Code Grant для EventSub и VK Видео Live DevAPI `client_credentials`. Буфер сообщений — 1000 на Session.

## 1. Установленное состояние существующего решения (AS-IS)

Перед проектированием проверены действующие исходники и контракты. Ниже приведены **действующие точки интеграции** в репозитории.

| Участок | Что существует сейчас | Следствие для подсистемы чатов |
|---|---|---|
| Назначения | `core.Stream → core.Destination`; `Destination` принадлежит Stream и TranscodeGroup. Поле `Destination.Platform` — свободная строка. | Источник чата связывается с конкретным `Destination.ID`; провайдер чата задаётся в `ChatSource.provider`. |
| Запуски | Для Stream существует текущая `Session`; у неё отдельные `SessionOutput`. Каждый выход хранит `OutputSnapshot.Destination` со стабильным `ID`, независимо от последующего редактирования конфигурации. | Chat Manager сопоставляет настройку Destination с **фактическим выполняющимся выходом**. |
| Состояния | Наблюдаемые `OutputState`: `CONNECTING`, `PUBLISHING`, `RETRYING`, `FAILED`, `STOPPED`. Оперативные наблюдения находятся в RAM; долговечные намерения и квитанции — в SQLite. | Чтение чата активируется после фактического `PUBLISHING` соответствующего выхода. |
| Идентичность | `RuntimeSessionFence` различает `SessionID`, `Incarnation`, `Lifecycle`; состояние выхода относится к конкретному `ExecutionFence`. Поздние наблюдения от прежней попытки отклоняются. | Адаптеры прекращают публикацию событий прежней попытки после смены точного выполнения. |
| Автозапуск OBS | `session.Manager.AdmitOBS` запускает Session через действующий механизм при первой корректной публикации OBS. При переподключении OBS работающие выходы сохраняют своё выполнение. | Чат запускается **по состоянию выхода**. |
| Медиа | Go ingress/router, группы, нативные RTMP/RTMPS Publisher, FFmpeg и fallback. | Чат работает в отдельном контуре Go и получает только события жизненного цикла выходов. |
| События | Существующие `core.Service.RuntimeAnchor` / `RuntimeEvents` и `GET /api/v1/events/snapshot`, `GET /api/v1/events` передают оперативные медиасобытия, с ограниченным журналом и resync при потере событий. | Жизненный цикл отслеживается через **внутренние** `RuntimeAnchor`/`RuntimeEvents`; сообщения передаёт собственный ChatHub/SSE. |
| Управление | Go + Chi + Huma v2; маршруты под `/api/v1`; OpenAPI генерируется из зарегистрированных операций. Ошибки API — Problem Details с машинным `code`. | Chat REST регистрируется через существующий Huma API, из которого автоматически формируется OpenAPI. |
| JSON | На актуальном `develop` числовые поля REST и SSE передаются JSON-числами с сохранением точности 64-битных целых на сервере; cursor и ID — строки. | В Chat API числовые поля соответствуют действующему JSON-контракту; публичные курсоры SSE — **непрозрачные строки**. |
| Данные | SQLite с GORM, схема мигрирует через Goose; используется `foreign_keys=ON`, WAL, ревизии конфигурации. | SQLite хранит конфигурацию и реквизиты; сообщения находятся в оперативном ChatHub. |
| Веб-интерфейс | Встроенная HTML-страница `/api/v1/docs` публикует API-документацию. | Новые две страницы реализовать простыми HTML/CSS/JavaScript ES modules, встроенными в бинарник. |
| Контур доверия | Self-hosted сервис в локальной сети; управляющий REST и SSE сейчас **без авторизации**. По текущему контракту часть медиаключей доступна через управляющий API. | API-ключи и токены используются только сервером; Overlay и SSE получают публичную проекцию событий и статусов в доверенном LAN. |

**Проверенные исходные контракты:** [основная архитектура, редакция 18](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/gost-restreamer-architecture.md), [`core/entities.go`](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/internal/core/entities.go), [`core/observations.go`](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/internal/core/observations.go), [`core/events.go`](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/internal/core/events.go), [`api/runtime.go`](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/internal/api/runtime.go), [`app/app.go`](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/internal/app/app.go), [API contract](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/docs/api-contracts.md), [numeric JSON contract](https://github.com/GregoryGost/gost-restreamer/blob/95f5245cd704/docs/numeric-json-contracts.md).

## 2. Цель, границы и принятые решения (TO-BE)

Добавить в работающий gost-restreamer **агрегатор только для чтения** сообщений чатов трёх площадок: **YouTube, Twitch, VK Видео Live (`live.vkvideo.ru`)**. Сервер собирает сообщения независимо от открытых веб-страниц, приводит их к общему формату и выдаёт стримеру единую ленту.

Закреплённые решения:

1. Серверная реализация — Go, внутри того же процесса и жизненного цикла `app.Application`.
2. Один выбранный протокол чтения на платформу: YouTube `liveChatMessages.streamList`; Twitch EventSub WebSocket `channel.chat.message`; VK Видео Live DevAPI + Centrifugo WebSocket.
3. Для браузерных интерфейсов — **HTTP REST + SSE/EventSource**; для Twitch и VK Видео Live Go-адаптеры подключаются к платформам через WebSocket.
4. Две независимые HTML-страницы: `/chat/overlay` и `/chat/dashboard`, с общими модулями обработки сообщений.
5. Внутренний ограниченный Ring Buffer в RAM для оперативной истории сообщений.
6. Привязка строго `Stream → Destination → 0..N ChatSource`. У каждого ChatSource **ровно один** Destination с обязательным `destination_id`.
7. Начало чтения определяется фактической публикацией соответствующего выхода. Чтение продолжается при переподключении OBS и работе выхода с fallback.
8. Выбор YouTube-видео относится к текущему запуску трансляции. При следующем запуске сервер заново обнаруживает эфир канала: единственный результат выбирается автоматически, несколько результатов требуют явного выбора.
9. Изменение канала или аккаунта ChatSource применяется во время трансляции и переподключает только затронутое чтение чата.
10. Ввод новых реквизитов не отзывает прежний действующий доступ. Новый доступ используется после успешной проверки и сохранения; отмена и ошибка проверки сохраняют прежние настройки и чтение. Это правило замены реквизитов не обещает действительность токена, отозванного самой площадкой.
11. Одновременная публикация двух источников в один платформенный канал не является поддерживаемым пользовательским сценарием. Читается чат выбранного действующего эфира канала; повторы доставки при восстановлении соединения устраняются сервером.
12. До начала трансляции настройки доступны, а лента пуста без текста об ожидании и других служебных записей. Открытая страница начинает получать сообщения после фактического запуска публикации; состояния источников показываются отдельно от ленты сообщений.

## 3. Контекст и компоненты

```text
                   EXISTING MEDIA CONTROL
Stream → Session → SessionOutput → OutputObserver / RuntimeEvents
   │                    │
   │                OutputSnapshot.Destination.ID
   │                    │
   └── Destination ── 0..N ChatSource (SQLite config)
                           │
                      Chat Manager
                   ┌───────┼─────────┐
                YouTube   Twitch   VK Видео Live
             streamList  EventSub   DevAPI WS
                   └───────┼─────────┘
                       Normalize
                       Dedupe
                 Session ChatHub / RAM
                           │
                   REST snapshot + SSE
                      ┌────┴────┐
                    Overlay   Dashboard
```

**Chat Manager** — отдельный компонент приложения, отвечающий за связывание текущих выходов и источников чатов, создание/отмену adapter workers, контроль ограничений и публикацию данных в `ChatHub`.

**Platform Adapter** — изолированный Go-клиент конкретной платформы, который обнаруживает правильный канал/эфир, читает события через единственный утверждённый транспорт, обновляет авторизацию и сообщает нормализованные данные/состояние.

**ChatHub** — независимый от существующей медиа-телеметрии буфер и поток событий по конкретной активной Session. Создание и закрытие браузерных страниц на его жизненный цикл не влияет.

**Credential Store** — отдельные полномочия платформ: API Key проекта Google для публичного чтения YouTube, пользовательский Twitch OAuth через Device Code и реквизиты DevAPI-приложения VK Видео Live. Несколько ChatSource могут использовать одну запись; обновление Twitch-токенов сериализовано.

## 4. Персистентная модель

### 4.1. ChatSource

Создаётся новая конфигурационная сущность `ChatSource`:

| Поле | Смысл и ограничение |
|---|---|
| `id`, `revision`, `created_at`, `updated_at` | Общие правила идентичности и оптимистической проверки ревизии проекта. |
| `destination_id` | **NOT NULL**, внешний ключ на `destinations.id`. Один родитель обязателен и неизменяем после создания. |
| `provider` | Доменный каталог: `youtube`, `twitch`, `vk_video_live`. Выбирается независимо от `Destination.Platform`. |
| `account_id` | Ссылка на настроенный `ChatAccount` того же провайдера. Для VK Видео Live запись содержит реквизиты DevAPI-приложения. |
| `name` | Необязательное удобочитаемое имя для Dashboard. |
| `enabled` | Разрешение на чтение: изменение действует во время эфира независимо от работы медиавыхода. |
| `channel_hint` | Для YouTube — **обязательный постоянный публичный Channel ID** формата `UC...`; для Twitch — канал авторизованного пользователя или заданный `broadcaster_user_id`; для VK Видео Live — **обязательный постоянный slug канала** из `live.vkvideo.ru/{slug}`: вводится один раз на постоянной основе. |
| `options` | Версионированные типизированные настройки адаптера с проверкой допустимых полей. |

Один Destination может иметь ноль, один или несколько ChatSource, в том числе разных провайдеров. Удаление Destination остаётся под **существующими** ограничениями удержания ресурсов; после разрешённого удаления связанные настройки ChatSource удаляются атомарно. Исторические `SessionOutput.Snapshot` сохраняют закреплённые значения.

`ChatSource` описывает чтение чата; оперативные подключения и ошибки ведёт Chat Manager в RAM. Допустимые значения `provider` определяются доменным каталогом; структурная настройка не требует уже подключённого runtime-адаптера. Расширение списка требует согласованного расширения каталога и регистрации реализации. Наличие доменного значения не доказывает доступность чтения площадки. Options имеют версию 1 и ровно один соответствующий провайдеру пустой типизированный вариант; произвольный словарь и постоянный Video ID не вводятся.

### 4.2. ChatAccount

Отдельная сущность `ChatAccount` хранит конфигурационную Record, неизменный `provider` и имя. Соответствующие провайдеру реквизиты представлены отдельными серверными `ChatCredentialBundle`/`ChatCredentials`, недоступными обычным чтениям Account/Source:

- `youtube`: серверный **API Key** Google Cloud с включённым YouTube Data API v3. Источник задаёт публичный `channel_id`, ключ хранится и используется на backend.
- `twitch`: собственный Twitch OAuth Client ID (тип **Public**, Device Code Grant); пользовательские `access_token`/`refresh_token`, `user_id`, scope `user:read:chat` и сроки. Refresh-токены Device Code одноразовые при обмене и имеют срок неактивности 30 суток по документации Twitch.
- `vk_video_live`: собственные `client_id`/`client_secret` **приложения DevAPI**; получаемый через `client_credentials` краткоживущий `access_token` и его срок. При истечении/отзыве app-токена сервер повторяет `client_credentials`.

Один ChatAccount обслуживает несколько ChatSource своего провайдера. YouTube использует один настроенный API Key; Twitch выполняет обмен одноразового `refresh_token` **одним сериализованным владельцем**; VK Видео Live переиспользует app-токен и повторяет `client_credentials` по необходимости.

Токены и реквизиты находятся в SQLite текущей инсталляции вместе с остальными сохраняемыми настройками. Доступ к файлу ограничивается правами ОС. **Публичные SSE, Overlay, диагностические статусы и чтение ChatSource передают санитизированные данные; полномочия остаются на backend**. Действующий режим журнала `full` наследуется от проекта: его безопасность зависит от доверенного контура и контроля файлов журнала; для подсистемы действует общая политика логирования приложения.

Успешная проверка и сохранение замены реквизитов или повторной авторизации инициируют переподключение затронутых адаптеров; до этого действует прежний пригодный доступ. Config Revision меняется при редактировании и ручной замене, CredentialRevision — при ручной замене и refresh. Refresh атомарно меняет весь набор токенов, сохраняет метаданные и идентичность доступа. Поздний refresh после замены отклоняется. Обновление имени применяется без пересоздания чтения; переименование во время незавершённой замены вправе завершить её обычным CAS-конфликтом. Удаление ChatAccount выполняется после перепривязки или удаления его зависимых ChatSource.

### 4.3. Границы хранения

**SQLite:** конфигурации ChatSource/ChatAccount, ревизии, API-ключи Google, OAuth- или DevAPI-реквизиты и обновления токенов. **RAM:** текущие подключения, статусы, последние сообщения, курсоры, дедупликация, счётчики ошибок и backoff. История чата существует как оперативный буфер текущей Session.

Расширение рассчитано на новую установку: новые сущности добавляются в единственный начальный SQL-скрипт Goose версии 1 с `storage_format=5` и `foreign_keys=ON`. Проверка набора таблиц и маркера выполняется до потенциально пишущих вызовов Goose и Recover. Прежний формат отклоняется без преобразования схемы, доменных данных и истории Goose; автоматическое пересоздание пользовательской БД, следующая миграция и GORM AutoMigrate не применяются. Исторические снимки Media Session остаются самостоятельными. Две области CAS, WriteID для сверки неоднозначного COMMIT, входы/результаты портов и конечные бюджеты определены в [контракте чатов](docs/chat-contracts.md).

## 5. Привязка к текущей Session и жизненный цикл

### 5.1. Определение активного выхода

`Chat Manager` потребляет **внутренние** `core.Service.RuntimeAnchor()` и `RuntimeEvents()` без HTTP-loopback, а для корреляции читает сохранённые `Session`/`SessionOutput`. Выбор чата основывается на:

- точной актуальной `SessionID + Incarnation + Lifecycle`;
- текущей `ExecutionFence` для `OutputID` и его `OutputObservation`;
- `OutputSnapshot.Destination.ID`;
- `Attached && DesiredRunning` по актуальному управлению выходом и включённому ChatSource.

Runtime-состояние и данные SQLite читаются согласованно через повторную проверку: после чтения исходной конфигурации и `RuntimeAnchor` Manager дочитывает события от курсора, пересверяет текущие выходы и повторяет сверку после `Gap`/`Reset`. `PUBLISHING` означает фактическую публикацию медиа в сеть; наличие платформенного live-чата определяется адаптером независимо и асинхронно.

### 5.2. Таблица переходов

| Выход / управление | Требуемая реакция ChatSource |
|---|---|
| Выход ожидает запуска, находится в `CONNECTING` или ещё не имеет наблюдателя | `WAITING_OUTPUT`; запуск чтения ожидает `PUBLISHING`. |
| Точная попытка впервые перешла в `PUBLISHING` | Запустить обнаружение платформенного чата, затем чтение. |
| Точная попытка в `RETRYING` после публикации | Сохранить уже работающее чтение и выполнять собственное восстановление upstream при необходимости. |
| `PUBLISHING`, но активный эфир или чат ещё не найден | `DISCOVERING` / `WAITING_CHAT` с повторной попыткой по ограничениям платформы. |
| Выход переключился на fallback, остался `PUBLISHING` | Продолжить читать чат без пересоздания подключения. |
| OBS отключился или подключился повторно при том же выполнении выхода | Сохранить текущее подключение чата. |
| Принят `stop`/`detach`, больше нет `DesiredRunning` или `Attached`, выход получил `FAILED`/`STOPPED`, наблюдатель удалён | Остановить чтение, отменить попытки reconnect. |
| Истёк или сменился `ExecutionFence`, завершилась Session, сменился `Incarnation` | Отозвать старые workers, исключить поздние сообщения и освободить старый ChatHub после закрытия его подписок. |
| Оператор отключил ChatSource (`enabled=false`) | Остановить соответствующий ChatSource при продолжающейся работе медиавыхода. |
| Оператор включил ChatSource при уже публикующем выходе | Запустить обнаружение и подключение непосредственно в Chat Manager. |

Если **несколько** действующих `SessionOutput` ссылаются на один Destination, ChatSource активен, пока хотя бы один подходящий выход удовлетворяет условиям. В рамках Session для ChatSource используется один upstream-worker, обслуживающий соответствующие выходы.

Подключения и подписки хранят identity соответствующей Session и исходных ChatSource. При обработке каждого сообщения проверяется актуальность worker и поколения; устаревшие события отбрасываются до нормализации и SSE.

### 5.3. Наблюдаемое состояние самого чата

ChatSource имеет **оперативный** статус:

- `DISABLED` — отключён настройкой;
- `WAITING_OUTPUT` — ожидание публикующего выхода;
- `DISCOVERING` — ищет нужный эфир/канал;
- `WAITING_CHAT` — ожидание доступности платформенного чата;
- `CONNECTING` — выполняется upstream-авторизация/подписка;
- `CONNECTED` — подписка подтверждена платформой;
- `RETRYING` — временный сетевой отказ / ограничение платформы;
- `AUTH_REQUIRED` — требуется повторная авторизация;
- `FAILED` — подтверждённая несоответствующая конфигурация или невосстановимая ошибка;
- `STOPPED` — завершено в результате остановки Session/Output.

Dashboard показывает статус, время последнего успешного события, дату обнаруженного эфира, безопасный код причины и число локально отброшенных сообщений. Состояние `CONNECTED` определяется подтверждением подписки независимо от активности аудитории.

## 6. Протоколы чтения и обнаружение чата

Каждому провайдеру соответствует один зарегистрированный reader с определёнными авторизацией, обнаружением и протоколом доставки.

### 6.1. YouTube

**Чтение — официальный `liveChatMessages.streamList` через gRPC с Google API Key.** Публичное чтение по API Key описано в [руководстве Streaming Live Chat](https://developers.google.com/youtube/data/live/streaming-live-chat) и [документации авторизации Live Streaming API](https://developers.google.com/youtube/data/live/authentication).

1. В Google Cloud создать проект, включить YouTube Data API v3 и выпустить API Key. Сохранить ключ на backend в `ChatAccount`.
2. В `ChatSource.channel_hint` один раз записать постоянный публичный `channel_id` YouTube (`UC...`). При появлении состояния выхода `PUBLISHING` искать активный публичный эфир через `search.list(part=snippet, channelId=..., eventType=live, type=video)`. Из ответа получить `videoId`. Обнаружение зависит от обновления поискового индекса YouTube; до появления эфира адаптер остаётся в `DISCOVERING`.
3. Для найденного видео вызвать `videos.list(part=liveStreamingDetails,id=...)` и прочитать `liveStreamingDetails.activeLiveChatId`. Поле существует только для действующего эфира с включённым чатом. Пустая выдача переводит источник в `WAITING_CHAT`; несколько эфиров показываются в Dashboard для явного выбора.
4. Выполнить единственный reader: `liveChatMessages.streamList` к `youtube.googleapis.com:443` с gRPC metadata `x-goog-api-key`, `part=[id,snippet,authorDetails]` и нужным `live_chat_id`. При обрыве возобновлять по `nextPageToken`; повторные сообщения фильтруются по ID. Ошибки отключённого/завершённого чата и недостатка прав обрабатываются отдельно.
5. **Квота обнаружения:** `search.list` имеет отдельный бюджет, по умолчанию **100 вызовов в сутки** на проект по актуальной [документации квот](https://developers.google.com/youtube/data/determine_quota_cost). Поиск ограничивается отсутствием найденного эфира и контролируемым backoff; интервалы опроса рассчитываются с учётом суточной квоты. `videos.list` стоит 1 единицу общей квоты, а `streamList` — 5 единиц за вызов. Проверять расход в проекте Google Cloud.

**Охват:** публичные эфиры YouTube, обнаруживаемые по `channel_id` через `search.list`, с доступным `activeLiveChatId`.

Источники: [Streaming Live Chat](https://developers.google.com/youtube/data/live/streaming-live-chat), [YouTube Live authorization](https://developers.google.com/youtube/data/live/authentication), [Search:list](https://developers.google.com/youtube/data/reference/rest/v3/search/list), [Videos:list](https://developers.google.com/youtube/data/reference/rest/v3/videos/list), [LiveChatMessages:streamList](https://developers.google.com/youtube/data/live/reference/rest/v3/liveChatMessages/streamList), [Quota calculator](https://developers.google.com/youtube/data/determine_quota_cost).
### 6.2. Twitch

- **Авторизация:** OAuth user token с разрешением `user:read:chat`; обновление и проверка токена перед подпиской.
- **Идентичность:** `broadcaster_user_id` канала и `user_id` авторизованного reader-аккаунта устанавливаются явно; чат привязан к постоянному идентификатору канала.
- **Чтение:** официальный EventSub `channel.chat.message` версии `1` поверх `wss://eventsub.wss.twitch.tv/ws`. После `session_welcome` создать подписку на выданный `session_id`.
- **Восстановление:** различать `session_reconnect` (переход на выданный URL) и реальный разрыв (новый socket и создание подписки заново). `revocation`, `keepalive` и лимиты подписок обрабатывать как часть протокола.
- **Граница потерь:** При полном разрыве upstream WebSocket Dashboard и метрики показывают возможный пробел в сообщениях. Локальный буфер воспроизводит события, фактически принятые адаптером.

Спецификация: [EventSub channel.chat.message](https://dev.twitch.tv/docs/eventsub/reference/chat), [EventSub WebSocket](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/).

### 6.3. VK Видео Live

**Авторизация — DevAPI `client_credentials`** с реквизитами собственного приложения.

1. Владелец единожды регистрирует собственное приложение на [портале DevAPI](https://dev.live.vkvideo.ru/) (для входа в кабинет может требоваться VK ID), сохраняет в настройках backend `client_id` и `client_secret`.
2. Backend запрашивает app-токен: `POST https://api.live.vkvideo.ru/oauth/server/token`, заголовок `Authorization: Basic base64(client_id:client_secret)`, form `grant_type=client_credentials`. Срок жизни токена определяет время следующего выпуска app-токена.
3. `ChatSource.channel_hint` указывает **постоянный slug** своего канала (например, `streamer`). Через `GET https://apidev.live.vkvideo.ru/v1/channel?channel_url=...` с `Authorization: Bearer <app-token>` определяется числовой `channel.id`; Для чтения используется постоянный идентификатор канала.
4. Через `GET https://apidev.live.vkvideo.ru/v1/websocket/token` с тем же Bearer-токеном получить краткоживущий WebSocket-токен.
5. Единственный выбранный reader — **Centrifugo WebSocket** `wss://pubsub.live.vkvideo.ru/connection/websocket?cf_protocol_version=v2`: послать `connect` с WebSocket-токеном; подписаться на публичный канал `channel-chat:<channel.id>`; ждать подтверждения `subscribe`, обрабатывать `push.pub.data`, ping/pong, закрытия, `unsubscribe`/`disconnect`. При переподключении заново получать устаревшие app/WS-токены по необходимости.
6. Нормализовать сообщения и события чата (текст, emoji/смайлы, автор, бейджи); статус `CONNECTED` выставлять после подтверждённой подписки.

**Основание выбора:** открытая реализация [UkiChat: получение app-токена и WebSocket-токена](https://github.com/ukionik/UkiChat/blob/main/UkiChat/UkiChat/Services/VkVideoLiveApiService.cs), [UkiChat: Centrifugo-клиент](https://github.com/ukionik/UkiChat/blob/main/UkiChat/UkiChat/Model/VkVideoLive/VkVideoLiveChatClient.cs), [подключение и повторный выпуск app-токена](https://github.com/ukionik/UkiChat/blob/main/UkiChat/UkiChat/Services/AppInitializationService.cs). Второе независимое подтверждение назначения client credentials для чтения: [Brix: VkApi.kt](https://github.com/0rb1ta/Brix/blob/main/streaming/src/main/kotlin/app/brix/streaming/chat/VkApi.kt). Официальный раздел: [авторизация DevAPI](https://dev.live.vkvideo.ru/docs/main/authorization). Для приёмки выполняется тест с собственным DevAPI-приложением: app-токен, WebSocket-токен, подписка и получение сообщений своего канала. Сетевой контракт UkiChat используется как референс с соблюдением лицензии исходного проекта.

### 6.4. Правило расширения

Новые провайдеры требуют расширения доменного каталога и регистрации адаптера. Доменная валидация проверяет типизированную конфигурацию; реестр runtime-реализаций определяет фактическую доступность чтения. Он не отключает структурную настройку уже объявленного провайдера до подключения его реализации.

## 7. Авторизация: выбранные способы для локальной VM

Подключение YouTube, Twitch и VK Видео Live выполняется непосредственно сервером на VM. Dashboard предоставляет настройки ключей и параметры подтверждения входа через Device Code.

### 7.1. YouTube: API Key

- Один раз создать Google Cloud Project, включить YouTube Data API v3 и выпустить API Key. Предусмотреть ограничение API Key по YouTube Data API и, при операционной возможности, по исходящему IP VM.
- В доверенном Dashboard сохранить ключ на backend и настроить постоянный `channel_id` (`UC...`). Сервер проверяет пригодность ключа через безопасный запрос `videos.list` к известному публичному видео либо подходящую валидацию API; сама проверка ключа не доказывает наличие активного эфира.
- Использовать публичные методы `search.list`, `videos.list` и gRPC `liveChatMessages.streamList` с `x-goog-api-key` (см. раздел 6.1).
- Связь с целевым каналом проверяется по настроенному `channel_id` и данным `videos.list`; API Key принадлежит Google Cloud Project.

Источники: [официальная схема чтения](https://developers.google.com/youtube/data/live/streaming-live-chat), [типы полномочий YouTube](https://developers.google.com/youtube/data/live/authentication).

### 7.2. Twitch: Device Code Grant

- Один раз создать приложение Twitch типа **Public** в [Developer Console](https://dev.twitch.tv/console/apps). Используется Device Code Grant приложения типа Public.
- Нажатие «Подключить Twitch» начинает серверный запрос `POST https://id.twitch.tv/oauth2/device` с `client_id` и `scopes=user:read:chat`. Dashboard показывает `verification_uri` и `user_code`; пользователь подтверждает разрешение в обычном браузере Twitch.
- Backend опрашивает `POST https://id.twitch.tv/oauth2/token` с `grant_type=urn:ietf:params:oauth:grant-type:device_code`, соблюдая выданный `interval`, срок действия кода, ответы `authorization_pending`, `slow_down`, отказ и отмену. После успешного обмена сохраняет пользовательский `access_token`, `refresh_token`, `user_id`, scope и сроки в SQLite.
- Для EventSub WebSocket используется user access token с `user:read:chat`. Проверка `/validate`, отзыв/истечение и обновление токенов выполняются одним владельцем `ChatAccount`. По актуальной документации Twitch refresh-токены Device Code **одноразовы при использовании** и требуют повторной авторизации после **30 суток бездействия**; новую пару сохранять атомарно. При истечении полномочий Dashboard показывает `AUTH_REQUIRED` и повторную авторизацию.

Источник: [Twitch OAuth — Device Code Grant](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/), [Twitch EventSub Chat](https://dev.twitch.tv/docs/eventsub/reference/chat).

### 7.3. VK Видео Live: DevAPI Client Credentials

- Собственное DevAPI-приложение с `client_id`/`client_secret` получает app access token через `grant_type=client_credentials` (раздел 6.3).
- При истечении токена запрашивать новый; `/v1/token` использовать для проверки типа/срока. Неверные реквизиты → `AUTH_REQUIRED`, временный отказ сервера → `RETRYING`.
- Для чата нужен постоянный slug своего канала, указанный один раз в ChatSource. Перед выпуском проверить выдачу app-токена, WebSocket-токена и подтверждение подписки именно с реквизитами собственной DevAPI-регистрации.

### 7.4. Хранение и отзыв полномочий

Сервер хранит API Key YouTube, Twitch access/refresh tokens и DevAPI `client_id`/`client_secret` в SQLite с текущей моделью прав файла и ограничением доверенного LAN. Чтение конфигурации, публичные SSE, Overlay и диагностические статусы предоставляют только санитизированные данные. Браузер передаёт ключ/Client Secret при сохранении настроек в доверенном Dashboard; backend управляет токенами Twitch и использует полномочия для платформенных запросов. Отзыв ключа Google или DevAPI-реквизитов требует переподключения соответствующих адаптеров; недействительный Twitch refresh переводит ChatSource в `AUTH_REQUIRED`.

Временные `device_code`/`user_code` Twitch имеют TTL и хранятся только в RAM; после перезапуска приложения Dashboard предлагает новую попытку авторизации. Выбранный приложением режим логирования `full` применяется как и прежде; лог-файлы должны оставаться в защищённом контуре. Доступ к локальному API и страницам ввода реквизитов ограничивается доверенной сетью.
## 8. Обработка и модель сообщения

Адаптер отдаёт нормализованные данные площадки без доверенных Session/Source, локального порядка и времени приёма Hub. Manager/Hub после проверки актуальности callback формируют окончательную запись:

```text
ChatMessage {
  session_id         // точная сессия
  chat_source_id     // источник конфигурации
  seq                // точный локальный порядок, назначенный Hub
  provider           // youtube | twitch | vk_video_live
  channel_id         // идентичность фактического платформенного чата
  provider_message_id
  provider_timestamp // если платформа предоставляет надёжное значение
  received_at        // время приёма Go-сервером, UTC
  author { id, display_name, color?, avatar_url? }
  text               // безопасный исходный текст
  parts[]            // text | emote, с проверенными URL изображений
  badges[]           // нормализованные метаданные
  kind               // message | supported_system_event
}
```

При публикации ChatHub добавляет `session_id`, `chat_source_id`, локальный `seq` и `received_at` для всех сообщений. При наличии исходного идентификатора `provider_message_id` сохраняет значение платформы. **Дедупликация:** `(session_id, provider, channel_id, provider_message_id)` в пределах удерживаемого окна; `channel_id` означает фактическую беседу: YouTube liveChatID, Twitch broadcasterID, VK channelID. Если конфигурационные источники разделяют один reader, выбирается минимальный ID среди актуальных допущенных ChatSource. Атрибуция первого принятого сообщения сохраняется для фильтрации и не переписывается изменением членства. Это не поддержка двух одновременных публикаций в один канал.

Порядок в общей ленте определяется серверным **порядком получения**, а не сортировкой по времени внешних платформ. Время платформы сохраняется отдельно; межплатформенная последовательность фиксирует порядок получения сервером.

Сообщения отображаются как текст и заранее распознанные структурированные фрагменты; рендеринг выполняется через безопасные DOM-API (`textContent`) и структурированные элементы. Ссылки и изображения проходят проверку схемы URL по разрешённому набору (`https:`).

## 9. RAM-буферы, доставка и переподключения браузеров

### 9.1. ChatHub

Один активный `Session` владеет логически самостоятельной лентой ChatHub с ограниченными по **количеству и суммарному объёму байтов** структурами:

| Начальный проектный бюджет | Значение |
|---|---|
| Последние сообщения Session | **До 1 000 сообщений**, с ограничением по байтам, стартовое значение 16 MiB |
| Одна нормализованная запись | До 64 KiB с явным отказом/учётом переполнения |
| Пакетизация во внутреннем Hub | Сбор до 50 ms или до 100 сообщений перед публикацией |
| Очередь отдельного SSE-клиента | До 256 событий плюс конечный бюджет байтов |
| DOM Overlay | До 50 сообщений |
| DOM Dashboard | До 200 сообщений |
| Срок жизни истории | Оперативная история текущей Session / процесса |

Числа — **исходные пределы для тестирования**, а не подтверждённые измерением оптимумы. Переполнение регистрируется счётчиком и событием `resync_required`/индикацией потери. Медленный подписчик обслуживается в собственной ограниченной очереди, изолированной от upstream Go worker. Соединения ChatHub закрываются при прекращении точной Session; новый запуск использует новый `epoch` и свою последовательность.

### 9.2. SSE

Доставка из ChatHub выполняется через отдельные ресурсы `/api/v1/chat/...`; действующий `/api/v1/events` продолжает обслуживать медиамониторинг:

1. Клиент читает **согласованный** `GET /api/v1/chat/streams/{streamId}/snapshot`: активную Session, её источник/статусы, хвост сообщений и непрозрачный cursor, соответствующий этому снимку.
2. Клиент подписывается на `GET /api/v1/chat/streams/{streamId}/events?cursor=...` через `EventSource`.
3. Сервер выдаёт `id:` как **непрозрачную строку курсора**, а `data:` — типизированный JSON. Поддерживается и `Last-Event-ID` при переподключении. Совпадение одновременных query cursor и заголовка проверяется.
4. События: `chat.message`, `chat.source_status`, `chat.gap`, `resync_required`, `chat.session_closed`. При пропущенном буфере, смене Session/epoch или повреждённом курсоре клиент обязан повторить snapshot.
5. SSE имеет явные пределы клиентов, размера кадра, heartbeat, времени записи и безопасного закрытия, аналогично текущей реализации медиамониторинга.

Внутренний `seq` — точный `uint64`; публичные **числовые** поля в JSON передаются JSON-числами, как в действующем проекте. Браузер выполняет повторную подписку и восстановление по непрозрачному `id`/cursor; `seq` обрабатывается как целое с точностью `uint64`. Поля `id`, `stream_id`, `session_id` остаются строками.

Локальный SSE replay воспроизводит события, фактически полученные ChatHub; возможные upstream-пробелы отображаются отдельно в Dashboard.

## 10. Управляющий REST API

Проектируемые маршруты регистрируются в существующем Chi/Huma API под общим префиксом `/api/v1`.

| Операция | Назначение |
|---|---|
| `GET/POST /api/v1/destinations/{destinationId}/chat-sources` | Список и создание источников конкретного Destination. |
| `GET/PATCH/DELETE /api/v1/chat-sources/{id}` | Чтение, редактирование и удаление ChatSource; `expected_revision` для изменений. |
| `GET /api/v1/chat/accounts` | Санитизированные метаданные учётных записей и состояние авторизации. |
| `GET/PATCH /api/v1/chat/accounts/{id}` | Чтение метаданных и переименование по `expected_revision`, без передачи полномочий. |
| `POST /api/v1/chat/accounts/connect` | Сохранить и проверить API Key YouTube, начать Twitch Device Code либо проверить VK DevAPI client credentials; ответ содержит публичное состояние выполнения. |
| `GET/DELETE /api/v1/chat/accounts/authorizations/{attemptId}` | Прочитать или отменить RAM-попытку подключения; Twitch показывает публичные параметры (`user_code`, `verification_uri`, срок действия). |
| `DELETE /api/v1/chat/accounts/{id}` | Отзыв сохранённой авторизации при отсутствии зависимых ChatSource. |
| `POST /api/v1/chat-sources/{id}/broadcast-selection` | Выбор видео из актуального обнаружения для точных Session/Source/revision; выбор живёт только в RAM текущего запуска. |
| `GET /api/v1/chat/streams/{streamId}/snapshot` | Согласованная начальная лента и состояние текущей Session. |
| `GET /api/v1/chat/streams/{streamId}/events` | SSE событий и сообщений чата. |

HTTP DTO, схемы и ошибки следуют существующим соглашениям: отдельные доменные/storage/HTTP-модели, Problem Details с безопасным `code`, поля времени UTC, `expected_revision`, ясные 404/409/422, серверное формирование OpenAPI из Huma. `POST/DELETE` для аккаунтов управляют привязкой и отзывом авторизации. При создании ChatSource проверяется существование Destination и совпадение типа ChatAccount; при удалении Destination соблюдаются имеющиеся ограничения его жизненного цикла.

Для замены существующего аккаунта connect принимает account_id и expected_revision и не создаёт вторую запись. Его `202` относится к ограниченной RAM-попытке, не к долговечной CommandReceipt; после рестарта незавершённая попытка запускается заново. Snapshot существующего Stream без активной Session успешен, возвращает session:null/messages:[]; настройки доступны отдельно. SSE ожидает появления Session и сообщает resync_required без служебной строки в ленте. Полные входы, результаты и ограничения — в [контракте чатов](docs/chat-contracts.md#целевой-http-контракт).

## 11. HTML-интерфейсы

Обе страницы обслуживаются одним Go HTTP-сервером и включаются в бинарник через `embed.FS`; клиентская часть построена на HTML/CSS/Vanilla JavaScript ES modules.

### 11.1. `/chat/overlay?stream_id=...`

Прозрачный фон, список сообщений, метка платформы, имя/цвет автора, эмодзи, бейджи и при наличии аватар. Подходит для OBS Browser Source и показывает только публичное представление сообщений и визуальных атрибутов. Число DOM-элементов ограничено; добавление и удаление выполняется без удержания всей истории.

### 11.2. `/chat/dashboard?stream_id=...`

Непрозрачная читаемая панель стримера: общая лента, фильтры источников, подключённые платформы, ошибки и состояния, включение/отключение ChatSource, остановка автопрокрутки, счётчик новых сообщений при прокрутке вверх. Отдельное действие привязки ChatAccount: YouTube — ввод API Key и постоянного Channel ID; Twitch — кнопка «Подключить», адрес активации и короткий код Device Code; VK Видео Live — ввод собственного Client ID/Secret. Веб-страница передаёт первоначальные реквизиты backend и отображает санитизированные состояния авторизации; Twitch-токенами управляет сервер.

### 11.3. Общая реализация

Статические HTML/CSS/Vanilla JS ES modules; общие модули EventSource, строгого JSON-разбора/курсора, нормализации визуальной модели, фильтров и безопасного рендеринга. Оперативное состояние открытой страницы находится в памяти JavaScript. Overlay подходит для обычного браузера и OBS Browser Source.

## 12. Надёжность, ограничения и эксплуатация

- **Лимиты:** конечные стартовые бюджеты одновременных ChatSource, WebSocket/gRPC-подключений, буферов, сообщений, SSE-клиентов, snapshot и попыток определены в [контракте](docs/chat-contracts.md#конечные-бюджеты). Числа не являются измеренными оптимумами. Ограничения площадки, Retry-After и протокольные интервалы имеют приоритет; фактические квоты проверяются при реализации адаптера.
- **Повторные попытки:** exponential backoff с jitter; `Retry-After` и ограничения провайдера имеют приоритет; после `AUTH_REQUIRED` ожидать повторную авторизацию от владельца.
- **Совместное чтение:** одно upstream-подключение на `(Session, provider, авторизованный аккаунт, найденный канал)`, если несколько ChatSource требуют тот же канал; ссылочные владельцы подключений независимы от медиавыходов.
- **Дедупликация:** ограниченный TTL/ёмкость ключей сообщений, удерживаемая не дольше текущей Session; восстановленная история YouTube не дублирует уже полученное.
- **Изоляция:** сбой любого адаптера затрагивает его собственный worker; Stream, Session, остальные ChatSource, RTMP-выходы и FFmpeg продолжают работу.
- **Завершение:** `Chat Manager` имеет свой `Close(ctx)` / `Done`; общий `Application.Shutdown` отменяет подключения и SSE, ждёт их освобождения **до закрытия Store**. При частичном запуске уже созданные ресурсы освобождаются тем же владельцем.
- **Рестарт приложения:** при новой Session создаётся новый ChatHub и чтение начинается после фактического `PUBLISHING`. Запуск эфира обслуживается действующим SessionManager.
- **Безопасность:** управление доступно в доверенной локальной сети согласно текущему контракту проекта. Публичные события, снимки, URL Overlay и HTML-страницы содержат санитизированные данные; полномочия платформ хранятся и используются сервером.
- **Поставки:** серверный Go-код и встроенные статические HTML/CSS/JavaScript файлы входят в текущие Debian/архивные артефакты.

## 13. Приёмка

### 13.1. Домен / Session lifecycle

- Создание ChatSource требует существующий Destination; ноль/несколько ChatSource на один Destination работают, провайдер задаётся независимо от `Destination.Platform`.
- При `CONNECTING` ChatSource ожидает; первый действительный `PUBLISHING` запускает reader; `RETRYING` и fallback сохраняют чтение; `STOPPED`/`FAILED`/`stop`/`detach` завершают.
- Автозапуск от OBS, потеря/повторное подключение OBS и ручная пауза сохраняют единственную подписку каждого активного ChatSource.
- Смена `SessionID`/`Incarnation`/`ExecutionFence` отбрасывает запоздалые callbacks; перезапуск отдельного выхода сохраняет состояние соседнего чата.
- Два выхода одного Destination используют одну логическую подписку ChatSource и одну запись каждого сообщения.

### 13.2. Адаптеры и авторизация

- Для каждой площадки — работающий собственный авторизованный эфир и реальное получение новых сообщений; различать подключённый socket и подтверждённую подписку.
- YouTube: обнаружение единственного liveChatId, явный выбор при нескольких эфирах; gRPC resume и типы завершения чата.
- Twitch: `welcome`, подписка, reconnect, revocation; явная фиксация возможных upstream-потерь.
- VK Видео Live: получение app-токена по `client_credentials`, поиск постоянного slug канала, WebSocket-токен, подтверждение подписки `channel-chat:<id>`, парсинг частей и бейджей, перевыпуск токенов и переподключение.
- Проверены получение/обновление/отзыв токенов, санитизацию публичных REST/SSE/Overlay-данных, восстановление после перезапуска Go-процесса только с валидными credential.

### 13.3. Потоки и UI

- Не менее 5, 20 и 100 тестовых сообщений в секунду с контролем ограничений памяти, переполнения и медленных SSE-клиентов.
- Проверка корректной дедупликации, порядка прихода, кириллицы, Unicode, эмодзи, URL-экранирования, бейджей, размеров сообщений.
- Reconnect браузера из RAM, `Last-Event-ID`, расхождение cursor/epoch, переполнение буфера и однозначное `resync_required`.
- Проверка числового контракта JSON на значениях `uint64` выше `2^53`: сервер сохраняет точность, клиент использует непрозрачный курсор.
- Overlay прозрачен и отображает публичные сообщения; Dashboard сохраняет ручную прокрутку и сообщает о новых сообщениях.
- Изоляция медиатракта от чатов проверяется при отказах адаптеров и перезапуске браузера.

**Целевой показатель локальной доставки**: p95 дополнительной задержки **после получения сообщения серверным адаптером** до вывода в открытом браузере — до 3 секунд при оговорённой нагрузке. Задержка самих платформ YouTube/Twitch/VK Видео Live измеряется отдельно от локального ChatHub/SSE.

## 14. Интеграционные проверки перед эксплуатацией

**Выбранные способы доступа:** API Key для YouTube, Device Code для Twitch и DevAPI `client_credentials` для VK Видео Live. Интеграционная проверка выполняется на реальных аккаунтах и собственном VK DevAPI-приложении:

1. **YouTube и Twitch на VM:** для YouTube проверить API Key на публичном канале: поиск эфира `search.list` при включении выхода, получение `activeLiveChatId` через `videos.list`, реальную подписку `streamList` с `x-goog-api-key`, `nextPageToken` и бюджет `search.list` (по умолчанию 100 запросов в сутки). Для Twitch проверить Device Code, получение user token с `user:read:chat`, создание EventSub WebSocket подписки, атомарную ротацию refresh-токена и повторное подключение после перезапуска сервиса.
2. **VK Видео Live:** проверить выдачу токена через `client_credentials`, `GET /v1/channel`, `GET /v1/websocket/token` и получение реального сообщения через Centrifugo-подписку `channel-chat:<id>` для нашего Client ID/Secret. Существует конкретный референс UkiChat с этим путём; приёмка выполняется на собственном проверочном запуске.
3. **Буферы и производительность:** утвердить стартовые границы из раздела 9 (**1000 сообщений на Session**, 16 MiB, 64 KiB на сообщение, пакетизация 50 ms/100 записей, очередь SSE 256, DOM 50/200). Эти значения **приняты как базовые**; нагрузочный тест входит в приёмку выпуска.
