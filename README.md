# gost-restreamer

Сервер рестриминга для собственной инфраструктуры: один поток из OBS, несколько независимых стриминговых площадок и подготовленная заглушка на случай потери источника.

## Возможности

- Приём AV1, HEVC или VP9 с AAC и конечными Opus/FLAC/MP3/AC-3; отправка на RTMP/RTMPS-назначения с применимой обычной либо Enhanced-привязкой.
- Автоматический запуск эфира со всеми включёнными назначениями при подключении OBS.
- Передача AV1, HEVC и VP9 без перекодирования; серверное преобразование в H.264, HEVC или VP9 с разрешением, частотой кадров и качеством по профилю.
- Профили кодирования с NVENC/x264 для H.264, SVT/AOM для AV1, x265/HEVC NVENC для HEVC и libvpx для VP9; CBR/VBR и применимые CQP/CRF, включая SSIM/MS-SSIM/VMAF для SVT.
- SDR-профили с 8/10-битными пикселями, применимыми 4:2:0/4:2:2/4:4:4 и gray, явным преобразованием цвета и масштабированием.
- 10-битный HDR PQ/HLG в применимых профилях с сохранением исходного цвета и MDCV/CLL при подготовке и переключении источников.
- AAC LC: mono, stereo, 2.1, 3.0, 4.0, 5.0, 5.1 и 7.1 с проверкой фактического расположения каналов.
- Opus CELT, FLAC PCM16, MP3 MPEG-1 Layer III и AC-3 с конечными привязками 48 kHz/stereo.
- Независимый выбор обработки LIVE-аудио: копирование совместимого звука либо явное перекодирование; FLAC требует перекодирования.
- Совместное использование результата перекодирования несколькими назначениями одной группы.
- Автоматическое переключение между живым источником и заглушкой с сохранением исправных исходящих соединений.
- Независимое добавление, остановка, повторный запуск и удаление выходов; отдельные очереди и переподключения для каждого назначения.
- Ручная пауза с показом заглушки, история запусков и фоновая очистка ресурсов после сбоев.

## Как устроена трансляция

OBS отправляет один поток на сервер. Группы обрабатывают его по своим профилям: передают исходное видео или перекодируют его для назначений. Звук по умолчанию копируется независимо от обработки видео; `profile.live_audio_mode: "transcode"` явно включает перекодирование звука. Несколько выходов одной группы используют один медиарезультат. Все профили используют единую модель настроек без выбора версии возможностей.

Публикация с правильным постоянным ключом автоматически запускает новую сессию и все включённые назначения, если активного эфира нет. Сервер принимает источник после фактической готовности выбранных локальных групп и заглушек; соединения с площадками устанавливаются независимо. Подключение к запускающейся сессии ожидает её готовности, подключение к работающей сохраняет её ручную паузу и состояние отдельных выходов. Подготовить заглушки нужно до подключения OBS. Для предварительного запуска с заглушки и явного выбора назначений также доступна команда API.

Заглушки подготавливаются до эфира из видео или изображения с цифровой тишиной выбранного аудиокодека. Звук исходного видео не используется. Для каждого профиля сохраняется готовый вариант. Обычно он воспроизводится без повторного кодирования; FLAC-аудио перекодируется одним непрерывным потоком на всю попытку, чтобы сохранять счётчик через петли, видео копируется. Перед запуском проверяется готовность видео и звука заглушки выбранных групп. Сам файл и границы его повторения беззвучны; непосредственно при переходе с LIVE возможен короткий остаток прежнего звука в декодере получателя.

Копирование LIVE-аудио требует совпадения фактических кодека, профиля, частоты, каналов, их расположения и конечной привязки с `format.audio` группы. При несовместимости группа продолжает пригодную заглушку и сообщает причину в журнале; автоматического перекодирования нет. Параметры кодировщика при копировании задают подготовку тишины. При явном перекодировании они применяются также к LIVE.

Многоканальный AAC и режимы качества SVT выбираются параметрами профиля; [зависимости и диапазоны](docs/api-contracts.md#качество-svt-и-многоканальный-aac-lc) проверяются до запуска процесса. SSIM/MS-SSIM/VMAF доступны для SVT CRF. Выход с более чем двумя аудиоканалами использует Enhanced Audio `mp4a`, поэтому получателю нужна поддержка этой формы RTMP; прямое декодирование такого выхода FFmpeg 7.1.5 недоступно. Это не подтверждает приём многоканального звука конкретной площадкой. AAC HE/HEv2/LD/ELD и SVT `iq` не поддерживаются.

[SDR-матрица](docs/api-contracts.md#sdr-форматы-цвет-и-кодировщики) включает x264 для LIVE H.264 и заглушек, AOM для заглушек AV1, применимые профили и цветовые характеристики. AV1 LIVE копируется. x264 принимает CRF с шагом 0,01; у SVT и AOM CRF целочисленный. Допустимые сочетания определяются кодеком, кодировщиком и параметрами. Для каждого полного профиля нужно подготовить совместимый вариант заглушки до эфира.

Видео преобразуется по фактическим исходным цветовым характеристикам. Для совместимого AV1 → H.264 NVENC с SDR BT.709/8-bit/4:2:0 сохраняется путь NVDEC/CUDA; остальные поддержанные сочетания используют программное декодирование и преобразование. PNG/JPEG и SDR-видео 8-bit/4:2:0 без полного цветового описания допускаются в ограниченной подготовке SDR BT.709/8-bit/4:2:0 через SVT AV1 или H.264 NVENC с AAC. Такой результат не доказывает исходный цвет изображения. NVENC lossless ограничен H.264 High 4:4:4/8-bit, CQP 0 и совместимыми настройками; он относится к входу кодировщика после преобразований. Работа аппаратного пути проверяется отдельно на NVIDIA.

[HEVC, VP9 и HDR](docs/api-contracts.md#hevc-vp9-и-hdr) входят в общую модель. Для HEVC доступны Main/8-bit и Main10/10-bit; для VP9 — profile0/8-bit и profile2/10-bit, в обоих случаях 4:2:0. HEVC/VP9 можно копировать либо перекодировать. HDR требует 10 бит, BT.2020, PQ или HLG и согласованного диапазона. Изменение FPS и размеров допускается, преобразование SDR↔HDR, PQ↔HLG и tone mapping не выполняются. AV1 LIVE остаётся copy, H.264 — transcode.

Для HDR-заглушки нужен MOV/MP4-источник с достоверным статичным цветовым описанием. Сервер проверяет его до публикации нового комплекта, сохраняет исходные MDCV/CLL и восстанавливает их при открытии и повторении файла. Эти сведения не являются заново измеренными максимумами результата. Неподдержанное или изменяющееся описание отклоняет подготовку и сохраняет прежний рабочий комплект. HDR-подготовка из изображений не поддерживается.

[Opus, FLAC, MP3 и AC-3](docs/api-contracts.md#opus-flac-mp3-и-ac-3) имеют конечные выходы 48 kHz/stereo и фиксированный рецепт: Opus CELT 2,5 ms/VBR с target 128 кбит/с, FLAC PCM16 с неприменимым target 0, MP3 MPEG-1 Layer III 128 кбит/с без reservoir, AC-3 192 кбит/с без LFE. FLAC требует явных video/аудио transcode; у остальных copy проверяет фактическую привязку. Аудиокодировщик выбирается явно.

Получателю нужны Enhanced Audio `Opus`, `fLaC`, `.mp3` либо `ac-3`. Начальный Opus pre-skip ограничен 0/120 и обрабатывается один раз; частичные аудиохвосты вне этой привязки отклоняются. Продолжаемый FLAC принимает блоки 48…4608 сэмплов, подготовленный файл — только полные 4608. Неподдержанный поток не дополняется нулями и не получает скрытой смены кодека. Локальная проверка приложения не подтверждает приём этих форм конкретной площадкой.

HEVC, VP9 и HDR требуют поддержки соответствующей Enhanced RTMP-привязки получателем. Локальные CPU- и протокольные проверки не подтверждают приём конкретной площадкой, работу HEVC NVENC на NVIDIA или длительную устойчивость; [границы проверок](docs/media-contracts.md#target-acceptance) учитываются отдельно.

Подготовка и `rebuild` недоступны во время активного эфира, включая ручную паузу. Пригодность файла проверяется по полному профилю, фактическому формату и текущему контракту генератора `fallback-fmp4-silent-v2`.

Настройки профиля принимаются обычными UTF-8 строками из [допустимых наборов](docs/string-json-contracts.md). Поля выбора версии профиля и `encoding.version` отсутствуют. Сохранённые профили содержат все применимые настройки; чтение и переименование не назначают значения по умолчанию.

Отказ или переподключение одного назначения затрагивает только его выход. Обрыв OBS включает заглушку; явная команда API останавливает эфир и выходы. Во время остановки публикация отклоняется, после её завершения новое подключение OBS может запустить следующий эфир. Для окончательного завершения клиент прекращает отправку из OBS и вызывает API остановки.

После перезапуска сервера прежний эфир сам не возобновляется: новый запускается командой API или новой публикацией OBS. Очистка ресурсов прежнего запуска выполняется в фоне независимо от нового. Таймаут подключения OBS после принятия запуска не отменяет созданную сессию; её состояние и завершение доступны через API.

## Технологии

Go, FFmpeg и SQLite с GORM/Goose. Обмен с FFmpeg идёт через Unix-сокеты в формате fMP4; исходящие RTMP/RTMPS-соединения обслуживаются в Go. Путь обработки определяется фактическим форматом и выбранным кодировщиком: поддержаны ограниченный NVDEC/CUDA → NVENC и программное преобразование с CPU-кодировщиками либо NVENC. Целевая серверная среда — Debian 13 (`trixie`), `linux/amd64`. Сервис и дочерние процессы запускаются от root; оба бинарника устанавливаются в `/opt/gost-restreamer`.

## Среда разработки

Требуются Go `1.27.3`, GNU Make и C-компилятор; CGO используется SQLite-драйвером. Версии Go и линтера закреплены в `go.mod` и `Makefile`. Инструменты и платформозависимые возможности проверяются для выбранной ОС разработки.

```sh
make tools
make check
```

`make tools` устанавливает закреплённый `golangci-lint` в `bin/` проекта. `make check` выполняет проверку форматирования и модулей, vet, линтер, тесты, проверку покрытия не ниже 85%, race и сборку пакетов.

Для показателей NVIDIA используется NVML на Linux с CGO. На macOS сборка и обычные тесты работают без NVML; показатели NVIDIA имеют явный статус недоступности. Аппаратные показания проверяются отдельно на целевом сервере.

| Команда | Действие |
| --- | --- |
| `make help` | Список команд проекта. |
| `make fmt` / `make fmt-check` | Форматирование Go-кода / проверка форматирования. |
| `make test` / `make test-race` | Тесты / тесты с детектором гонок. |
| `make coverage` | Свежий полный набор тестов и проверка покрытия ≥85% без исключений. |
| `make vet` / `make lint` | Статический анализ. |
| `make build` | Сборка Go-пакетов. |
| `make binary` | Сборка сервиса в `bin/gost-restreamer`. |
| `make process-helper` | Сборка `bin/gost-process-helper` для управления дочерними FFmpeg/ffprobe. |
| `make package VERSION=<версия>` | Оба бинарника, пример YAML, systemd-unit, архив текущей платформы и проверенная SHA-256. |
| `make package-debian VERSION=<версия>` | GoReleaser Community `2.19.0`: `.deb`, `.tar.gz` и SHA256 для Debian 13/amd64; нужен чистый checkout с соответствующим локальным тегом. |
| `make release-check` | Проверка конфигураций GoReleaser и тесты повторного выпуска; нужны GoReleaser `2.19.0` и Node.js `24`. |

### Запуск сервиса

Собираются оба исполняемых файла:

```sh
make binary process-helper
```

Версию обоих бинарников можно прочитать без конфигурации и запуска сервиса:

```sh
./bin/gost-restreamer --version
./bin/gost-process-helper --version
```

Вывод содержит версию приложения, commit, признак локальных изменений и версию Go. Выпуски имеют вид `v0.1.0`, сборки разработки — `v0.2.0-dev.1+<commit>`. Для явно назначенной локальной версии используйте `make binary process-helper VERSION=v0.2.0-dev.1+a1b2c3d`. Без `VERSION` используются доступные метаданные Go; при их отсутствии выводится `devel` и неизвестное происхождение. Формат версий и определение происхождения сборки описаны в [контракте версионирования](docs/versioning.md).

Настройки инсталляции задаются YAML-файлом на основе [примера](configs/example.yaml). Перед локальным запуском нужно выбрать доступные абсолютные каталоги данных и runtime и настроить путь к собранному helper. Параметр `--config` выбирает файл:

```sh
./bin/gost-restreamer --config /absolute/path/to/config.yaml
```

Файл может содержать только нужные переопределения, например:

```yaml
paths:
  data: /absolute/path/to/local-data
  runtime: /tmp/gost-restreamer
executables:
  helper: /absolute/path/to/gost-restreamer/bin/gost-process-helper
```

Без параметра используются `/etc/gost-restreamer/config.yaml` и, при его отсутствии, `config.yml` в том же каталоге. При наличии обоих выбирается `.yaml` и выводится предупреждение. Встроенные defaults заполняют пропущенные поля, неизвестные настройки останавливают запуск. Изменения файла применяются после перезапуска.

HTTP API доступен под `/api/v1`; стандартные адреса — HTTP `:8080` и ingest `:1935`. Управление работает без авторизации в локальном контуре владельца. Отсутствие NVIDIA или FFmpeg отражается отдельно от готовности управления; для медиазапуска нужны соответствующие компоненты. Полный контракт выбора конфигурации, OBS-маршрута и остановки — в [документации приложения](docs/application-contracts.md).

### Установка на Debian 13

Поставка для Debian 13/amd64 содержит `.deb`, `.tar.gz` и `SHA256SUMS`. Сборки разработки доступны через GitHub Actions → нужный запуск → Artifacts; срок хранения — 14 дней.

Устанавливайте `.deb` на Debian 13/amd64: проверьте `sha256sum -c gost-restreamer-<Git-версия>-SHA256SUMS`, затем выполните `apt install ./gost-restreamer_<Debian-версия>_amd64.deb` от root. Оба бинарника устанавливаются в `/opt/gost-restreamer`, конфигурация — в `/etc/gost-restreamer/config.yaml`. После настройки службу нужно явно запустить через `systemctl enable --now gost-restreamer`. Обновление останавливает службу; после проверки настроек запустите её вручную. Debian conffiles сохраняют изменённые YAML и unit; SQLite и медиа сохраняются при обновлении и удалении. [Инструкция установки, обновления и диагностики](docs/deployment.md) описывает точные команды и зависимости FFmpeg/NVIDIA.

Если сервис установлен вручную из `.tar.gz`, перед первой установкой `.deb` явно остановите `gost-restreamer` и используйте `apt -o Dpkg::Options::=--force-confold install ./<пакет>.deb`, чтобы сохранить локальные YAML и unit. В инструкции описаны [скачивание dev-поставки прямо на VM](docs/deployment.md#скачивание-dev-поставки-прямо-на-vm) и [обновление с проверкой версий и readiness](docs/deployment.md#обновление-и-переход-с-ручной-установки).

OBS использует один штатный AV1/AAC-выход; группы и независимые назначения обслуживает backend. [Руководство клиента](docs/obs-client-guide.md) содержит примеры настройки, команд и REST/SSE для отдельного OBS-плагина.

Встроенных средств резервного копирования и восстановления из копий нет. `PUBLISHING` означает состояние серверной отправки; фактическое воспроизведение проверяется на принимающей площадке. Переключение заглушки сохраняет исправные соединения работающего процесса; падение процесса, VM или внешней сети их не сохраняет. Результаты проверки медиатракта и границы целевой приёмки приведены в [медиаконтракте](docs/media-contracts.md#target-acceptance).

### Медиапроверки с FFmpeg

Обязательные проверки Go работают без FFmpeg, GPU и внешних площадок. Для CPU-интеграций нужны `ffmpeg` и `ffprobe` версии `7.1.5`, кодировщики `libaom-av1`, `libsvtav1`, `libx264`, `libx265`, `libvpx-vp9`, `aac`, `libopus`, `flac`, `libmp3lame`, `ac3`, фильтры zscale/setparams и протокол `async`.

Запуск в POSIX shell:

```sh
GOST_MEDIA_FFMPEG="$(command -v ffmpeg)" \
GOST_FMP4_FFMPEG="$(command -v ffmpeg)" \
go test -count=1 ./internal/fallback ./internal/media/fmp4 ./tests/integration
```

Короткая проверка структурированного progress штатной файловой команды FFmpeg:

```sh
GOST_MEDIA_FFMPEG="$(command -v ffmpeg)" \
go test -count=1 ./internal/media/ffmpeg -run '^TestFileCommandCPUProgress$'
```

<summary>Дополнительная аппаратная проверка на macOS</summary>

На машине с доступным VideoToolbox можно явно проверить аппаратное кодирование H.264:

```sh
GOST_MEDIA_FFMPEG="$(command -v ffmpeg)" GOST_MEDIA_VIDEOTOOLBOX=1 \
go test -count=1 ./tests/integration -run '^TestAcceptanceProfileConversionCPUAndOptionalVideoToolbox$'
```

Сценарий использует `h264_videotoolbox -allow_sw 0`; AV1-декодирование, изменение FPS и масштабирование выполняются на CPU. Условия аппаратных проверок описаны в [профиле среды разработки](CODEX_PROJECT.md#среды-разработки-и-локальные-медиапроверки).
