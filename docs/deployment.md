# Установка и обслуживание

Целевая установка — Debian 13 / `linux/amd64` в домашней VM Proxmox владельца; фактически проверенная версия VM — Debian 13.4 (`trixie`). Оба бинарника устанавливаются в `/opt/gost-restreamer`. Сервис, `gost-process-helper`, FFmpeg и ffprobe запускаются от `root`. Отдельный системный пользователь не создаётся. Фактическая установка, доступ к RTX A1000 и эфиры проверяются в T11.

## Состав поставки и скачивание

CI формирует один `.deb` с обоими бинарниками, `.tar.gz` с теми же бинарниками, примером YAML и unit, а также общий `gost-restreamer-<Git-версия>-SHA256SUMS`. Рабочие конфигурации, БД, медиа и журналы в поставку не входят. В Debian-пакет не включены FFmpeg, ffprobe, драйверы NVIDIA и NVML.

| Файл | Пример имени |
| --- | --- |
| Debian package | `gost-restreamer_0.2.0~dev.1+abc123_amd64.deb` или `gost-restreamer_0.2.0_amd64.deb` |
| Архив | `gost-restreamer-v0.2.0-dev.1+abc123-linux-amd64.tar.gz` или `gost-restreamer-v0.2.0-linux-amd64.tar.gz` |
| Контрольные суммы | `gost-restreamer-v0.2.0-dev.1+abc123-SHA256SUMS` или `gost-restreamer-v0.2.0-SHA256SUMS` |

После merge в `develop` скачайте ZIP из Actions → успешный запуск → Artifacts и распакуйте его. Артефакты хранятся 14 дней с учётом настроек GitHub; Git-тег остаётся после их истечения. Dev GitHub Releases не создаются. После merge в `main` файлы прикрепляются к **Draft Release**, доступному владельцу до ручной публикации. Владелец проверяет успешность workflow и файлы, затем нажимает Publish release. CI не публикует draft, не заменяет его существующие файлы и не изменяет уже опубликованный релиз. Не публикуйте вручную одновременно с выполняющимся повтором workflow.

`make package-debian VERSION=<Git-версия>` использует GoReleaser Community `2.19.0` и nFPM. Нужны Debian 13/amd64, Go `1.27.3`, C-компилятор, CGO=1 и чистый checkout с соответствующим локальным тегом на HEAD. Цель не отправляет тег и ничего не публикует. `make package` сохранён как прежняя локальная сборка архива текущей платформы; его `.sha256` не является форматом новой поставки CI, а Darwin-архив не подходит для Debian.

CI сверяет реальные версии/commit обоих бинарников, состав пакета, права, conffiles и SHA256. Новая сборка настроена на `golang:1.27.3-trixie`. Исторический успешный запуск T10 ниже использовал Debian 12; он не подтверждает новую GoReleaser/CGO-сборку и установку на Debian 13.

### Скачивание dev-поставки прямо на VM

GoReleaser нужен только для сборки. На VM устанавливается готовый `.deb`; для скачивания и распаковки ZIP нужны `curl` и `unzip`.

Проверенный 8 ноября 2026 года пример — [успешный GitHub Actions №10](https://github.com/GregoryGost/gost-restreamer/actions/runs/42429626734), версия `v0.1.0-dev.3+09534d305f31`, artifact ID `13596619394`. Для следующей поставки возьмите версию и artifact ID из её успешного запуска. Артефакт примера имеет срок хранения до 22 ноября 2026 года и может быть удалён раньше; повтор CI получает другой ID.

Команды выполняются в Bash от root непосредственно на Debian VM. Если `GH_TOKEN` уже задан в этой оболочке, используется его текущее значение; иначе команда запрашивает токен без отображения ввода. Для скачивания Actions Artifact через API нужен токен с доступом на чтение Actions выбранного репозитория; публичность исходников не меняет этот способ скачивания. [Требования GitHub к download endpoint](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact).

```bash
(
  set -eu
  git_version='v0.1.0-dev.3+09534d305f31'
  artifact_id='13596619394'
  download_dir="/root/downloads/gost-restreamer-$git_version"
  install -d -m 0700 "$download_dir"
  cd "$download_dir"

  if [ -z "${GH_TOKEN:-}" ]; then
    read -rsp 'GitHub token: ' GH_TOKEN
    printf '\n'
  fi
  test -n "$GH_TOKEN"
  curl --fail --location --show-error \
    --header 'Accept: application/vnd.github+json' \
    --header "Authorization: Bearer $GH_TOKEN" \
    --output gost-restreamer-artifact.zip \
    "https://api.github.com/repos/GregoryGost/gost-restreamer/actions/artifacts/$artifact_id/zip"
  unzip -o gost-restreamer-artifact.zip
  sha256sum --strict -c "gost-restreamer-$git_version-SHA256SUMS"
  printf 'Поставка проверена: %s\n' "$download_dir"
)
```

В каталоге остаются ZIP и все три файла поставки. Общий `SHA256SUMS` проверяет и `.deb`, и `.tar.gz`, поэтому при распаковке нужны оба файла. Распаковывать внутренний `.tar.gz` для установки `.deb` не требуется. Прежняя команда проверки `<архив>.tar.gz.sha256` относится к старой поставке и локальной цели `make package`.

## Требования к VM

На VM должны быть доступны FFmpeg и ffprobe, подходящая сборка FFmpeg для NVDEC/NVENC и драйвер NVIDIA с доступом к переданному в VM GPU. Проверенная медиаграница использует FFmpeg/ffprobe `7.1.5`, `libsvtav1`, `h264_nvenc`, AAC, CUDA-фильтры и протокол `async`. Наличие executable или списка кодировщиков не доказывает аппаратную работоспособность; её проверяет T11.

Управляющий API слушает `:8080`, OBS ingest — `:1935`. Эти адреса меняются через YAML. Управление в локальном контуре владельца работает без авторизации. Состояние API доступно отдельно от медиавозможностей.

## Новая установка

Команды выполняются от root на целевой Debian 13/amd64 VM. Скачайте все три файла в один каталог; `v0.2.0` ниже — пример стабильной версии:

```sh
cd /root/downloads
sha256sum --strict -c gost-restreamer-v0.2.0-SHA256SUMS
apt install ./gost-restreamer_0.2.0_amd64.deb
/opt/gost-restreamer/gost-restreamer --version
/opt/gost-restreamer/gost-process-helper --version
```

APT устанавливает объявленные зависимости `libc6 (>= 2.41)` и `systemd`. FFmpeg/NVIDIA подготавливаются отдельно по требованиям VM. Пакет помещает бинарники с режимом `0755`, YAML — `0600` в каталог `0700`, unit — `0644`. Владелец файлов — root. YAML и unit зарегистрированы как Debian conffiles; уже существующий локально изменённый файл требует обычного решения dpkg о сохранении. Для сохранения прежних настроек можно явно передать `-o Dpkg::Options::=--force-confold` команде APT.

Установка выполняет `systemctl daemon-reload`, если запущен systemd. Автоматического enable/start нет. Настройте `/etc/gost-restreamer/config.yaml` до явного запуска. Unit выбирает `config.yaml`; для существующего `config.yml` измените `ExecStart` через `systemctl edit gost-restreamer`, сбросив прежний `ExecStart=` и указав нужный полный путь. Правила YAML и defaults — в [контракте приложения](application-contracts.md).

Стандартные пути:

| Назначение | Путь |
| --- | --- |
| Сервис и helper | `/opt/gost-restreamer/gost-restreamer`, `/opt/gost-restreamer/gost-process-helper` |
| Конфигурация | `/etc/gost-restreamer/config.yaml` |
| SQLite, fallback и долговечные журналы владения | `/var/lib/gost-restreamer/` |
| UDS и доказательства владения runtime-объектами | `/run/gost-restreamer/` |

Unit задаёт `PATH=/opt/gost-restreamer:/usr/local/bin:/usr/bin:/bin`. Пример конфигурации ищет helper, FFmpeg и ffprobe по этому PATH. При другом расположении задайте абсолютные `executables.helper`, `executables.ffmpeg` и `executables.ffprobe`. Параметры `paths.data` и `paths.runtime` также должны быть абсолютными. При изменении рабочих каталогов согласуйте `WorkingDirectory`, `StateDirectory` и `RuntimeDirectory` unit с YAML.

```sh
systemd-analyze verify /etc/systemd/system/gost-restreamer.service
systemctl daemon-reload
systemctl enable --now gost-restreamer
systemctl status gost-restreamer
curl --fail http://127.0.0.1:8080/api/v1/health/ready
```

`Type=exec` подтверждает запуск executable; прикладную готовность нужно читать через HTTP. Миграции и recovery хранилища выполняются до начала обслуживания API. Сам факт запуска службы не начинает эфир: Session запускается явной командой через API.

## Остановка, перезапуск и runtime

```sh
systemctl stop gost-restreamer
systemctl start gost-restreamer
systemctl restart gost-restreamer
journalctl -u gost-restreamer -f
```

Служба создаёт каталоги данных и runtime с владельцем `root:root` и режимом `0700`, задаёт `UMask=0077`. `RuntimeDirectoryPreserve=yes` сохраняет runtime-каталог при stop/start и restart: его содержимое участвует в доказательствах безопасной очистки. Семантика параметров задана [systemd.exec Debian 13](https://manpages.debian.org/trixie/systemd/systemd.exec.5.en.html).

`KillMode=mixed` сначала направляет SIGTERM основному процессу, позволяя приложению завершить собственных пользователей и helper. Если основной процесс уже вышел либо истёк `TimeoutStopSec`, оставшиеся процессы группы могут получить SIGKILL. Это следует из [systemd.kill Debian 13](https://manpages.debian.org/trixie/systemd/systemd.kill.5.en.html). Принудительное завершение не записывает от имени приложения успешное подтверждение cleanup.

В примере `lifecycle.shutdown_timeout=30s`, а `TimeoutStopSec=40s`. При увеличении срока приложения увеличьте и предел systemd с запасом. Если приложение сообщает ошибку или неподтверждённое завершение, сохраняются его журналы и удержания; удаление каталогов вручную не заменяет подтверждения. Отдельная systemd-служба для helper не нужна: его запускает приложение для управляемой команды.

Каталог `/run` временный и теряется при перезагрузке VM. Сохранение при restart службы не обещает сохранение после reboot. Утраченные доказательства не позволяют объявить прежний cleanup успешным; новый ручной start использует отдельное выполнение по существующему контракту. История и долговечное управление остаются в каталоге данных. Протокол описан в [контракте SessionManager](session-manager-contracts.md).

## Обновление и переход с ручной установки

Ранее установленные вручную бинарники из `.tar.gz` и unit можно заменить установкой `.deb` по тем же путям. Перед первой установкой пакета **явно остановите службу**: у ручной установки нет зарегистрированного в dpkg старого `prerm`, который мог бы сделать это перед заменой файлов. Успешный stop сессии через API завершает эфир; остановка systemd-службы отдельно завершает процесс сервиса.

Следующий пример продолжает скачивание версии `v0.1.0-dev.3+09534d305f31` выше. Он подходит и для перехода с ручной установки, и для обновления уже зарегистрированного пакета; команды выполняются от root на VM:

```bash
(
  set -eu
  cd /root/downloads/gost-restreamer-v0.1.0-dev.3+09534d305f31
  deb='./gost-restreamer_0.1.0~dev.3+09534d305f31_amd64.deb'
  sha256sum --strict -c gost-restreamer-v0.1.0-dev.3+09534d305f31-SHA256SUMS
  dpkg-deb --field "$deb" Package Version Architecture

  systemctl stop gost-restreamer
  apt -o Dpkg::Options::=--force-confold install "$deb"
  /opt/gost-restreamer/gost-restreamer --version
  /opt/gost-restreamer/gost-process-helper --version
  dpkg-query --show --showformat='${Package} ${Version} ${Architecture}\n' gost-restreamer
  systemd-analyze verify /etc/systemd/system/gost-restreamer.service
  systemctl start gost-restreamer
  systemctl status gost-restreamer --no-pager --lines=0
  curl --fail-with-body --silent --show-error \
    --retry 10 --retry-delay 1 --retry-connrefused \
    --connect-timeout 2 --max-time 3 \
    --write-out '\n' \
    http://127.0.0.1:8080/api/v1/health/ready
)
```

Оба `--version` должны показать `v0.1.0-dev.3+09534d305f31` и commit `09534d305f313a6b94fa4aa335fce00c6822f889`; поле Debian Version — `0.1.0~dev.3+09534d305f31`. Для следующего выпуска замените каталог, имя `.deb` и `SHA256SUMS` на файлы одной выбранной поставки.

Флаг `--force-confold` сохраняет существующие локально изменённые YAML и unit, включая файлы прежней ручной установки; новая редакция может появиться как `.dpkg-dist`. Неизменённые conffiles dpkg обновляет автоматически. Существующий рабочий YAML продолжает использоваться; пример из архива предназначен для сверки новых параметров. SQLite и медиа остаются в `/var/lib/gost-restreamer/`, runtime-доказательства — в `/run/gost-restreamer/`. Оба бинарника после перехода обслуживаются пакетным менеджером. [Правила dpkg для conffiles](https://manpages.debian.org/trixie/dpkg/dpkg.1.en.html#confold:).

При последующем обновлении `.deb` старый `prerm upgrade` дополнительно останавливает службу перед заменой бинарников. При ошибке dpkg вызывает новый `prerm failed-upgrade`: он также проверяет остановку и распространяет ошибку, если остановить службу не удалось. Уже отсутствующий и неактивный unit пропускается. После установки перечитываются unit; автоматического старта нет, в том числе при восстановлении после неудачного обновления. Предпочитайте systemd drop-in через `systemctl edit` для локальных настроек unit. Перед запуском проверьте сохранённые локальные настройки и новые параметры поставки. Прежний эфир автоматически не возобновляется; после успешного readiness новый запуск принимается через API в рамках T11.

## Удаление

Стандартное удаление останавливает службу, отключает существующий unit и удаляет бинарники, сохраняя conffiles и пользовательские данные:

```sh
apt remove gost-restreamer
```

`apt purge gost-restreamer` дополнительно удаляет принадлежащие пакету conffiles YAML и unit. SQLite, медиа и остальные постоянные данные в `/var/lib/gost-restreamer/` сохраняются и при purge. Скрипты не удаляют `/run/gost-restreamer/`: доказательства runtime должны оставаться до штатной очистки приложения или reboot. Пользовательские systemd drop-in не удаляются скриптами. Новая установка и обновление не выполняют миграции сами; хранилище открывает приложение при следующем запуске.

Debian-версии упорядочены как `0.2.0~dev.1+… < 0.2.0~dev.2+… < 0.2.0 < 0.3.0~dev.1+…`. Точный Git-тег, включая `v` и `+commit`, остаётся внутри обоих бинарников. [Правила версионирования](versioning.md) также описывают повторные сборки и отсутствие смены номера при повторе CI.

Текущая разработка использует одну первичную схему. Несовместимая development-БД отклоняется без автоматического пересоздания; искусственная миграция старых development-форматов не поставляется. Отказ миграции или открытия БД завершает startup. До успешной готовности не считайте обновление принятым и не удаляйте прежние данные для обхода ошибки.

Резервное копирование и восстановление из резервных копий, их инструкции и автоматизация отложены решением владельца. Эта процедура их не выполняет.

## Диагностика

Читайте `/api/v1/health/live`, `/api/v1/health/ready` и `/api/v1/system/capabilities` отдельно. Успешный readiness означает готовность управления и хранилища; успешную работу NVENC/NVDEC или получение видео площадкой он не подтверждает. Ошибка helper препятствует сборке приложения, а недоступные FFmpeg/NVIDIA сообщаются отдельно и проверяются владельцами соответствующих операций.

Журнал приложения — JSON в stderr, который unit направляет в journald. Выбран режим `full`: записанные диагностические поля сохраняют полные значения, включая ключи и URL. Доступ и срок хранения журнала определяются настройками локального journald. Внешний экспортёр и отдельный архиватор логов не добавляются.

После перезапуска прежний эфир отмечается прерванным и автоматически не возобновляется. Постоянство исходящих соединений при переключении LIVE/fallback проверяется внутри работающего процесса; падение процесса, VM и внешней сети этих соединений не сохраняет. `PUBLISHING` означает наблюдение отправки, а просмотр на площадке проверяется отдельно в T11.

## Локальные результаты и границы приёмки

Локальная реализация поставки подготовлена на Darwin/arm64 с Go `1.27.3`, CGO=1, линтером `2.15.0`, gopls `0.24.0` и FFmpeg/ffprobe `7.1.5`. Настоящий нативный архив проверен по составу четырёх файлов, SHA-256, распакованным байтам, executable-битам и версиям обоих бинарников. Этот этап проверял Darwin-артефакт; исполнение Linux CI и выдача Debian 12 CGO-архива тогда оставались непроверенными. Docker, Podman и `systemd-analyze` в этой локальной среде отсутствуют.

Стабильный `candidate-v1` из 425 входов прошёл полный `make check`: покрыто **14393/16589 инструкций — 86,762312%**, точный порог 85% пройден без исключений; vet, lint, race и сборка прошли. Новые сценарии используют настоящий API/SessionManager/SQLite/Goose/FileStore/UDS/RTMP; генератор и кодировщики структурного полного потока контролируются тестами. Отдельная CPU-регрессия с настоящим FFmpeg прошла **10 верхнеуровневых тестов / 24 конечных сценария**, без VideoToolbox и GPU. Проверены декодирование, короткие петли, A/V и временные шкалы. Реальный `SQLITE_FULL` получен лимитом страниц временной БД; заполнение диска ОС этим не подтверждено.

В свежем независимом normal-прогоне того же снимка новый полный HTTP-сценарий получил `FAILED/ErrInvalid` на запуске до media workers. Первая диагностика и исходный независимый `NOT_ACCEPTED` сохранены. Два последующих полных диагностических прогона прошли; они не установили историческую причину и не заменяют приёмку.

Отдельный контрольный опыт без изменения репозитория запустил четыре изолированные фикстуры. С тестовым сроком операции 300 ms получены три отказа: фоновые FILE cleanup-записи исчерпали контекст, последующая сверка не смогла подтвердить свежесть и отозвала SessionObserver; Registry отклонил его при остальных корректных параметрах. С единственным изменением срока до штатных 5 s прошли все четыре сценария. Это подтверждение конкретного воспроизводимого пути, а не доказательство точного триггера первого события. Защитный отзыв является существующим контрактом и сохранён.
