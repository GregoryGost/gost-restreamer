# Контракты домена и хранения чатов

Подсистема собирает только сообщения для чтения. Конфигурация и полномочия площадок сохраняются в SQLite; сообщения, состояния, подключения, попытки авторизации, дедупликация и курсоры принадлежат оперативной памяти процесса. Общая архитектура описана в [спецификации чатов](../chat-architecture.md).

Домен и репозитории хранят настройки и полномочия. Внутренний пакет `internal/chat` управляет оперативными лентами, связывает источники с медиавыходами и предоставляет порты для подключения адаптеров. Сетевую авторизацию и чтение платформ выполняют адаптеры. Целевые HTTP-маршруты и страницы описаны как граница интеграции приложения.

## Представления и владельцы

- `internal/core` определяет доменные значения, структурную валидацию, сервисы, интерфейсы репозиториев и типизированные контракты сообщений и бюджетов. Он не импортирует GORM, Huma, FFmpeg или сетевые SDK.
- `internal/storage` отображает конфигурацию и полномочия в GORM/SQLite, реализует короткие транзакции, CAS и перевод ошибок. Репозиторий доступен только внутри callback существующего UnitOfWork.
- Chat Manager сопоставляет настройки с фактическими Session/Output, управляет привязками источников и жизненным циклом чтения. ChatHub задаёт порядок сообщений и хранит историю и журнал событий одной Session.
- Владелец полномочий сериализует внешние обмены и сверку сохранения отдельно для каждого аккаунта. Адаптер обнаруживает платформенный чат и нормализует данные. Идентичность Session и локальный порядок назначает сервер.
- HTTP DTO отделены от доменных и storage-моделей. Обычные чтения ChatAccount/ChatSource не содержат ключей или токенов; серверное чтение полномочий имеет отдельный явный порт. Политика локального журнала `full` сохраняется.

## Конфигурация источников и аккаунтов

`ChatSource` содержит общую Record, обязательные DestinationID, AccountID и Provider, необязательное имя, явный Enabled, постоянный ChannelHint и типизированные Options. Provider выбирается из `youtube`, `twitch`, `vk_video_live` независимо от свободного Destination.Platform. Эти значения структурно допустимы до появления runtime-адаптеров.

Источник имеет ровно один Destination. Его родитель и время создания после вставки неизменны; перенос к другому Destination выполняется созданием другой записи. Provider/account/channel/options можно заменить вместе одной CAS-операцией с полной проверкой согласованности. Имя и Enabled также меняются через обычный CAS.

ChannelHint означает:

| Provider | Постоянное значение |
| --- | --- |
| `youtube` | Непустой Channel ID с префиксом `UC`; конкретную принадлежность видео подтверждает адаптер. |
| `twitch` | Пустое значение для собственного авторизованного пользователя либо явный десятичный broadcaster ID. |
| `vk_video_live` | Постоянный slug канала; произвольный URL не принимается. |

Options имеют версию 1 и ровно один типизированный вариант, соответствующий Provider. Начальные варианты пусты: дополнительные постоянные настройки не согласованы. Неизвестные поля, версии и несовпадающий вариант отклоняются без подстановки другого значения. YouTube Video ID не сохраняется в options.

`ChatAccount` содержит конфигурационную Record, неизменный Provider и необязательное имя. Метод подключения определяется Provider. Один аккаунт может обслуживать несколько источников своего провайдера. Глобальной уникальности канала или пары Destination/provider нет: исключённый сценарий двух одновременных публикаций в один канал не превращается в ограничение всех конфигурационных строк.

Новые идентификаторы чатов, ссылки, ChannelHint и ID сообщений ограничены 256 байтами UTF-8, имя — 512, URL — 4096; структурированное сообщение содержит до 256 частей и 64 бейджей. Корректность UTF-8 и отсутствие нулевых символов проверяются до сохранения или принятия значения. Платформенные ограничения сверх известной формы подтверждаются адаптером.

## Полномочия и две ревизии

`ChatCredentialBundle` содержит набор своего провайдера. Отдельное серверное значение `ChatCredentials` связывает его с аккаунтом, CredentialRevision, временем изменения и CredentialWriteID. `ChatCredentialResult` возвращает доверенному владельцу согласованные метаданные аккаунта и полномочия; HTTP не сериализует этот внутренний результат целиком.

| Provider | Сохраняемые полномочия |
| --- | --- |
| YouTube | API Key Google Cloud. |
| Twitch | Client ID, reader User ID, access/refresh-пара, scopes с `user:read:chat` и срок access token. |
| VK Видео Live | Client ID/Secret, app access token и срок. |

Временные Device Code/user code и ещё не принятые результаты авторизации не становятся долговечными сущностями. Первый аккаунт сохраняется с полным набором после успешной внешней проверки доверенным backend-компонентом. Core/storage проверяют структуру, но не утверждают действительность токена на площадке. Истечение срока не делает сохранённую строку нечитаемой: структурная проверка не сравнивает её с текущими часами.

В одной строке Account раздельно хранятся config payload и credential payload с собственными служебными полями. Обычные чтения и списки аккаунтов полномочия не декодируют и не возвращают.

| Операция | Что проверяется | Атомарный результат |
| --- | --- | --- |
| Создание | Новый ID и согласованный полный набор | Обе ревизии равны 1. |
| Редактирование метаданных | `expected_revision` | Config Revision увеличивается, credential-область сохраняется. |
| Принятие проверенной ручной замены / reconnect | `expected_revision` | Config Revision и актуальная CredentialRevision увеличиваются; заменяется весь набор полномочий. |
| Автоматический refresh | `expected_credential_revision` | Меняются только весь credential-набор, его ревизия, время и WriteID. |
| Удаление аккаунта | `expected_revision` | CAS DELETE, запрещённый при зависимых ChatSource. |

Reconnect читает актуальную credential revision внутри Write. Поэтому нормальный refresh старого доступа во время проверки новой авторизации сам по себе не отменяет замену. Поздний refresh после успешного reconnect отклоняется. Две ручные замены с одной config revision конкурируют CAS.

Refresh сохраняет идентичность доступа: Twitch ClientID/UserID, VK ClientID/ClientSecret и YouTube APIKey не меняются этой операцией. Попытка их смены возвращает конфликт без записи; проверенная ручная замена выполняется через reconnect и пользовательский CAS. Иначе смена аккаунта могла бы обойти изменение config revision и проверку DELETE. Токены, сроки и допустимые scopes обновляются полным согласованным набором.

Переименование во время длительной авторизации вправе завершить replacement конфликтом; проверка площадкой не обещает безусловный commit. Прежние настройки и пригодный доступ остаются. Успешный reconnect изменяет config revision, поэтому DELETE с прежней пользовательской ревизией не удаляет заново подключённый аккаунт. Переполнение любого изменяемого uint64 отклоняет операцию целиком.

Ввод новых реквизитов не отзывает прежний доступ. Он используется до успешной проверки и сохранения замены. Отмена или ошибка до принятия результата не меняет действующие настройки. Это не обещает работоспособность ключа, отозванного самой площадкой.

### Неоднозначное сохранение

Сетевой обмен находится вне повторяемого Write. CredentialWriteID назначается до сохранения и остаётся тем же для попыток записи уже полученного результата. После ошибки, допускающей состоявшийся COMMIT, владелец до следующего credential-обмена перечитывает ID, версии и полный набор:

- Совпадение ожидаемых ID, версий и результата подтверждает commit.
- Подтверждённое прежнее состояние допускает повтор только сохранения того же проверенного результата.
- Иное состояние означает устаревший результат; недоступное чтение сохраняет неопределённость.

Сам ID без версий и результата не является доказательством. Прежний одноразовый Twitch refresh не обменивается повторно вслепую. Потеря несохранённого результата из RAM при падении процесса может потребовать новой авторизации; exactly-once между площадкой и SQLite не заявляется. Дополнительная таблица обменов не создаётся.

Отмена попытки подтверждается до принятия сохранения. После успешно принятого COMMIT возвращается завершённый результат; отмена не откатывает уже зафиксированные полномочия.

## Транзакции, связи и формат SQLite

ChatRepository входит в общий Repositories/UoW. Списки имеют типизированные фильтры, limit от 1 до 500 и возрастающую границу `(created_at,id)`. Источник можно выбирать по Destination, Account, Provider и через родителя по Stream без дублирования StreamID в его записи. Полные списки не материализуются без ограничения.

Родители и совпадение Provider проверяются в короткой Write-транзакции. БД независимо защищает связи:

- `chat_accounts` имеет `UNIQUE(id,provider)` и закрытый CHECK провайдера.
- `chat_sources.destination_id` обязателен и ссылается на Destination с `ON DELETE CASCADE`.
- Обязательная составная ссылка `(account_id,provider)` ведёт на Account с `ON DELETE RESTRICT`.
- Enabled хранится как 0/1. Ревизии сохраняют точный uint64 в двадцатизначном TEXT/BINARY, время — UTC с точностью до микросекунд. Конфигурация и полномочия имеют отдельные оболочки MetadataVersion=1.

Существующий CAS DELETE Destination сохраняется. Разрешённое удаление атомарно удаляет связанные ChatSource. Удержание Output, неверная ревизия или другой отказ сохраняют весь граф. Используемый ChatAccount удалить нельзя. Исторические Session/Output-снимки самостоятельны, не получают FK на текущие chat-конфигурации и не переписываются.

Единственный начальный SQL `migrations/sqlite/00001_initial.sql` остаётся миграцией Goose 1 и создаёт формат 5. Preflight проверяет полный текущий набор таблиц, маркер 5 и Goose 0/1 до потенциально пишущих вызовов Goose и Recover. Прежний формат, неизвестная/неполная схема и остаток только с Goose 0 отклоняются без преобразования схемы, доменных данных и истории миграций. Автоматического пересоздания и следующей миграции нет. Весь Open может создавать lock/WAL/SHM-файлы даже при отказе формату.

GORM не управляет схемой; используется рабочий Goose runner и общий CGO sql.DB. Проверки сохранности выполняются на временной файловой SQLite. Для прежнего формата применяется зафиксированный baseline-артефакт, а не новая схема с изменённым маркером. Общие ограничения описаны в [контракте хранения](domain-storage-contracts.md#sqlite-и-миграции).

## Контракты жизненного цикла и ленты

Manager потребляет внутренние RuntimeAnchor/RuntimeEvents и сохранённые Session/Output без HTTP-loopback. Gap/Reset требует повторной согласованной сверки. При первом принятом PUBLISHING точный наблюдатель выхода сохраняет свидетельство в RAM. RuntimeAnchor возвращает его даже после вытеснения события из журнала. CONNECTING и RETRYING до первой публикации оставляют чат в ожидании. После первой публикации чтение сохраняется при повторных CONNECTING и RETRYING того же выхода, работе с fallback, ручной паузе и переподключении OBS. Stop/detach, терминальное состояние или отзыв точного выполнения прекращают соответствующие привязки и reconnect.

Лента принадлежит сохранённой RUNNING Session и её точному действующему наблюдателю. При завершении, отзыве или смене этого наблюдателя прежняя эпоха закрывается. Остановка последнего подходящего выхода прекращает чтение, сохраняя ленту действующей Session. Внутренний сигнал подтверждённого RUNNING позволяет открыть ленту даже у Session без выходов и подключения OBS.

Worker имеет непрозрачную оперативную идентичность Session/Incarnation/поколения. Она не равна конфигурационной ревизии или ревизии полномочий. Привязки Source/Execution отделены от общего обработчика: отзыв одного участника не отзывает соседей. Подтверждённое изменение канала/аккаунта применяется сразу через единый протокол Manager; ненадёжное уведомление после записи не заменяет проверку актуальности обратных вызовов. Переименование и обычный refresh сами по себе не означают перезапуск чтения; ручной reconnect имеет отдельный результат применения.

Adapter передаёт provider, фактическую идентичность беседы, provider-message ID, автора, текст/parts/badges и платформенное время. Manager/Hub после проверки callback назначают Session/Source, server received_at и точный uint64-порядок. Время платформы не задаёт межплатформенную сортировку. Для YouTube фактический chat ID — liveChatID, Twitch — broadcasterID, VK — channelID.

Дедупликация использует Session/provider/chat/message ID в пределах сохранённого окна. Если конфигурационные записи разделяют один reader, `chat_source_id` выбирается как минимальный ID среди текущих допущенных участников. Атрибуция первого принятого сообщения сохраняется; смена членства историю не переписывает. Это техническое правило повторной доставки, а не поддержка двух публикаций в один платформенный канал.

Когда действующая лента удаляет оперативный статус источника, `resync_required` получает собственную позицию в журнале. Клиент берёт новый снимок конфигураций и статусов, сохранившаяся история сообщений остаётся доступной.

YouTube-выбор хранится только в RAM текущего запуска: точные Session/Source, Source revision, поколение обнаружения и video из актуального набора. Устаревший выбор отклоняется. Следующий запуск обнаруживает эфир заново: один результат выбирается автоматически, несколько требуют явного выбора.

## Целевой HTTP-контракт

Маршруты чатов регистрируются при последующей интеграции API под `/api/v1`; наличие этого раздела не означает их текущую доступность.

| Операция | Вход и результат |
| --- | --- |
| `GET/POST /destinations/{destinationId}/chat-sources` | Ограниченный список или создание Source с обязательными provider/account/channel/options и явным enabled; необязательное имя по умолчанию пусто. Создание возвращает сохранённый Source. |
| `GET/PATCH/DELETE /chat-sources/{id}` | Чтение либо изменение/удаление по `expected_revision`. Родитель из тела не переносится. PATCH сохраняет отсутствующие поля; false и пустое допустимое значение применяются явно, null не заменяет обязательное значение. |
| `GET /chat/accounts` и `GET/PATCH/DELETE /chat/accounts/{id}` | Санитизированные метаданные, ограниченный список, переименование или удаление по пользовательской `expected_revision`. PATCH не принимает поля полномочий и не меняет Provider. |
| `POST /chat/accounts/connect` | Provider и начальные реквизиты: API Key для YouTube, Client ID публичного приложения для Twitch, Client ID/Secret для VK Видео Live. Для замены обязательны существующий account_id и expected_revision. Результат — публичная RAM-попытка подключения с идентификатором и состоянием. |
| `GET/DELETE /chat/accounts/authorizations/{attemptId}` | Публичное состояние попытки или отмена. Twitch дополнительно показывает user_code, verification_uri и срок подтверждения. Токены и client secret не возвращаются. |
| `POST /chat-sources/{id}/broadcast-selection` | session_id, ожидаемая ревизия Source, поколение обнаружения и video_id из текущего набора. Успех принимает выбор для этого запуска; устаревшее доказательство даёт конфликт. |
| `GET /chat/streams/{streamId}/snapshot` | Согласованные Session, сообщения, состояния и непрозрачный cursor. Существующий Stream без активной Session получает успешные `session:null`, `messages:[]`; настройки и состояния доступны отдельно. |
| `GET /chat/streams/{streamId}/events` | SSE с cursor/Last-Event-ID, проверкой их совпадения и событиями chat.message, chat.source_status, chat.gap, resync_required, chat.session_closed. |

Create/PATCH конфигурации возвращают сохранённую публичную проекцию, DELETE — пустой успешный ответ. Конкретные DTO/OpenAPI проверяются при регистрации маршрутов. Ошибки следуют существующей классификации: неверные параметры — 422, отсутствующий объект — 404, CAS/устаревший выбор/используемый аккаунт — 409, недоступный ресурс — 503; слишком большое входное тело — 413. Problem Details и статусы содержат безопасные коды без полномочий и произвольной диагностики площадки.

Подключение возвращает `202` и ссылку на RAM-попытку; это не долговечная CommandReceipt медиакоманды. После рестарта незавершённая попытка отсутствует и запускается заново. Сохранённый Account появляется или меняется только после успешной проверки и commit. Для существующего аккаунта Provider сохраняется, незавершённая попытка не создаёт вторую запись и не выключает прежний доступ.

После успешного применения изменения чтения прежние callbacks отозваны; установление нового платформенного соединения асинхронно и отражается отдельным состоянием. Отсутствие соединения не превращается в служебную запись ленты. SSE способен ждать появления Session и сообщить resync_required; открытая страница после snapshot получает сообщения фактически публикуемого эфира. Лента до трансляции пуста, без текста «Ожидание». Закрытие страницы не управляет чтением площадок.

Числа REST/SSE передаются числами с точным применимым 64-битным диапазоном; ID, даты и cursor — строки. Cursor непрозрачен и не преобразуется браузером в число. Полномочия отсутствуют в публичных ответах, HTML/Overlay URL, SSE и причинах ошибок. Статусы находятся отдельно от сообщений ленты. Управление наследует существующий локальный доступ без авторизации.

## Конечные бюджеты

Значения — инженерные стартовые пределы для последующей проверки, не измеренная производительность. Типы/defaults/валидация не означают, что ещё не подключённый runtime уже потребляет эти бюджеты.

| Ресурс | Начальный предел |
| --- | --- |
| Удерживаемые Sessions / активные Sources | 4 / 64 всего, 32 Source на Session |
| Обработчики чтения / физические соединения с площадками | 32 / 64 с учётом перехода между соединениями |
| Владельцы полномочий аккаунтов / одновременные HTTP-запросы | 32 / 16 |
| RAM-авторизации | 8 всего, одна replacement на Account |
| Привязки источников / их логический объём в реестре | 256 / 8 MiB |
| История Session | 1000 сообщений / 16 MiB |
| Полный конечный JSON сообщения | 64 KiB |
| Входная очередь Session | 256 записей / 1 MiB |
| Журнал воспроизведения Session | 2048 событий / 16 MiB |
| Дедупликация Session | 8192 ключа / 2 MiB / TTL 15 минут |
| SSE-клиенты | 32 всего, 8 на Stream |
| Очередь SSE-клиента | 256 событий / 1 MiB |
| Полный кадр SSE / cursor | 128 KiB / 4 KiB |
| Ответ HTTP / сообщение WS или gRPC от площадки | 1 MiB / 1 MiB |
| Входное тело REST / полный набор полномочий | 1 MiB / 64 KiB |

| DOM Overlay / Dashboard | 50 / 200 сообщений |

JSON-бюджет сообщения считается после экранирования и добавления всех полей Hub. Структурная доменная проверка предварительно ограничивает вход; окончательный размер закодированного сообщения проверяется при его формировании. Превышение учитывается как потеря. Каждое `chat.message` получает отдельный SSE-кадр: пакет из 100 сообщений не является одним большим массивом в одном кадре. Snapshot имеет отдельный предел; ограничение ответа площадки в 1 MiB к нему не применяется. Срок конечного HTTP-запроса не ограничивает весь срок потокового соединения: им владеют контекст обработчика, протокольный keepalive и отмена.

История и журнал событий учитывают закодированные байты. Для остальных удерживаемых элементов логический вес равен 256 байтам плюс строки и байтовые срезы, для каждого вложенного part/badge добавляются 64 байта и его строки. Все сложения проверяют переполнение; предел количества дополнительно ограничивает накладные структуры. Это не точный бюджет heap/RSS/TLS или ресурсов ОС.

Приём нового владельца не вытесняет действующего, а закрывающиеся ресурсы занимают слот до физического завершения. Переполнение входа и превышение размера записи дают явный учёт потери; медленный SSE получает resync/закрытие. Обычное вытеснение старой истории не означает потери своевременному подписчику; cursor вне журнала воспроизведения требует snapshot. Исчерпание окна попыток оставляет отменяемое ожидание RETRYING. Интервал площадки, Retry-After и более строгая проверенная квота имеют приоритет.

## Зависимости и внешние ограничения

Домен и хранение используют закреплённые Go `1.27.3`, GORM `1.31.2`, диалект SQLite `1.6.0`, CGO-драйвер `1.14.22` и Goose `3.27.0`. Адаптер YouTube использует gRPC `1.85.0` и protobuf `1.36.12`. Официальный исходник и воспроизводимая сборка дескриптора описаны в [контракте протокола YouTube](../internal/chat/youtube/README.md).

Один экземпляр адаптера YouTube обслуживает все ключи одного Google Cloud Project на сервере. Он ограничивает обнаружение 100 вызовами `search.list` и 10 000 вызовами `videos.list` для обнаружения в сутки по тихоокеанскому времени. При исчерпании квоты Manager ждёт вне сетевого слота. Учёт в памяти сбрасывается при перезапуске процесса, а Google применяет суточный лимит ко всем вызовам проекта. Каждая страница поиска учитывается отдельно. Неоконченный проход не даёт набора для выбора. Обнаруженное видео без чата проверяется через `videos.list`. После явного выбора видео перечитывается перед подключением к чату.

Серверная операция подключения YouTube проверяет ключ отдельно от обнаружения эфира. После принятия проверенной замены Manager отзывает обратные вызовы прежнего чтения. Во время повторных попыток одного читателя Manager удерживает ограниченный `nextPageToken` от обработанного пакета. Отзыв читателя освобождает позицию.

### Подключение и чтение Twitch

Серверный `ConnectTwitch` получает Client ID публичного приложения и возвращает параметры подтверждения Device Code. Manager опрашивает Twitch в пределах времени попытки. Пока идёт подтверждение, прежнее чтение продолжает работать. После подтверждения и проверки пользователя доступ сохраняется прежними операциями создания или замены аккаунта. `Authorization` возвращает публичные поля, а `CancelAuthorization` прекращает попытку до допуска к записи. Если исход записи установить не удалось, попытка возвращает `PENDING` и отдельную ошибку неопределённости. Параметры подтверждения при этом уже скрыты. [Device Code Grant](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#device-code-grant-flow)

`CredentialOwner` проверяет полномочия перед подпиской и по часовому вызову действующего читателя, включая тихий чат. Одноразовый refresh выполняется вне транзакции. Полная новая пара проверяется и сохраняется через CAS. Успешная ротация сохраняет подписку, а недействительные полномочия требуют повторной авторизации. [Требования Twitch к проверке токена](https://dev.twitch.tv/docs/authentication/validate-tokens/)

После первой публикации привязанного выхода читатель подписывается на один чат через EventSub `channel.chat.message` v1. Пустой `ChannelHint` выбирает канал авторизованного пользователя. `CONNECTED` появляется после подтверждения соответствующей подписки Helix. При управляемом переходе исходный сокет продолжает принимать сообщения до подтверждения нового. После полной потери подтверждённой подписки Hub получает `chat.gap`, а Manager запускает новое подключение и подписку. `github.com/coder/websocket v1.8.15` ограничивает размер полного сообщения, включая фрагменты. Основной и временный сокеты учитываются в общем бюджете `Connections` до закрытия. [EventSub WebSocket](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/)

### Подключение и чтение VK Видео Live

Серверная операция `ConnectVKVideoLive` принимает Client ID и Client Secret приложения DevAPI. Сохранению предшествуют выпуск `client_credentials` и проверка типа `application` и срока через `/v1/token`. Подтверждённый app-токен и его срок сохраняются вместе с реквизитами. При замене аккаунта проверка идёт при действующем прежнем чтении. Подтверждённая запись применяет новую ревизию и отзывает старые привязки. [Авторизация VK](https://dev.live.vkvideo.ru/docs/main/authorization) · [Проверка токена](https://dev.live.vkvideo.ru/docs/method/token)

`CredentialOwner` переиспользует app-токен до истечения и условно обновляет отвергнутый набор после HTTP 401 от поиска канала или выдачи WebSocket-токена. Владелец сверяет ревизию и квитанцию отвергнутого набора. Конкурентный запрос может получить уже сохранённый более свежий набор. Обычный перевыпуск увеличивает только ревизию полномочий, а повтор исходного запроса расходует общий HTTP-бюджет после освобождения предыдущего слота. Если восстановление завершилось временным отказом, следующая плановая попытка учитывает самый строгий полученный `Retry-After`. [Ошибки VK DevAPI](https://dev.live.vkvideo.ru/docs/main/errors)

После фактической публикации выхода адаптер ищет канал по slug через `/v1/channel`. Читатели разделяют подписку по точной Session, аккаунту и числовому ID канала. На каждое соединение используется свежий токен `/v1/websocket/token`. `CONNECTED` появляется после подтверждения `subscribe` на `channel-chat:<id>`. После потери подтверждённой подписки `chat.gap` обозначает возможный пробел, а Manager соблюдает общий бюджет повторов. Доставку реального сообщения в выбранный канал проверяют на активной трансляции. [Канал VK](https://dev.live.vkvideo.ru/docs/method/channel) · [Токен WebSocket](https://dev.live.vkvideo.ru/docs/method/websocket) · [Протокол Centrifugo v4](https://centrifugal.dev/docs/4/transports/client_protocol)

### Совместимость хранилища и внешних служб

GORM Updates с map сохраняет явные false/нули; Save/upsert не заменяет CAS ([официальный контракт](https://gorm.io/docs/update.html)). Составные FK требуют подходящего UNIQUE родителя, а CASCADE/RESTRICT действуют в операции удаления ([SQLite](https://www.sqlite.org/foreignkeys.html)). Goose использует встроенный FS и тот же sql.DB ([закреплённый исходник 3.27.0](https://github.com/pressly/goose/blob/v3.27.0/provider.go)).

YouTube gRPC `FAILED_PRECONDITION` не различает disabled/ended по одному коду. До отдельного подтверждения допустима общая безопасная причина недоступности. Фактические квоты и совместимость площадок проверяются в целевой среде. [YouTube](https://developers.google.com/youtube/data/live/reference/rest/v3/liveChatMessages/streamList)
