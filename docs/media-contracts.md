# Общие контракты медиатракта

Документ задаёт общие значения и инварианты для рабочих пакетов Go backend и выбранные границы конкретных адаптеров. Очереди, часы, ingest, UDS, FFmpeg, Switcher и Publishers проверяются вместе с соответствующими компонентами; описание контракта не является отчётом о приёмке реализации.

## Границы и зависимости

`internal/core` содержит форматы, профиль группы и `WatchdogPolicy`, `internal/media` — пакет, конфигурацию дорожки, единицу времени и ограничения очередей. В `media` сохранён совместимый alias `WatchdogPolicy`. Зависимость направлена из `media` в `core`; сами эти значения используют только стандартную библиотеку Go. Зависимости хранения подключены отдельно, выбранный SDK не меняется.

| Область | Выбранное семейство и требуемая возможность | Этап проверки и подключения |
| --- | --- | --- |
| Приём и отправка | `github.com/bluenviron/gortmplib v1.0.1`: собственный raw-адаптер AV1/AAC; необходимые codec/box типы — `mediacommon/v2 v2.9.3`, `go-mp4 v1.7.1`. | T03: ingest/metadata/timestamps/Override и ранние ограничения; forwarding RTMP/RTMPS — T05. |
| Хранение | GORM `v1.31.2`, SQLite dialect `v1.6.0`/CGO driver `v1.14.22`, Goose `v3.27.0`: CRUD, транзакции и единственный runner SQL-миграций. | T02: общий CGO pool, фактический SQLite, WAL/FK и временная файловая БД. |
| Управляющий API | `github.com/danielgtaylor/huma/v2`, `github.com/go-chi/chi/v5`: типизированные операции, middleware, OpenAPI и HTTP/SSE. | T08: версии и реальные границы HTTP. |
| Локальный кэш | `github.com/maypok86/otter/v2`: ограниченный восстанавливаемый кэш и остановка фоновых задач. | T09: только после выбора полезного чтения и проверки API конкретной версии. |
| Конфигурация и контейнер | Streaming fMP4 с ограниченным Go mux/demux через UDS; YAML-библиотека ещё не выбрана. | T03: реальные metadata/timestamps/UDS; T09: конфигурация и политика новых зависимостей. |

Сохраняемые представления, ORM-модели, SQL-схема, точная сериализация и каноническая идентичность `FallbackVariant` описаны в [контрактах домена и хранения](domain-storage-contracts.md). Сетевые представления проверяются вместе с адаптерами. Полный профиль используется при хранении и подготовке fallback; совпадение настроек не заменяет проверку существующего файла.

[SessionManager и processowner](session-manager-contracts.md) связывают эти компоненты с командами, первоначальной готовностью, отдельным helper и проверяемой очисткой. Независимая локальная приёмка этой интеграции завершена в T06; [результат и ограничения](session-manager-contracts.md#локальная-приёмка) относятся к её собственному снимку. Приведённые ниже результаты прежних снимков сохраняют свою исходную область.

В редакции 9 новая загрузка безусловно заменяет содержимое явно выбранной заглушки и требует новой подготовки, даже если её байты совпадают с прежними. Дедупликации загрузок по содержимому нет. Общий файл допускается для совпадающих полных профилей внутри одной подготовленной версии. Замена публикуется после успешной подготовки и проверки, при ошибке прежняя рабочая версия сохраняется. Генерация и rebuild запрещены во время эфира, включая ручную паузу; воспроизведение уже готового fallback по UDS продолжает работать. Реализация и проверка этих требований относятся к T04.

## Форматы и полный профиль

В `core` используются следующие типы значений:

| Тип | Поля |
| --- | --- |
| `Codec` | Строковые значения `CodecAV1 = "av1"`, `CodecH264 = "h264"`, `CodecAAC = "aac"`. |
| `GroupMode` | `ModeCopy = "copy"`, `ModeTranscode = "transcode"`. |
| `FrameRate` | `Numerator`, `Denominator`: `uint32`, кадров в секунду. |
| `ColorInfo` | `Range`, `Primaries`, `Transfer`, `Matrix`: `string`. |
| `VideoFormat` | `Codec Codec`; `Width`, `Height uint32`; `FrameRate FrameRate`; `CodecProfile`, `Level`, `Tier`, `PixelFormat string`; `BitDepth uint8`; `Color ColorInfo`. |
| `AudioFormat` | `Codec Codec`; `CodecProfile string`; `SampleRateHz uint32`; `Channels uint16`; `ChannelLayout string`. |
| `MediaFormat` | `Video VideoFormat`, `Audio AudioFormat`. |
| `VideoEncoding` | `TargetBitrateBPS`, `MaxBitrateBPS`, `BufferBits uint64`; `GOPFrames`, `MaxBFrames uint32`; `ClosedGOP bool`. |
| `AudioEncoding` | `BitrateBPS uint64`. |
| `GroupProfile` | `Mode GroupMode`; `Format MediaFormat`; `VideoEncoding VideoEncoding`; `AudioEncoding AudioEncoding`; `Encoding EncodingSettings`. |
| `EncodingSettings` | Версия, выбор кодировщиков, RC, разрешение масштабирования, применимые NVENC/SVT-настройки и нормализованные строки custom. Сравнимое значение без удерживаемых ссылочных коллекций. |

`FrameRate`, `ColorInfo`, `VideoFormat`, `AudioFormat`, `MediaFormat`, `VideoEncoding`, `AudioEncoding` и `GroupProfile` имеют `Validate() error`. Части дроби, размеры, глубина цвета, sample rate, число каналов, целевой битрейт и GOP положительны. В прежнем профиле buffer/max также положительны и `TargetBitrateBPS <= MaxBitrateBPS`. В версии 2 ограничения зависят от encoder/RC: AV1 VBR явно требует нулевые max/buffer, обозначающие отсутствие неподдерживаемого ограничения. Нулевой `MaxBFrames` допустим. Видео ограничено AV1/H.264, аудио — AAC; текущий `MediaFormat` всегда содержит обе дорожки. Режим группы должен быть известен.

Профиль кодека, pixel format, цвет и channel layout задаются непустыми строками; строка из одних пробелов недопустима. `Level` и `Tier` могут быть пустыми, если значение не заявлено или неприменимо. Структурная валидация `MediaFormat` не подтверждает поддержку энкодером. Новый профиль версии 2 дополнительно проверяет поддерживаемое подмножество encoder/RC/форматов; его defaults материализуются при запросе, а не при чтении или исполнении. Прежняя допустимость сохранённых профилей не ужесточается.

`FrameRate.Equal`, `MediaFormat.Equal` и `GroupProfile.Equal` сравнивают корректные значения. Если один аргумент не проходит валидацию, результат — `false`. Дроби сравниваются математически: `60/1` равно `120/2`; целочисленное сравнение не должно переполняться. Полное равенство профиля учитывает каждое поле, включая режим, настройки кодирования, необязательные level/tier и структуру GOP. Строки сравниваются точно; нормализация наблюдаемых описаний принадлежит адаптеру.

`copy` имеет явный выходной профиль до первого OBS. Его encoding-поля задают подготовку fallback и параметры группы; они не предписывают перекодирование LIVE. Полное равенство профиля и пригодность источника для переключения — разные контракты. `core.CompatibleFormat` сравнивает фактические форматы, а общий пакет `media/codec` проверяет headers и access units; одного совпадения метаданных недостаточно.

В версии 2 владелец заранее вручную задаёт ожидаемые выходные настройки OBS, включая CBR/VBR и битрейты. AV1-заглушка использует тот же применимый режим; низкоуровневые NVENC-параметры OBS не переносятся на серверный `libsvtav1`. Сервер copy LIVE не меняет. Полная таблица [encoder options, native-семантики и custom](api-contracts.md#полный-профиль-кодирования) задаёт публичное подмножество. Неподдержанное сочетание и конфликт custom с обычным полем отклоняются; произвольная команда FFmpeg не принимается.

Один общий compiler настроек кодирования обслуживает LIVE и подготовку. Прежние профили проходят семантический адаптер: LIVE H.264 сохраняет явный VBR, H.264 fallback — прежнее отсутствие `-rc` и advanced overrides, AV1 fallback — прежний CBR-рецепт. Две копии старых построителей не сохраняются. У версии 2 RC и применимые advanced/audio/custom-поля берутся из полного профиля. Эти поля участвуют в идентичности варианта, даже если кодировщик выбирает внутренние параметры автоматически.

В целевом `transcode` разрешение и FPS выхода задаёт полный профиль группы; входной OBS остаётся 1440p60. AV1 1440p60 `copy`, H.264 1440p60 и H.264 1080p60 — три независимых профиля. Два назначения одной H.264-группы используют один результат кодирования; разные разрешения, FPS или остальные поля полного профиля не объединяются в один выход. Для них нужны отдельные fallback-варианты.

`BuildNVIDIACommand` использует единственную выходную сетку: `fps=fps=N/D:round=near:eof_action=round`, затем `scale_cuda` с размерами профиля. У версии 2 при `rescale_output=false` масштабирование пропускается и требуется совпадение входных и выходных размеров. Подготовка asset всегда приводит его к целевым размерам. Дробь сокращается только для командной арифметики, исходный профиль не меняется. Выходной `-r` не добавляется; `-fps_mode:v passthrough` передаёт уже преобразованные кадры, `-enc_time_base:v filter` использует сетку фильтра. Преобразование FPS применяется и при одинаковых заявленных частотах. Цвет/битность SDR и остальные ограничения порта сохраняются, автоматического программного кодировщика в приложении нет. Семантика сверена с [фильтром fps](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavfilter/vf_fps.c) и [CLI FFmpeg 7.1.5](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/doc/ffmpeg.texi).

Для сокращённого `N/D` один выходной tick равен `D/N` секунды. Первая video PTS и EOF округляются к общей сетке до ближайшего значения, при половине — от нуля; последующие presentation ticks идут с шагом один. `start_time` не задаётся, дорожки раздельно не обнуляются. Кодирование с B-кадрами создаёт новые DTS, поэтому сравнение с входными DTS не является оракулом преобразования. Проверяются выходные частота/длительности, PTS/DTS, число кадров и A/V по независимо заданным ожиданиям; сохранение меток транспорта проверяется отдельно.

`NVIDIAConfig` требует фактические `VideoTimeBase` и `AudioTimeBase`. Выходной video track timescale равен `N`; movie timescale — точный LCM сокращённых знаменателей обеих входных шкал, `N` и обеих частот AAC. Непредставимые значения и превышение `INT_MAX` отклоняются до запуска. Поскольку `fps` в FFmpeg 7.1.5 вычисляет выражение через binary64 и `av_d2q`, одного ограничения частей дроби недостаточно. Предварительная проверка требует `2*M*abs(A*D-N*B)<B` точной целочисленной арифметикой, где `M=INT_MAX`, а `A/B` воспроизводит начальный пересчёт `av_d2q`. Неоднозначная дробь отклоняется, вместо молчаливой подмены FPS; произвольный предел частоты не вводится. Проверенная граница относится к обычной IEEE binary64 арифметике FFmpeg 7.1.5.

AAC перекодируется по профилю. [Native AAC FFmpeg 7.1.5](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/aacenc.c) использует `initial_padding=1024` и AU по 1024 сэмпла; начальная задержка и хвост учитываются отдельно от округления video до половины выходного кадра. Короткие интеграции рабочих Go/UDS/Supervisor/fMP4 проверяют 1440p → 1080p, 60 → 30, рациональную частоту, ненулевые/отрицательные начала и настоящую обработку AAC. Отдельный локальный VideoToolbox-сценарий использует `-allow_sw 0` и проверяет ту же сетку. Он не подтверждает NVDEC/NVENC, которые остаются целевой аппаратной приёмкой.

Ошибки валидации `core` распознаются через `errors.Is`: некорректная дробь/описание формата — `ErrInvalidFormat`, настройки кодирования/группы — `ErrInvalidProfile`. Ошибка содержит контекст поля; проверка не требует сравнения полного текста.

## Дорожка, конфигурация и пакет

В `media` определены:

| Тип или операция | Контракт |
| --- | --- |
| `Track` | `TrackVideo = "video"`, `TrackAudio = "audio"`. |
| `TimeBase` | `Numerator`, `Denominator uint32`: секунд на tick; обе части положительны. `Validate() error` и математическое `Equal(TimeBase) bool`, возвращающее `false` для некорректных значений. |
| `CodecConfigInfo` | `Track Track`; `SourceEpoch`, `Revision uint64`; `TimeBase TimeBase`; `Video core.VideoFormat`; `Audio core.AudioFormat`. Активен только формат выбранной дорожки, второй должен быть нулевым. |
| `NewCodecConfig(info CodecConfigInfo, headers []byte) (CodecConfig, error)` | Проверяет описание и непустые headers, копирует байты. Epoch и revision положительны. Кодек выводится из активного формата. |
| `CodecConfig` | Закрытые данные; `Info()` возвращает описание по значению, `Headers()` — копию, `StoredBytes() uint64` — длину headers. `Validate() error` отклоняет нулевое/некорректное значение. |
| `PacketInfo` | `PTS`, `DTS`, `DurationTicks int64`; `Keyframe bool`. |
| `NewPacket(info PacketInfo, config CodecConfig, payload []byte) (Packet, error)` | Принимает корректную неизменяемую config, проверяет описание и непустой payload, копирует payload. |
| `Packet` | `Info()`, `Config()` возвращают значения; `Payload()` — копию. `StoredBytes() uint64` учитывает payload и headers. `Validate() error` отклоняет нулевое/некорректное значение. |

Пакет представляет один сжатый access unit. Его дорожка, формат, epoch, revision и единица времени однозначно определяются config. Отрицательные PTS/DTS допустимы; условия `PTS >= DTS` нет. `DurationTicks >= 0`, ноль означает неизвестную длительность. Аудиопакет не помечается `Keyframe`. Для видео этот признак означает заявленную адаптером пригодность независимого старта; конструктор не проверяет битовый поток.

Нулевые `Packet` и `CodecConfig` не готовы к обработке; их getters безопасны и возвращают нулевые значения/пустые данные. `Validate` и конструкторы возвращают обёрнутые `ErrInvalidPacket`, `ErrInvalidConfig` или `ErrInvalidTimeBase` соответственно. Некорректная config в `NewPacket` распознаётся как `ErrInvalidPacket`; проверка самой config — как `ErrInvalidConfig`. Ошибки вложенных полей могут сохраняться в цепочке, но корневая категория обязательна.

Описание формата связывается с headers в одном неизменяемом значении. Соответствие описания содержимому headers, правильность access unit, настоящая random-access точка и декодируемость проверяются адаптером и интеграцией. Синтетические bytes и успешный конструктор этого не подтверждают.

## Владение памятью и учёт размеров

После конструирования Packet и CodecConfig неизменяемы; их можно передавать по значению и читать совместно. Изменение исходных slices либо результата `Payload()`/`Headers()` не меняет объект или уже переданные копии. Конфигурацию можно разделять между пакетами; байтовые массивы наружу не выдаются. Пулы, заимствованные буферы, refcount и `Release` не вводятся.

Это явная граница копирования: в Go копирование slice само по себе сохраняет общий backing array. Основание — [спецификация Go 1.27.3](https://github.com/golang/go/blob/go1.27.3/doc/go_spec.html#Representation_of_values); доступная локальная документация `bytes.Clone` подтверждает копирование байтов.

`StoredBytes` — логический вес сжатых данных: payload + headers, для одной config — только headers. Общая config консервативно учитывается в каждом пакете. Это не размер heap/RSS. Количество объектов ограничивается отдельно; адаптеры также ограничивают входное описание и отдельные хранилища metadata.

## Поколения источника и временная шкала

Идентичность feed задаётся владельцем входного слота вне Packet. LIVE и FALLBACK имеют независимые текущие состояния; epoch не сравниваются глобально между ними или между группами. Владелец feed назначает `SourceEpoch` при новой инкарнации источника, Override, перезапуске producer либо разрыве входной временной шкалы. Значения не переиспользуются и не переполняются с переходом к нулю.

Обе дорожки одного текущего экземпляра feed принадлежат одной epoch. `Revision` локальна для `(feed, epoch, track)` и меняется при изменении headers, наблюдаемого формата или TimeBase. Номера аудио- и видеоревизий могут различаться. Один ключ `(feed, epoch, track, revision)` всегда обозначает одну config. Владелец публикует согласованный снимок текущих A/V-конфигураций; новые данные принимаются только относительно этого снимка. Запоздалые пакеты прежней epoch или прежней текущей revision отбрасываются.

Внутри непрерывного сегмента дорожки DTS не убывает; PTS может менять порядок при перестановке кадров. Конструктор одного пакета не может проверить последовательность. Изменение единиц, сброс и переполнение внешних timestamps обрабатываются на границе адаптера. Обычная петля с непрерывными timestamps не требует новой epoch; обнаруженный сброс при петле требует новой границы непрерывности.

Выходной timeline строится отдельно от входных epoch. Переключение, Override и граница петли сохраняют согласованную A/V-шкалу и композиционное смещение `PTS − DTS`; аудио начинается с согласованного полного access unit. Рескейлинг и offsets реализуются в рабочих адаптерах/Switcher: они обязаны явно определить округление и проверять переполнение до арифметической операции. Signed overflow в Go не вызывает panic, поэтому одного типа `int64` недостаточно для такой проверки.

PTS/DTS не являются временем получения пакета, wall clock либо временем сохраняемого Event. Watchdog использует локальные монотонные часы и прогресс валидных данных обеих дорожек.

## Контейнер и конкретная граница FFmpeg

Для T03 выбран fMP4. NUT не передаёт независимый DTS каждого пакета: локальный контрпример FFmpeg 7.1.5 сохранил payload, но изменил `PTS−DTS` с `12/30` до `2/30` секунды. Успешное декодирование не доказывает сохранение времени.

Go fMP4 передаёт codec headers как полный `av1C`, `avcC` или AAC ASC. Общий обратимый сдвиг origin одинаков для обеих меток обеих дорожек; самостоятельное обнуление каждой дорожки запрещено. Time bases, movie timescale, durations, offsets и диапазоны проверяются до сериализации. Точное представление не заменяется молчаливым округлением. Непредставимое значение даёт явную ошибку.

H.264 использует независимые PTS/DTS и signed composition offsets в поддержанном диапазоне. AV1 ISOBMFF v1.2 определяет sample как temporal unit и запрещает composition-offset fields для AV1. Поэтому AV1 mux не записывает такие поля даже с нулевым значением, а AV1 Packet с различающимися PTS/DTS отклоняет как неподдержанный этой codec binding. Это не сужает общий Packet или Router.

В Enhanced RTMP AV1 имеется единственная wire-метка TU без отдельного composition offset. Контракт входного адаптера представляет её точно в обоих полях Packet как TU transport/presentation schedule, сохраняет порядок TU и проверяет неубывание; wrap/reset получает явную границу либо ошибку. Восстановление отсутствующего исходного encoder DTS не обещается. Hidden frames внутри TU сами по себе не запрещены; single-layer Main SDR и фактическая random-access пригодность проверяются по bitstream. Конкретная версия OBS/encoder подтверждается отдельно в T11.

Проверенный output profile FFmpeg 7.1.5: `delay_moov+default_base_moof+frag_every_frame`, `-min_frag_duration 1`, `-use_editlist 1`, точный общий `-movie_timescale`, `-avoid_negative_ts disabled`; положение `-copyts` и `-fps_mode` определяется командой. Минимальная длительность исключает обнаруженный flush пустого трека, портивший AAC DTS. Значение movie timescale `48000` относится к проверенному 30 FPS/48 kHz fixture, а не ко всем источникам. `empty_moov` и `negative_cts_offsets` не являются универсальными defaults: в проверках они меняли origins/композиционные смещения.

MP4-вход FFmpeg задаётся как `-f mp4 -fflags +ignidx -flags2:a +skip_manual -i async:unix:<path>`; выход остаётся `unix:<path>`. Физический транспорт в обоих направлениях — UDS. В FFmpeg 7.1.5 прямой Unix-вход ошибочно отмечен как seekable: кроме полного прохода до EOF, MOV выполняет обратные чтения заголовков, которые при дробном recv могут потерять исходный буфер. `ignidx` ограничивает предварительное сканирование текущим `mdat`, а `async` сохраняет конечное окно для чтения назад. В проверенной версии это фиксированный FIFO 8 MiB с history до 4 MiB и одним дополнительным потоком FFmpeg; CLI-размеры не настраиваются. Стоимость учитывается на каждый worker, завершение FFmpeg освобождает поток, FIFO и внутренний Unix-сокет. Рабочий FFmpeg должен включать протокол `async`.

Для транспорта полных AAC AU из Go общий обратимый origin не означает, что первые сэмплы нужно отбросить. Однако [MOV FFmpeg 7.1.5](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavformat/mov.c) при пустом `stts` воспринимает положительный `elst.media_time` как AAC `skip_samples`, хотя временные метки отдельно корректирует правильно. Входной аудиодекодер с [настройкой skip_manual](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/decode.c) сохраняет все переданные сэмплы и их знаковые метки, предотвращая потерю короткой дорожки при ненулевом транспортном сдвиге. Он не заменяет обработку начальной задержки нового AAC encoder. Контрольное декодирование полных AU со знаковыми метками также использует явный `skip_manual`; обычное воспроизведение MP4 может намеренно обрезать начало до нуля. Эти результаты имеют разное назначение; пакетные и A/V-ожидания остаются точными.

Проверка через настоящие сокеты с чтениями по 5 и записями по 7 bytes покрывает AV1/AAC → H.264/AAC и H.264/AAC copy, положительные и отрицательные origins; временные метки, extradata и декодируемость сравниваются независимо. Один успешный запуск либо успех через pipe не заменяют полную приёмку сокетной границы.

Конкретный FFmpeg CLI-порт явно отклоняет `PTS<DTS`, недопустимые равные DTS и непредставимые значения до сериализации нарушающего пакета. Общий signed Packet/Router и Go fMP4 сохраняют более широкий контракт. Отрицательные origins и обычные H.264 B-кадры остаются поддержанными. Принятая портом шкала сохраняет обе метки; guessed DTS недопустим. Exit 0 и `-xerror` не заменяют сравнение самих временных меток, поскольку FFmpeg способен переписать DTS лишь с предупреждением.

Framing UDS проверяется дробными чтениями/записями, ограничениями box/sample/extradata до allocation и разрывами соединения. Codec description сверяется с headers/sample entry; неизвестный FPS/цвет не подставляется из профиля группы. Реальная CPU-интеграция проверяет отдельно рациональные PTS/DTS, A/V origins, extradata и декодируемость.

Первичные источники: [FFmpeg n7.1.5 NUT](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavformat/nutenc.c), [MOV muxer](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavformat/movenc.c), [CLI timestamps](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/fftools/ffmpeg_mux.c#L166), [AV1 ISOBMFF v1.2](https://aomediacodec.github.io/av1-isobmff/v1.2.0.html#av1-sample-format), [Enhanced RTMP v2](https://github.com/veovera/enhanced-rtmp/blob/main/docs/enhanced/enhanced-rtmp-v2.md#enhanced-video).

## Ограничения очередей и восстановление потребителя

`QueueLimits` содержит `MaxPackets uint32`, `MaxBytes`, `MaxPacketBytes`, `MaxConfigBytes uint64` и `ResyncTimeout time.Duration`. `Validate() error` требует положительных значений и `MaxConfigBytes <= MaxPacketBytes <= MaxBytes`; ошибка распознаётся как `ErrInvalidQueueLimits`. `MaxPacketBytes` относится к тому же логическому весу payload + headers, что `Packet.StoredBytes`.

Численные defaults здесь не назначаются. T03/T05 выбирают значения по размерам пакетов, числу потребителей, удерживаемой памяти и допустимому ожиданию; проверяют границы до запуска. Интервалы `time.Duration` выражены в наносекундах. Валидация настроек сама по себе не ограничивает вход: адаптер проверяет размер до чтения/выделения полной копии, будущая очередь проверяет вес и количество при добавлении.

Переполнение или oversized packet затрагивают только данного потребителя. Его устаревший backlog очищается; зависимые кадры отбрасываются, текущие headers сохраняются только в пределах бюджета. Восстановление начинается с актуальной config и следующей пригодной независимой video-точки; аудио до согласованного начала не выпускается. Ожидание ограничено `ResyncTimeout`. Дальнейшие reconnect/окончательный отказ относятся к владельцу потребителя. Router не ждёт медленный Publisher и не отменяет остальные выходы.

## Контракт независимого Publisher

`internal/media/publisher` владеет выполнением одного назначения: подпиской стабильного выходного Router группы, соединением, переподключениями, счётчиками и завершением. `internal/media/rtmp` отвечает за исходящий протокол, TLS и представление сжатых данных. В этих пакетах нет SQL и запуска FFmpeg на назначение. Общим кодированием и переключением источников владеет Group/Switcher; ссылку на группу освобождает вызывающий код отдельно от Publisher.

Запуск разделён на локальную подготовку и сетевую активацию. Вызывающий код выполняет `Claim → MarkIssued → BindExecutionOwner → Prepare → Complete(true) → OpenOutputObserver → Activate`. `Prepare` проверяет точный сохранённый снимок, совместимость назначения, ограничения и эксклюзивность выполнения, не открывая соединений. `Complete(true)` подтверждает подготовленное локальное выполнение. `Activate` получает долгоживущий контекст выхода и точный `OutputObserver`; контекст запроса подготовки не становится временем жизни передачи. Состояние `PUBLISHING` допустимо только после `NetStream.Publish.Start` и полной отправки начальных видео- и аудиопакетов. Оно не подтверждает декодирование или изображение у зрителя.

Отказ подготовки оформляет вызывающий код через `Complete(false)`. Ошибка после успешного `Complete`, до сетевой активации, требует отдельной остановки точного прежнего исполнения. SessionManager использует атомарный `CompensateOutputStart`: проверка fence и принятие stop находятся в одной транзакции, выигравший пользовательский stop и новое исполнение сохраняются. Окончательный отказ работающего Publisher возвращается вызывающему коду для `FailOutput`; сам компонент не закрывает пригодный OutputObserver ради обхода этой операции. Неоднозначный исход управляющей записи разрешается по точным сохранённым данным, без повторного сетевого выполнения. Отдельное удержание и освобождение физического исполнения описаны в [доменном контракте](domain-storage-contracts.md#физическое-выполнение-выхода).

Одна Subscription является единственной очередью назначения. Каждая очистка при переполнении или смене источника/конфигурации меняет непереиспользуемое поколение доставки. `Delivery.IsCurrent` проверяет и это поколение: прежняя выдача становится устаревшей даже при неизменных заголовках. Повторная очистка во время восстановления не продлевает уже начатый `ResyncTimeout`. При новом соединении подписка создаётся после подтверждения публикации и начинает свежую синхронизацию. На исправном соединении смена источника, конфигурации или восстановление очереди повторяет актуальные заголовки перед независимым видеокадром и согласованным AAC, сохраняя соединение и общее начало отсчёта времени. Уже допущенное полное RTMP-сообщение завершается целиком либо соединение отбрасывается при ошибке записи; записанные байты отозвать нельзя.

Временные DNS/TCP/TLS-транспортные ошибки, EOF, сброс и отказ соединения, истечение сетевых сроков повторяются до остановки выхода. Положительная задержка увеличивается экспоненциально с заданным верхним пределом; её сброс требует полной фактической начальной A/V-отправки. Некорректные настройки, неподдержанный формат/протокол, непредставимое время, явный отказ авторизации/публикации и ошибка проверки сертификата окончательны. Ожидания подключения, TLS, общего запуска RTMP и полной записи сообщения ограничены явно. После подтверждения публикации отсутствие входящих управляющих сообщений допустимо; начатое сообщение имеет конечный срок завершения, который фрагменты и чередование сообщений не продлевают. Отмена прерывает сеть и ожидает принадлежащие компоненту операции, включая позднее завершение подключения.

Встроенное назначение принимает `Endpoint` как URL приложения и `StreamKey` как отдельное точное имя AMF-публикации. Сохраняются исходное экранирование пути и строка запроса; ключ не преобразуется в путь. Userinfo и любой разделитель fragment `#` явно отклоняются до сети. Контракт `OutboundResolver` допускает адаптеры площадок без закрытого enum и без подстановки параметров кодирования по имени площадки. RTMPS проверяет цепочку сертификата, hostname и SNI; тестовый центр доверия задаётся явно.

Выходной адаптер использует публичные примитивы закреплённой `gortmplib v1.0.1` и собственное обрамление сообщений: fmt0 в начале, fmt3 для продолжений, little-endian MessageStreamID и повторение расширенной временной метки. Высокоуровневый SDK Writer не используется для преобразования конфигураций и пакетов. Настоящие `av1C`, `avcC`, ASC и полезная нагрузка AV1 TU/H.264 AVCC/AAC AU передаются побайтно после проверки существующим codec-портом; temporal delimiter не добавляется. Один читатель принимает управляющие сообщения, целые исходящие медиаданные, команды и управляющие ответы сериализуются одним владельцем записи.

Преобразование времени на RTMP-границе задаётся `Q(t)`: точные рациональные миллисекунды округляются до ближайшего целого, половина — от нуля. PTS и DTS округляются независимо; H.264 composition offset равен `Q(PTS) − Q(DTS)` и проверяется на signed24. Отдельное округление разности, промежуточный float/`time.Duration` и искусственный шаг `+1 ms` не применяются. На новом соединении первый независимый видеокадр задаёт общий `O = min(Q(PTS), Q(DTS))`; обе дорожки используют `Q(t) − O`. AAC и AV1 требуют исходного `PTS == DTS`; общий Packet со знаковыми временными метками сохраняет более широкий контракт. Начальный AAC начинается не раньше PTS видео, поэтому дополнительная очередь для выбора начала отсчёта не нужна. Это начало не меняется при восстановлении на исправном соединении. Проверяются неотрицательный транспортный DTS, неубывание каждой дорожки, представимость и однозначность последовательных значений; логическое время хранится без сворачивания, временная метка сетевого сообщения вычисляется явным modulo `2³²`.

Счётчики очереди учитывают потерянные AU до передачи через `Next`, Publisher — оставленные после получения: устаревшие, прерванные сетью, отменой или окончательным отказом. Каждый AU получает одну причину потери; успешно полностью записанный AU позднее потерей не становится. Заголовки и управляющие сообщения не являются AU. Положительный результат `Write n` учитывается и при частичной ошибке; для RTMPS это незашифрованные байты RTMP, принятые `tls.Conn.Write`, а не число байтов NIC или подтверждение получателя. Счётчики полностью отправленных полезных данных, AU и видеокадров растут лишь после полной записи сообщения. При замене подписки её окончательные потери переносятся один раз; согласованный снимок не суммирует одновременно перенесённый итог и прежнюю активную подписку. Накопительные `uint64` насыщаются с явным признаком; идентичности и поколения не насыщаются. Очередь, ожидающее аудио, конфигурации, выданный AU и сетевые буферы имеют отдельный логический учёт; это не heap/RSS/TLS/OS-память. Окна скоростей и сборщики остаются следующему слою мониторинга.

### Входящие ACK и достоверность диагностики

Входящие ACK не управляют разрешением отправки. Отсутствие ACK, числовое опережение, дубликат, устаревшее либо неоднозначное значение не закрывают соединение и не вызывают reconnect или `FAILED`. Срок полной TCP/TLS-записи, отмена, очереди и изоляция назначений сохраняются. Адресация, длина и обрамление управляющих сообщений по-прежнему проверяются; собственные ACK по `WindowAcknowledgementSize` и ответы ping продолжают работать. `SetPeerBandwidth` сохраняет правила управляющего ответа для hard/soft/dynamic, но его окно не ограничивает Write. Прежний предел окна `MaxInt32` для разрешения отправки снят.

Диагностика использует единственный локальный `WrittenBytes` конкретного соединения: сумму фактических положительных `Write n` до TLS-шифрования, включая 3073 байта согласования RTMP, обрамление, управляющие сообщения и частичную запись с ошибкой. Потенциально записываемые байты к этому счётчику не прибавляются. Обработчик чтения не ждёт завершения записи ради диагностики и продолжает разбирать управляющий поток.

Для сопоставления `uint32` хранится абсолютная опорная величина `A`, изначально нулевая, и `H=2³¹`. При локальном счётчике `W` условие `W>A && W-A>=H` означает потерю однозначной эпохи до нового соединения. Фактическое переполнение самого `W` также прекращает достоверное сопоставление, сохраняя передачу. Ближайший оборот по локальному счётчику не угадывается.

Пока эпоха известна, разность `d=uint32(raw-uint32(A))` равная нулю обозначает дубликат; `d>=H` игнорируется. При `0<d<H` сумма `X=A+d` принимается только без переполнения и при расстоянии до `W` меньше `H`. Изолированный непредставимый или далёкий ACK не продвигает опорную величину и сам по себе не делает всё соединение неопределённым. Принятый `X` продвигает `A`, в том числе при числовом опережении и во время записи.

Событие опережения создаётся только для нового принятого `X>W`, когда физический `Write` не выполняется; его размер точно равен `X-W`. Каждое такое подтверждение считается отдельно. Во время незавершённого `Write` точный принятый объём неизвестен: метрики не меняются и ACK позднее не переигрывается. Повтор принятого подтверждения также не становится новым событием. Нижняя оценка, основанная на полном размере незавершённой записи, не подставляется вместо размера опережения.

Четыре значения `ack_ahead_events_total`, `ack_ahead_bytes_last`, `ack_ahead_bytes_max`, `ack_last_anomaly_at` описаны в [контракте мониторинга](monitoring-contracts.md#диагностика-опережения-ack). Обработчик чтения синхронно передаёт подтверждённое событие короткому обработчику Publisher после освобождения блокировки транспорта. Обработчик обновляет только локальные RAM-счётчики, без ввода-вывода, обращения к `RuntimeAuthority`, журналирования и повторного входа в соединение. Он установлен до `DialOutbound`, поэтому сохраняет события неудачного согласования и коротких попыток. Опрос снимка не суммирует те же события повторно. Завершение `Wait` предшествует следующей попытке; новое соединение получает собственную опорную величину, накопления Publisher сохраняются до нового запуска выхода.

Это ограниченное правило числовой диагностики, а не доказательство ошибки площадки. Пропущенные наблюдения во время записи и после потери эпохи не означают отсутствия расхождений. Отдельного допуска `+4` и исключений по имени площадки нет. Причина исходного расхождения остаётся неизвестной; результаты локальной приёмки T13 учитываются отдельно от прежней T05 и целевого эфира T11.

Первичные протокольные источники: [RTMP December 2012](https://rtmp.veriskope.com/pdf/rtmp_specification_1.0.pdf), [авторские уточнения RTMP](https://zenomt.github.io/rtmp-errata-addenda/rtmp-errata-addenda.html), [Enhanced RTMP v2](https://veovera.org/docs/enhanced/enhanced-rtmp-v2.html). Независимая локальная проверка прежней отправки описана в [результате приёмки](#результат-локальной-приёмки-отправки).

## Watchdog и условия LIVE/fallback

`core.WatchdogPolicy` содержит положительные `VideoTimeout`, `AudioTimeout`, `RecoveryWindow`, `KeyframeTimeout time.Duration`. `media.WatchdogPolicy` остаётся псевдонимом типа; обе прежние категории ссылаются на одну ошибку для `errors.Is`. `Validate() error` возвращает категорию `ErrInvalidWatchdogPolicy`. Порядок соотношений этих интервалов и значения по умолчанию не навязываются без проверки компонента.

Предварительные условия допуска источника: обе обязательные дорожки, подтверждённое адаптером соответствие выходному формату группы, актуальные headers, пригодная точка независимого старта и согласуемая временная шкала. Побайтовое равенство headers независимых кодирований не требуется. Равенство заявленных MediaFormat не доказывает пригодности: codec-aware проверка и интеграционные результаты принадлежат T03/T04. Пока пригодность неизвестна, группа остаётся на пригодном fallback.

| Событие | Требуемое поведение будущего компонента |
| --- | --- |
| До первого OBS | Подготовленный и проверенный fallback; выходной профиль `copy` уже известен. |
| Пропала любая обязательная дорожка либо данные перестали продвигаться | Fallback соответствующей группы. Headers, дубликаты и открытое соединение не восстанавливают здоровье. |
| Источник восстановился | Обе дорожки здоровы непрерывно в течение `RecoveryWindow`; затем требуется актуальная пригодная video-точка в пределах `KeyframeTimeout`. Нарушение сбрасывает стабилизацию. |
| Изменилась metadata/config | Новая revision, повторная проверка пригодности и точки синхронизации; старые queued packets исключаются. |
| Несовместимый LIVE | Профиль и исправные выходы сохраняются; источник не становится LIVE. |
| Ручная пауза | Fallback сохраняется независимо от продолжающегося OBS. |
| Override | Старый вход OBS заменён после проверки ключа Stream и активной Session; группы, fallback и исправные Publishers сохраняются. |
| Отказ fallback без пригодного LIVE | Явное отсутствие подачи и причина ошибки; успешная передача не объявляется. |

Переход режима сам по себе не закрывает исправные исходящие соединения. Постоянство соединений проверяется на настоящих локальных RTMP/RTMPS-границах в T05; сохранение картинки/звука у зрителя — отдельно в T11.

## Группы и подготовленные файлы

`internal/media/group.Registry` принадлежит выданному владельцу Session. Ключ группы включает точное разрешение родительской Session, настроенный `GroupID`, полный канонический профиль, точный manifest поколения/варианта и правила fallback. Выходы с одинаковым снимком разделяют Router и результат кодирования; разные настроенные группы или профили получают независимых работников. Выход держит ссылку, общие ресурсы принадлежат Session. Последняя ссылка отзывает группу и ждёт полного завершения; запись об останавливающейся группе запрещает параллельную замену до join. Чисто завершённая группа освобождает бюджет и для другого ключа; неподтверждённая или ошибочная очистка сохраняет блокировку.

У группы стабильный выходной Router, отдельные источники LIVE/fallback и Switcher с ограниченными очередями. Терминальная LIVE-подписка после длительного отсутствия OBS переподключается с конечной задержкой, сохраняя группу и fallback. Override заменяет только входную попытку и зависимый transcode worker. `copy` не запускает кодировщик. Группа наблюдает `DesiredPaused`, а потеря пригодного fallback при отсутствии LIVE означает явное отсутствие подачи с причиной.

`Group.Ready` и `WaitReady(ctx)` проверяют пригодность текущей fallback-попытки: обе дорожки, подтверждённую независимую video-точку и условия A/V/timing Switcher. Старый успех, process/UDS и выбранный LIVE этого доказательства не заменяют. Новая попытка, EOF, отказ или просроченная дорожка отзывают готовность. Registry применяет desired-control с монотонной ревизией; новая группа получает актуальное желание, старый poll не откатывает его.

Проигрыватель использует отдельную топологию Supervisor: независимо открытый обычный файл, проверенный по размеру/хешу, передаётся через FD в FFmpeg, затем через выходной UDS/fMP4 в Go. Команда FFmpeg 7.1.5 использует `-fd 3 -i fd:`, `-stream_loop -1`, `-re`, `-c copy`. Дескрипторы принадлежат попытке до её полного завершения; `dup` общего reader не подменяет независимое открытие с позицией 0. Предварительная проверка ffprobe и кодирование при запуске проигрывателя не выполняются.

Switcher сериализует пакеты и управляющие события, учитывает монотонный прогресс обеих дорожек и собственные выходные epoch/revisions. Задержанное событие не переводит часы проверки назад. Новый сегмент начинается с действительной точки независимого старта и полного AAC AU; один точный рациональный сдвиг обеих дорожек сохраняет `PTS−DTS` и исходное A/V-смещение. Границы декодирования и максимальная уже опубликованная presentation-метка сохраняются между источниками и попытками. Неизвестная длительность требует ограниченного lookahead; хвост не получает выдуманное значение. Непредставимый пересчёт времени, переполнение, несовместимый кодек и невозможный переход отклоняются явно. `MaxAVSkew` и `MaxTransitionGap` задаются вызывающим; нулевой разрыв при переходе не обещается.

Подготовка использует конечные бюджеты загрузки/результата, ffprobe/заголовков/диагностики, размеров/длительности, очереди и сроков. Production выбирает `libsvtav1` для AV1 и `h264_nvenc` для H.264; CPU-кодировщики подставляются только явно в тестах. Поддержанный порт ограничен 8-bit yuv420p SDR bt709 и проверенным AAC-LC mono/stereo; структурно валидный профиль ещё не подтверждает поддержку энкодером. AV1 CBR требует равных target/max и точного буфера 20–10000 ms. В версии 2 AV1 VBR использует `rc=1`, random-access prediction и hierarchical level 0, CBR — `rc=2` и low-delay; native `mbr=0` в обоих режимах. Ненулевые VBR max/buffer отклоняются, режима CBR вместо VBR нет. Внутренние prediction/overlays/DG/TF/SCD-настройки закрыты для custom. Неизвестные параметры не дополняются значениями желаемого профиля. Прежняя локальная CPU-приёмка относится к указанному ниже прежнему снимку, а новые режимы требуют собственной рабочей проверки; целевой NVENC проверяется отдельно.

`EffectiveLoopDuration` сохраняет исходную продолжительность и отдельно вычисляет длину петли: округляет вверх до общей сетки полных видеокадров, AAC AU по 1024 сэмпла и точных микросекунд CLI. `tpad` повторяет последний видеокадр, `apad` добавляет тишину, а `-t` задаёт вычисленную длину. Например, при 30 FPS/48 kHz исходная секунда превращается в петлю 1,6 s: 48 кадров и 75 AAC AU. Бюджет `MaxDuration` проверяется после округления до запуска процесса; слишком большая или непредставимая сетка отклоняется.

`NormalizePrepared` работает только с результатом принадлежащего Manager нативного AAC-кодировщика. Фактические метаданные ffprobe и каждая единица доступа fMP4 должны совпасть. Удаляется только целая первая AU с `Skip Samples=1024`, `discard_padding=0`, подтверждённой длительностью и концом в нуле. Оставшиеся payload, логические PTS/DTS и длительности не меняются. Заголовок AV1 берётся из фактического первого независимого TU. При отрицательном H.264 decode origin контейнер использует один точно представимый общий сдвиг через `OriginMapping`; edit list снимает его для обеих дорожек. Произвольный секундный сдвиг не используется. Затем проверяются полные дорожки, непрерывный общий период и точное соответствие вычисленной длине. Сжатый AAC-контекст влияет на первые декодированные сэмплы; неизменность PCM после удаления начальной задержки кодировщика не обещается. Реальные проверки отдельно сверяют число сэмплов, звук, тишину и временные метки.

Подготовленный файл имеет presentation origin 0. Пусть `F=FPS.den/FPS.num`, `A=1024/sample_rate`, `T=N·F=M·A`. Сохраняемый AAC имеет `PTS=DTS=j·A`, H.264 в неизменном decode order — `DTS=d0+i·F`, где `d0≤0`, а его PTS образуют точную перестановку кадров от 0 до `N−1`. Первый видеокадр — подтверждённый IDR с PTS 0. Presentation-покрытие обеих дорожек равно `[0,T)`; decode-интервалы имеют одинаковую длину, но их абсолютные концы при B-кадрах различаются. Signed CTS сохраняется; сортировка payload по PTS, замена PTS на DTS и принудительное отключение B-кадров не выполняются.

Общий контейнерный сдвиг не меньше `−d0` и точно представим в обеих шкалах. Для шкал `1/tv` и `1/ta` он выбирается на сетке `1/gcd(tv,ta)` с проверкой переполнения; одного `S=−d0` при рациональном FPS может быть недостаточно. Повтор k добавляет ровно `k·T` к обеим дорожкам, без priming или decode lead в периоде. AV1 сохраняет PTS=DTS. Неподтверждённый/частичный padding, разрывы/дубликаты presentation coverage, переставленные decode DTS и непредставимые смещения отклоняются. Общие fMP4/Switcher и существующие A/V-бюджеты не ослабляются. Дополнительный нормализованный staging заранее регистрируется; исходный и нормализованный файлы каждый ограничены `MaxOutputBytes`, поэтому временно требуется до двух таких бюджетов на вариант. После проверки исходный staging удаляется с барьером долговечности.

Пригодность H.264 с B-кадрами зависит также от действующего `MaxTransitionGap`: задержка декодирования не получает дополнительного бюджета автоматически. Например, две кадровые длительности при `25/2` FPS равны 160 мс и не помещаются в бюджет 100 мс. Сохранённый профиль не означает готовность конкретной группы; проверка её фактической готовности остаётся обязательной.

Пакетная проверка подготовки отключает синтетическое заполнение временных полей ffprobe через `+nofillin`. При отсутствующей duration видео ожидаемый шаг сетки затем обязательно сравнивается с настоящей duration каждой единицы доступа fMP4; для AAC сохраняется доказательство полной AU. Выдуманное ffprobe значение не подменяет содержимое файла, а отсутствие или расхождение duration в самом fMP4 остаётся ошибкой.

Prepared video timescale сохраняет сокращённый числитель FPS `N`, если `N≥1000`; при меньшем `N` используется уже вычисленный movie timescale — LCM числителя и частоты AAC. Шаг кадра в выбранной шкале должен быть положительным, точным и не превышать `INT_MAX`; новые профили проверяют эту представимость до сохранения, а построитель — до запуска. Чтение прежней истории не ужесточается. Более точная шкала сохраняет физические PTS/DTS и длительности и исключает подтверждённую ветку FFmpeg 7.1.5, которая при CTTS и грубой шкале подставляет один tick вместо длительности кадра. Безусловное увеличение уже достаточной шкалы не применяется.

FilePlayer сохраняет обычное копирование сжатых AU. `noparse` не гарантирует сохранность временных меток, а `nofillin` лишает native loop нужных длительностей и нарушает период; эти флаги не используются как исправление проигрывателя. Проверка проходит по настоящим `tfdt/trun` через Go demux для каждой AU: один средний FPS, общая длительность или вывод ffprobe могут скрыть повреждение границ фрагментов.

AAC-проверка разбирает ASC и обязательный префикс SCE/CPE, длины предшествующих FIL/DSE, ICS и запрещённые поля. Простой блок без спектральных полос и инструментов проверяется до настоящего `ID_END`. Границу и длительность AU предоставляет адаптер; спектральный Huffman-поток целиком не декодируется этой проверкой. Это не обещание обнаружить любое повреждение битового потока. Декодируемость рабочих источников подтверждается отдельно реальным FFmpeg; одного конструктора пакета или поиска завершающих битов недостаточно.

## Тестовые данные и измеримые критерии

Маленькие синтетические наборы в `internal/media/testdata/` имеют описание происхождения и заранее заданные ожидаемые свойства: дорожки, конфигурации, epoch/revision, единицы, timestamps, ключевые кадры и логические размеры. Они создаются для структурных проверок; payload/headers явно условные и не заявляются декодируемыми. Файлы прежнего GPU-замера не используются.

Независимый FLV, ffprobe и framemd5 подтверждают декодирование и число AU, а подписка выходного Router группы — соответствие каждой метки точному `Q(t)−O` при одном origin. Счётчики сравниваются с принятыми байтами и полными медиасообщениями после EOF получателя. Выполнены и прежние CPU-регрессии fallback/fMP4; аппаратные проверки этим запуском не подменяются.

Независимые граничные проверки покрывают little-endian, расширенные временные метки и фрагментацию, дробные/частичные записи, округление и CTS/signed24/сворачивание меток, строгую проверку ответов/URL/ключа/TLS, отсутствие управляющего трафика и сроки частичных сообщений, фактическое завершение и изоляцию. ACK-нумерация обеих сторон включает 3073 байта согласования RTMP; это сверено с созданием счётчиков закреплённой библиотеки до согласования и отдельным принимающим эталоном. AV1 `videocodecid` в метаданных — числовой FOURCC `0x61763031`. Отдельная регрессия публичных API проверяет отказ observer/Activate после успешного Complete и компенсацию вызывающим кодом без единой попытки подключения.

Конкретный исходящий порт ограничен 8-bit yuv420p SDR BT.709 и AAC-LC mono/stereo, фактическими форматами существующего codec-порта. Непустые `Endpoint`/`StreamKey` ограничены 65535 байтами, сообщения/блоки — 10 MiB, одновременные потоки блоков — 62 при поддержке полных CSID, глубина AMF — 64, очередь управляющих ответов — 65536 сообщений, окно отправленных, но пока не подтверждённых байтов — MaxInt32. Рабочие значения всех бюджетов и сроков задаются явно; эти верхние границы не являются значениями по умолчанию. Userinfo/fragment и Adobe challenge authentication не поддержаны. Сохраняемые снимки не переписываются ради совместимости.

Указанное здесь ограничение неподтверждённых байтов окном `MaxInt32` относится к принятому прежнему снимку T05. Текущий [контракт обработки ACK](#входящие-ack-и-достоверность-диагностики) снимает зависимость отправки от этого окна; прежние проверки не являются приёмкой нового поведения.

Схема и зависимости не менялись. Этот результат подтверждает рабочие компоненты на macOS/arm64 и короткие CPU-границы. NVIDIA, Debian, реальные OBS/площадки, полноценное высокоразрешающее декодирование и длительная устойчивость остаются отдельной целевой приёмкой T11. SessionManager, сборщики, REST/SSE и исполняемый сервис не входят в эту приёмку.

## Локальная проверка обработки ACK 8 ноября 2026 года

Исправление T13 реализовано по выбранному варианту А: каждое новое достоверно измеримое опережающее подтверждение считается отдельно. Отправка больше не зависит от ACK. Четыре показателя проходят через Publisher и RAM-наблюдения в общий REST/SSE DTO и генерируемую схему; переподключение сохраняет накопления, новый запуск выхода начинает их заново.

Полный race прошёл; RTMP исполнялся заново, остальные пакеты использовали кэш. Форматирование, модули, vet, lint и сборка прошли. Замена избыточного указания типа и явная проверка ошибки устранили их без изменения принимающих ожиданий; подтверждённых необъяснённых отказов итогового набора нет.
