# Общие контракты медиатракта

Документ задаёт общие значения и инварианты для рабочих пакетов Go backend. Исполняемая основа ограничена типами, конструкторами, валидацией и сравнением значений. Очереди, часы, ingest, UDS, FFmpeg, Switcher и Publishers реализуются вместе с соответствующими компонентами.

## Границы и зависимости

`internal/core` содержит форматы и профиль группы, `internal/media` — пакет, конфигурацию дорожки, единицу времени и настройки ограничений. Зависимость направлена из `media` в `core`. Для этих типов достаточно стандартной библиотеки Go; `go.mod` и выбранный SDK не меняются.

| Область | Выбранное семейство и требуемая возможность | Этап проверки и подключения |
| --- | --- | --- |
| Приём и отправка | `github.com/bluenviron/gortmplib` — кандидат для Enhanced RTMP AV1/AAC, H.264/AAC и RTMP/RTMPS. | T03/T05: точный тег, API, metadata, timestamps, Override и реальные локальные соединения. |
| Хранение | `gorm.io/gorm`, `gorm.io/driver/sqlite`, `github.com/pressly/goose/v3`: CRUD, транзакции и единственный runner SQL-миграций. | T02: совместимость тегов, CGO, фактический SQLite, WAL/FK и временная файловая БД. |
| Управляющий API | `github.com/danielgtaylor/huma/v2`, `github.com/go-chi/chi/v5`: типизированные операции, middleware, OpenAPI и HTTP/SSE. | T08: версии и реальные границы HTTP. |
| Локальный кэш | `github.com/maypok86/otter/v2`: ограниченный восстанавливаемый кэш и остановка фоновых задач. | T09: только после выбора полезного чтения и проверки API конкретной версии. |
| Конфигурация и контейнер | YAML-библиотека и Go mux/demux ещё не выбраны; NUT — кандидат. | T03/T09: проверка рабочих адаптеров и политика новых зависимостей. |

Сохраняемые и сетевые представления этих типов, ORM-модели, SQL-схема, сериализация и digest ключа `FallbackVariant` здесь не устанавливаются. Полный профиль станет входом для решений T02/T04; совпадение настроек не заменяет проверку существующего файла.

## Форматы и полный профиль

В `core` используются следующие типы значений:

| Тип | Поля |
| --- | --- |
| `Codec` | Строковые значения `CodecAV1 = "av1"`, `CodecH264 = "h264"`, `CodecAAC = "aac"`. |
| `GroupMode` | `ModeCopy = "copy"`, `ModeTranscode = "transcode"`. |
| `FrameRate` | `Numerator`, `Denominator`: `uint32`, кадров в секунду. |
| `ColorInfo` | `Range`, `Primaries`, `Transfer`, `Matrix`: `string`. |
| `VideoFormat` | `Codec Codec`; `Width`, `Height uint32`; `FrameRate FrameRate`; `CodecProfile`, `Level`, `Tier`, `PixelFormat string`; `BitDepth uint8`; `Color ColorInfo`. |
| `AudioFormat` | `Codec Codec`; `CodecProfile string`; `SampleRateHz uint32`; `Channels uint16`; `ChannelLayout string`. |
| `MediaFormat` | `Video VideoFormat`, `Audio AudioFormat`. |
| `VideoEncoding` | `TargetBitrateBPS`, `MaxBitrateBPS`, `BufferBits uint64`; `GOPFrames`, `MaxBFrames uint32`; `ClosedGOP bool`. |
| `AudioEncoding` | `BitrateBPS uint64`. |
| `GroupProfile` | `Mode GroupMode`; `Format MediaFormat`; `VideoEncoding VideoEncoding`; `AudioEncoding AudioEncoding`. |

`FrameRate`, `ColorInfo`, `VideoFormat`, `AudioFormat`, `MediaFormat`, `VideoEncoding`, `AudioEncoding` и `GroupProfile` имеют `Validate() error`. Части дроби, размеры, глубина цвета, sample rate, число каналов, битрейты, buffer и GOP должны быть положительными; `TargetBitrateBPS <= MaxBitrateBPS`. Нулевой `MaxBFrames` допустим. Видео ограничено AV1/H.264, аудио — AAC; текущий `MediaFormat` всегда содержит обе дорожки. Режим группы должен быть известен.

Профиль кодека, pixel format, цвет и channel layout задаются непустыми строками; строка из одних пробелов недопустима. `Level` и `Tier` могут быть пустыми, если значение не заявлено или неприменимо. Их синтаксис и codec-specific ограничения проверяет будущий адаптер; структурная валидация не подтверждает поддержку энкодером. Значения автоматически не переписываются и не дополняются defaults.

`FrameRate.Equal`, `MediaFormat.Equal` и `GroupProfile.Equal` сравнивают корректные значения. Если один аргумент не проходит валидацию, результат — `false`. Дроби сравниваются математически: `60/1` равно `120/2`; целочисленное сравнение не должно переполняться. Полное равенство профиля учитывает каждое поле, включая режим, настройки кодирования, необязательные level/tier и структуру GOP. Строки сравниваются точно; нормализация наблюдаемых описаний принадлежит адаптеру.

`copy` имеет явный выходной профиль до первого OBS. Его encoding-поля задают подготовку fallback и параметры группы; они не предписывают перекодирование LIVE. Полное равенство профиля и пригодность источника для переключения — разные контракты. Исполняемых `CompatibleWith` или `CanSwitch` в этой основе нет.

Ошибки валидации `core` распознаются через `errors.Is`: некорректная дробь/описание формата — `ErrInvalidFormat`, настройки кодирования/группы — `ErrInvalidProfile`. Ошибка содержит контекст поля; проверка не требует сравнения полного текста.

## Дорожка, конфигурация и пакет

В `media` определены:

| Тип или операция | Контракт |
| --- | --- |
| `Track` | `TrackVideo = "video"`, `TrackAudio = "audio"`. |
| `TimeBase` | `Numerator`, `Denominator uint32`: секунд на tick; обе части положительны. `Validate() error` и математическое `Equal(TimeBase) bool`, возвращающее `false` для некорректных значений. |
| `CodecConfigInfo` | `Track Track`; `SourceEpoch`, `Revision uint64`; `TimeBase TimeBase`; `Video core.VideoFormat`; `Audio core.AudioFormat`. Активен только формат выбранной дорожки, второй должен быть нулевым. |
| `NewCodecConfig(info CodecConfigInfo, headers []byte) (CodecConfig, error)` | Проверяет описание и непустые headers, копирует байты. Epoch и revision положительны. Кодек выводится из активного формата. |
| `CodecConfig` | Закрытые данные; `Info()` возвращает описание по значению, `Headers()` — копию, `StoredBytes() uint64` — длину headers. `Validate() error` отклоняет нулевое/некорректное значение. |
| `PacketInfo` | `PTS`, `DTS`, `DurationTicks int64`; `Keyframe bool`. |
| `NewPacket(info PacketInfo, config CodecConfig, payload []byte) (Packet, error)` | Принимает корректную неизменяемую config, проверяет описание и непустой payload, копирует payload. |
| `Packet` | `Info()`, `Config()` возвращают значения; `Payload()` — копию. `StoredBytes() uint64` учитывает payload и headers. `Validate() error` отклоняет нулевое/некорректное значение. |

Пакет представляет один сжатый access unit. Его дорожка, формат, epoch, revision и единица времени однозначно определяются config. Отрицательные PTS/DTS допустимы; условия `PTS >= DTS` нет. `DurationTicks >= 0`, ноль означает неизвестную длительность. Аудиопакет не помечается `Keyframe`. Для видео этот признак означает заявленную адаптером пригодность независимого старта; конструктор не проверяет битовый поток.

Нулевые `Packet` и `CodecConfig` не готовы к обработке; их getters безопасны и возвращают нулевые значения/пустые данные. `Validate` и конструкторы возвращают обёрнутые `ErrInvalidPacket`, `ErrInvalidConfig` или `ErrInvalidTimeBase` соответственно. Некорректная config в `NewPacket` распознаётся как `ErrInvalidPacket`; проверка самой config — как `ErrInvalidConfig`. Ошибки вложенных полей могут сохраняться в цепочке, но корневая категория обязательна.

Описание формата связывается с headers в одном неизменяемом значении. Соответствие описания содержимому headers, правильность access unit, настоящая random-access точка и декодируемость проверяются адаптером и интеграцией. Синтетические bytes и успешный конструктор этого не подтверждают.

## Владение памятью и учёт размеров

После конструирования Packet и CodecConfig неизменяемы; их можно передавать по значению и читать совместно. Изменение исходных slices либо результата `Payload()`/`Headers()` не меняет объект или уже переданные копии. Конфигурацию можно разделять между пакетами; байтовые массивы наружу не выдаются. Пулы, заимствованные буферы, refcount и `Release` не вводятся.

Это явная граница копирования: в Go копирование slice само по себе сохраняет общий backing array. Основание — [спецификация Go 1.27.3](https://github.com/golang/go/blob/go1.27.3/doc/go_spec.html#Representation_of_values); доступная локальная документация `bytes.Clone` подтверждает копирование байтов.

`StoredBytes` — логический вес сжатых данных: payload + headers, для одной config — только headers. Общая config консервативно учитывается в каждом пакете. Это не размер heap/RSS. Количество объектов ограничивается отдельно; адаптеры также ограничивают входное описание и отдельные хранилища metadata.

## Поколения источника и временная шкала

Идентичность feed задаётся владельцем входного слота вне Packet. LIVE и FALLBACK имеют независимые текущие состояния; epoch не сравниваются глобально между ними или между группами. Владелец feed назначает `SourceEpoch` при новой инкарнации источника, Override, перезапуске producer либо разрыве входной временной шкалы. Значения не переиспользуются и не переполняются с переходом к нулю.

Обе дорожки одного текущего экземпляра feed принадлежат одной epoch. `Revision` локальна для `(feed, epoch, track)` и меняется при изменении headers, наблюдаемого формата или TimeBase. Номера аудио- и видеоревизий могут различаться. Один ключ `(feed, epoch, track, revision)` всегда обозначает одну config. Владелец публикует согласованный снимок текущих A/V-конфигураций; новые данные принимаются только относительно этого снимка. Запоздалые пакеты прежней epoch или прежней текущей revision отбрасываются.

Внутри непрерывного сегмента дорожки DTS не убывает; PTS может менять порядок при перестановке кадров. Конструктор одного пакета не может проверить последовательность. Изменение единиц, сброс и переполнение внешних timestamps обрабатываются на границе адаптера. Обычная петля с непрерывными timestamps не требует новой epoch; обнаруженный сброс при петле требует новой границы непрерывности.

Выходной timeline строится отдельно от входных epoch. Переключение, Override и граница петли сохраняют согласованную A/V-шкалу и композиционное смещение `PTS − DTS`; аудио начинается с согласованного полного access unit. Рескейлинг и offsets реализуются в рабочих адаптерах/Switcher: они обязаны явно определить округление и проверять переполнение до арифметической операции. Signed overflow в Go не вызывает panic, поэтому одного типа `int64` недостаточно для такой проверки.

PTS/DTS не являются временем получения пакета, wall clock либо временем сохраняемого Event. Watchdog использует локальные монотонные часы и прогресс валидных данных обеих дорожек.

## Ограничения очередей и восстановление потребителя

`QueueLimits` содержит `MaxPackets uint32`, `MaxBytes`, `MaxPacketBytes`, `MaxConfigBytes uint64` и `ResyncTimeout time.Duration`. `Validate() error` требует положительных значений и `MaxConfigBytes <= MaxPacketBytes <= MaxBytes`; ошибка распознаётся как `ErrInvalidQueueLimits`. `MaxPacketBytes` относится к тому же логическому весу payload + headers, что `Packet.StoredBytes`.

Численные defaults здесь не назначаются. T03/T05 выбирают значения по размерам пакетов, числу потребителей, удерживаемой памяти и допустимому ожиданию; проверяют границы до запуска. Интервалы `time.Duration` выражены в наносекундах. Валидация настроек сама по себе не ограничивает вход: адаптер проверяет размер до чтения/выделения полной копии, будущая очередь проверяет вес и количество при добавлении.

Переполнение или oversized packet затрагивают только данного потребителя. Его устаревший backlog очищается; зависимые кадры отбрасываются, текущие headers сохраняются только в пределах бюджета. Восстановление начинается с актуальной config и следующей пригодной независимой video-точки; аудио до согласованного начала не выпускается. Ожидание ограничено `ResyncTimeout`. Дальнейшие reconnect/окончательный отказ относятся к владельцу потребителя. Router не ждёт медленный Publisher и не отменяет остальные выходы.

## Watchdog и условия LIVE/fallback

`WatchdogPolicy` содержит положительные `VideoTimeout`, `AudioTimeout`, `RecoveryWindow`, `KeyframeTimeout time.Duration`. `Validate() error` возвращает категорию `ErrInvalidWatchdogPolicy`. Порядок соотношений этих интервалов и значения по умолчанию не навязываются без проверки компонента.

Предварительные условия допуска источника: обе обязательные дорожки, подтверждённое адаптером соответствие выходному формату группы, актуальные headers, пригодная точка независимого старта и согласуемая временная шкала. Побайтовое равенство headers независимых кодирований не требуется. Равенство заявленных MediaFormat не доказывает пригодности: codec-aware проверка и интеграционные результаты принадлежат T03/T04. Пока пригодность неизвестна, группа остаётся на пригодном fallback.

| Событие | Требуемое поведение будущего компонента |
| --- | --- |
| До первого OBS | Подготовленный и проверенный fallback; выходной профиль `copy` уже известен. |
| Пропала любая обязательная дорожка либо данные перестали продвигаться | Fallback соответствующей группы. Headers, дубликаты и открытое соединение не восстанавливают здоровье. |
| Источник восстановился | Обе дорожки здоровы непрерывно в течение `RecoveryWindow`; затем требуется актуальная пригодная video-точка в пределах `KeyframeTimeout`. Нарушение сбрасывает стабилизацию. |
| Изменилась metadata/config | Новая revision, повторная проверка пригодности и точки синхронизации; старые queued packets исключаются. |
| Несовместимый LIVE | Профиль и исправные выходы сохраняются; источник не становится LIVE. |
| Ручная пауза | Fallback сохраняется независимо от продолжающегося OBS. |
| Override | Старый вход заменён после авторизации; группы, fallback и исправные Publishers сохраняются. |
| Отказ fallback без пригодного LIVE | Явное отсутствие подачи и причина ошибки; успешная передача не объявляется. |

Переход режима сам по себе не закрывает исправные исходящие соединения. Постоянство соединений проверяется на настоящих локальных RTMP/RTMPS-границах в T05; сохранение картинки/звука у зрителя — отдельно в T11.

## Тестовые данные и измеримые критерии

Unit-тесты находятся рядом с пакетами. Маленькие синтетические наборы в `internal/media/testdata/` имеют описание происхождения и заранее заданные ожидаемые свойства: дорожки, конфигурации, epoch/revision, единицы, timestamps, ключевые кадры и логические размеры. Они создаются для структурных проверок; payload/headers явно условные и не заявляются декодируемыми. Файлы прежнего GPU-замера не используются.

Исполняемая основа проверяется положительными, отрицательными и граничными сценариями валидации, математического равенства дробей/профилей и отсутствия aliasing. Отрицательные PTS/DTS и перестановка PTS допустимы. Числа в небольших fixtures — тестовые входы, а не эксплуатационные defaults или SLO.

| Будущая проверка | Измеряемый результат и ожидаемое свойство | Где обосновать допуски |
| --- | --- | --- |
| Преобразование timestamps | DTS отдельно по дорожке, PTS/DTS и `PTS − DTS` в точной time base; явный результат округления, отсутствие молчаливого overflow. | T03: известные входы и единицы реального адаптера. |
| A/V и переходы | Междорожечный сдвиг, gap/overlap, длительность перехода по монотонным часам; согласованный cut-point и независимая точка старта. | T04/T05: подготовленные источники и действующие настройки до прогона. |
| Очередь и resync | Вес, число элементов, oversized packets, срок ожидания и продвижение исправных потребителей. | T03/T05: действующие бюджеты и контролируемый медленный потребитель. |
| Локальный медиатракт | Настоящие ingest/UDS/Publisher, metadata и временная шкала; декодируемость отдельно короткой CPU-интеграцией FFmpeg. | T03–T05; FFmpeg не требуется обязательному CI. |
| Целевой эфир | Фактическое воспроизведение, A/V, переходы, GPU и длительная устойчивость. | T11: разрешённая целевая среда и заранее согласованные критерии. |

Unit-проверки этих значений не подтверждают runtime-очередь, авторизацию, декодируемость, отсутствие артефактов AV1-переключения или аппаратную/live-совместимость. После появления пакетов обязательный `make check` включает форматирование, модули, vet, lint, тесты, race и сборку. Введённые контракты, fixtures и результаты проверки относятся к одному стабильному снимку.
