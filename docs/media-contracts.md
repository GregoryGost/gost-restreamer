# Общие контракты медиатракта

Документ задаёт общие значения и инварианты для рабочих пакетов Go backend и выбранные границы конкретных адаптеров. Очереди, часы, ingest, UDS, FFmpeg, Switcher и Publishers проверяются вместе с соответствующими компонентами; описание контракта не является отчётом о приёмке реализации.

Результаты локальных проверок ниже относятся к указанным историческим снимкам. Актуальные результаты основного прогона на VM и отложенные сценарии приведены в разделе [целевой приёмки](#target-acceptance).

## Границы и зависимости

`internal/core` содержит форматы, профиль группы и `WatchdogPolicy`, `internal/media` — пакет, конфигурацию дорожки, единицу времени и ограничения очередей. В `media` сохранён совместимый alias `WatchdogPolicy`. Зависимость направлена из `media` в `core`; сами эти значения используют только стандартную библиотеку Go. Зависимости хранения подключены отдельно, выбранный SDK не меняется.

| Область | Выбранное семейство и требуемая возможность | Этап проверки и подключения |
| --- | --- | --- |
| Приём и отправка | `github.com/bluenviron/gortmplib v1.0.1`: собственный raw-адаптер AV1/H.264/HEVC/VP9/AAC; необходимые codec/box типы — `mediacommon/v2 v2.9.3`, `go-mp4 v1.7.1`. | Прежние результаты T03/T05 относятся к исходной AV1/AAC-области; расширенные привязки проверяются отдельно. |
| Хранение | GORM `v1.31.2`, SQLite dialect `v1.6.0`/CGO driver `v1.14.22`, Goose `v3.27.0`: CRUD, транзакции и единственный runner SQL-миграций. | T02: общий CGO pool, фактический SQLite, WAL/FK и временная файловая БД. |
| Управляющий API | `github.com/danielgtaylor/huma/v2 v2.40.0`, `github.com/go-chi/chi/v5 v5.5.0`: типизированные операции, middleware, OpenAPI и HTTP/SSE. | T08: реальные границы HTTP. |
| Локальный кэш | Экземпляр Otter не создаётся: подходящий путь восстанавливаемого чтения не выбран. | [Контракт приложения](application-contracts.md#решение-о-локальном-кэше): текущее состояние выполнения не допускает вытеснения. |
| Конфигурация и контейнер | Streaming fMP4 с ограниченным Go mux/demux через UDS; YAML — `go.yaml.in/yaml/v3 v3.0.5`. | T03: реальные metadata/timestamps/UDS; T09: загрузка и проверка конфигурации. |

Сохраняемые представления, ORM-модели, SQL-схема, точная сериализация и каноническая идентичность `FallbackVariant` описаны в [контрактах домена и хранения](domain-storage-contracts.md). Сетевые представления проверяются вместе с адаптерами. Полный профиль используется при хранении и подготовке fallback; совпадение настроек не заменяет проверку существующего файла.

[SessionManager и processowner](session-manager-contracts.md) связывают эти компоненты с командами, первоначальной готовностью, отдельным helper и проверяемой очисткой. Независимая локальная приёмка этой интеграции завершена в T06; [результат и ограничения](session-manager-contracts.md#локальная-приёмка) относятся к её собственному снимку. Приведённые ниже результаты прежних снимков сохраняют свою исходную область.

Новая загрузка безусловно заменяет содержимое явно выбранной заглушки и требует новой подготовки, даже если её байты совпадают с прежними. Дедупликации загрузок по содержимому нет. Общий файл допускается для совпадающих полных профилей внутри одной подготовленной версии. Замена публикуется после успешной подготовки и проверки, при ошибке прежняя рабочая версия сохраняется. Генерация и rebuild запрещены во время эфира, включая ручную паузу; воспроизведение уже готового fallback по UDS продолжает работать. Локальная приёмка этих требований описана [ниже](#результат-локальной-приёмки-групп).

## Форматы и полный профиль

В `core` используются следующие типы значений:

| Тип | Поля |
| --- | --- |
| `Codec` | Строковые значения `CodecAV1 = "av1"`, `CodecH264 = "h264"`, `CodecHEVC = "hevc"`, `CodecVP9 = "vp9"`, `CodecAAC = "aac"`, `CodecOpus = "opus"`, `CodecFLAC = "flac"`, `CodecMP3 = "mp3"`, `CodecAC3 = "ac3"`. |
| `GroupMode` | `ModeCopy = "copy"`, `ModeTranscode = "transcode"`. |
| `FrameRate` | `Numerator`, `Denominator`: `uint32`, кадров в секунду. |
| `ColorInfo` | `Range`, `Primaries`, `Transfer`, `Matrix`: `string`. |
| `VideoFormat` | `Codec Codec`; `Width`, `Height uint32`; `FrameRate FrameRate`; `CodecProfile`, `Level`, `Tier`, `PixelFormat string`; `BitDepth uint8`; `Color ColorInfo`. |
| `AudioFormat` | `Codec Codec`; `CodecProfile string`; `SampleRateHz uint32`; `Channels uint16`; `ChannelLayout string`. |
| `MediaFormat` | `Video VideoFormat`, `Audio AudioFormat`. |
| `VideoEncoding` | `TargetBitrateBPS`, `MaxBitrateBPS`, `BufferBits uint64`; `GOPFrames`, `MaxBFrames uint32`; `ClosedGOP bool`. |
| `AudioEncoding` | `BitrateBPS uint64`. |
| `GroupProfile` | `Mode GroupMode`; `Format MediaFormat`; `VideoEncoding VideoEncoding`; `AudioEncoding AudioEncoding`; `Encoding EncodingSettings`; `LiveAudioMode LiveAudioMode`. |
| `LiveAudioMode` | Явный `copy` либо `transcode`; пустое сохранённое значение недопустимо. |
| `EncodingSettings` | Конкретные кодировщики, RC, присутствие QP/CRF, rescale, применимые NVENC/SVT и нормализованный custom; версий возможностей нет. Сравнимое значение без удерживаемых ссылочных коллекций. |
| `OptionalCRF` | `Set bool`, `ValueHundredths int`: присутствие и точное качество в сотых долях. Публичное представление остаётся JSON-числом. |

`FrameRate`, `ColorInfo`, `VideoFormat`, `AudioFormat`, `MediaFormat`, `VideoEncoding`, `AudioEncoding` и `GroupProfile` имеют Validate. Части FPS, размеры, глубина, частота аудио, каналы и GOP положительны. Битрейтные и чистые режимы качества проверяются по конкретному кодировщику: чистые CQP/CRF требуют target/max/buffer=0, SVT VBR — max/buffer=0. FLAC имеет неприменимый audio target=0 только в точной привязке. MaxBFrames=0 допустим. Структурный MediaFormat содержит обе дорожки и поддержанные video/audio codecs; эти проверки не назначают desired-настройки.

Desired-профиль проверяется по [единой закрытой матрице](string-json-contracts.md#настройки). Level/tier могут быть пустыми. AV1 LIVE — copy, H.264 — transcode, HEVC/VP9 — copy либо transcode. AAC LC допускает mono/stereo и применимые 2.1/3.0/4.0/5.0/5.1/7.1; четыре другие конечные привязки — 48 kHz/stereo. Encoder/RC и числовые зависимости предметны, не зависят от версии. Defaults назначаются только при материализации входа; чтение и исполнение их не добавляют. Нулевого исполнимого Encoding и миграции старых настроек нет.

Публичное описание измеренного формата имеет отдельный конечный каталог: известные обозначения производителя сохраняются, пустые строки остаются пустыми, нераспознанные непустые обозначения проецируются в UNKNOWN. Raw VerifiedFormat и парсеры этим представлением не меняются. Дополнительное имя наблюдения не становится допустимой настройкой и не подтверждает возможность обработки.

`FrameRate.Equal`, `MediaFormat.Equal` и `GroupProfile.Equal` сравнивают корректные значения. Если один аргумент не проходит валидацию, результат — `false`. Дроби сравниваются математически: `60/1` равно `120/2`; целочисленное сравнение не должно переполняться. Полное равенство профиля учитывает каждое поле, включая режим, настройки кодирования, необязательные level/tier и структуру GOP. Строки сравниваются точно; нормализация наблюдаемых описаний принадлежит адаптеру.

Copy имеет явный полный выходной профиль до первого OBS. Его encoder-поля задают подготовку и ожидаемый формат, не перекодирование LIVE. Полное равенство профиля и пригодность источника — разные контракты. CompatibleProfileFormat валидирует желаемый профиль и сравнивает фактический формат; CompatibleActualFormat сравнивает два actual/declaration. Прежнего CompatibleFormat и выбора проверки по версии нет. Codec-порт отдельно проверяет реальные headers/AU; метаданных недостаточно.

Создание профиля без live_audio_mode получает copy независимо от видео. Сохранённый профиль всегда содержит явный селектор; чтение, Validate и переименование значения по умолчанию не назначают. Полная замена после CAS требует явного селектора. Audio transcode допускается только с видео transcode; видео copy сохраняет обе дорожки. [Хранение](domain-storage-contracts.md#точное-представление-профиля) использует одну полную форму без версий возможностей.

LIVE copy требует совместимой фактической аудиопривязки с format.audio. Перед построителем проверяются заголовки, AU, частота, каналы и раскладка; построитель проверяет доступный ему actual-вход. Несовместимость отклоняет только LIVE группы, оставляя пригодную заглушку и причину в журнале. Изменение конфигурации и Override требуют новой проверки. Target Opus не является фактическим VBR-битрейтом; MP3/AC-3 подтверждают фиксированный bitrate заголовками. Побайтовое равенство независимых AAC ASC не требуется.

До подготовки владелец вручную задаёт ожидаемые выходные настройки OBS, включая RC и битрейты. Параметры серверного SVT/AOM описывают подготовку AV1, не encoder игрового ПК; LIVE copy сохраняется. [Encoder options и custom](api-contracts.md#полный-профиль-кодирования) задают публичное подмножество. Неподдержанные сочетания и конфликты отклоняются; произвольная команда FFmpeg не принимается.

Один компилятор настроек обслуживает LIVE и подготовку, выбирая рецепт видео по кодировщику и рецепт аудио по привязке, LIVE-селектору и назначению. Старых семантических адаптеров, отдельных версионных рецептов и aliases нет. SVT CQP использует AQ 0, CRF — AQ 2, качество 1…63 и нулевые target/max/buffer; только CRF допускает дополнительные tune 2/4/5. Общий Plan не задаёт физический pix_fmt: CUDA/YUV/P010 единолично выбирает построитель команды. Все параметры и присутствие качества входят в идентичность.

Выбор LIVE-аудио независим от видеорецепта. Для эффективного `copy` компилятор выдаёт только `-c:a copy`, без аудиофильтров, битрейта, изменения частоты и каналов, дополнительных параметров AAC. Настройки `AudioEncoding` и дополнительные параметры аудио всегда применяются к подготовке тишины и также к явному LIVE transcode. Сохраняется одна общая цепочка UDS/fMP4/FFmpeg группы; отдельная очередь исходного аудио не создаётся. Равенство относится к полезной нагрузке соответствующих переданных AAC AU с действующими правилами среза/устаревания, не к контейнеру и не к каждому принятому входному пакету.

В целевом `transcode` разрешение и FPS выхода задаёт полный профиль группы; входной OBS остаётся 1440p60. AV1 1440p60 `copy`, H.264 1440p60 и H.264 1080p60 — три независимых профиля. Два назначения одной H.264-группы используют один результат кодирования; разные разрешения, FPS или остальные поля полного профиля не объединяются в один выход. Для них нужны отдельные fallback-варианты.

BuildNVIDIACommand выбирает ограниченный CUDA-путь для совместимого AV1 → H.264 NVENC: SDR BT.709/8-bit/yuv420p, одинаковые цвет/диапазон/глубина, применимые profile/level/CBR/VBR/AAC LC. Используются av1_cuvid/NVDEC и scale_cuda по rescale policy. Остальные поддержанные сочетания проходят программное декодирование и преобразование по фактическому цвету. Ошибка выбранного пути не запускает повтор с другим encoder. CUDA/HDR/HEVC/VP9 и новые аудиопривязки этим аппаратным маршрутом не расширяются.

Выходная FPS-сетка едина: fps=fps=N/D:round=near:eof_action=round, без выходного -r; fps_mode passthrough и enc_time_base filter передают преобразованные кадры. При rescale_output=false размеры LIVE должны совпадать, подготовка всегда приводит источник к цели. Цвет/глубина преобразуются по запрошенному формату только при известных необходимых характеристиках. PNG/JPEG и SDR8/yuv420p с неполными CICP имеют узкую подготовку SDR BT.709/8/420 через SVT AV1/H.264 NVENC с AAC; SourceFormat остаётся неизвестным, HDR и произвольные дополнительные цветовые преобразования не добавляются.

Для сокращённого `N/D` один выходной tick равен `D/N` секунды. Первая video PTS и EOF округляются к общей сетке до ближайшего значения, при половине — от нуля; последующие presentation ticks идут с шагом один. `start_time` не задаётся, дорожки раздельно не обнуляются. Кодирование с B-кадрами создаёт новые DTS, поэтому сравнение с входными DTS не является оракулом преобразования. Проверяются выходные частота/длительности, PTS/DTS, число кадров и A/V по независимо заданным ожиданиям; сохранение меток транспорта проверяется отдельно.

`NVIDIAConfig` требует фактические `VideoTimeBase` и `AudioTimeBase`. Выходной video track timescale равен `N`; movie timescale — точный LCM сокращённых знаменателей обеих входных шкал, `N` и обеих частот аудио. Непредставимые значения и превышение `INT_MAX` отклоняются до запуска. Поскольку `fps` в FFmpeg 7.1.5 вычисляет выражение через binary64 и `av_d2q`, одного ограничения частей дроби недостаточно. Предварительная проверка требует `2*M*abs(A*D-N*B)<B` точной целочисленной арифметикой, где `M=INT_MAX`, а `A/B` воспроизводит начальный пересчёт `av_d2q`. Неоднозначная дробь отклоняется, вместо молчаливой подмены FPS; произвольный предел частоты не вводится. Проверенная граница относится к обычной IEEE binary64 арифметике FFmpeg 7.1.5.

При LIVE transcode и подготовке тишины AAC кодируется по профилю. [Native AAC FFmpeg 7.1.5](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/aacenc.c) использует `initial_padding=1024` и AU по 1024 сэмпла; начальная задержка и хвост нового кодирования учитываются отдельно от округления видео до половины выходного кадра. В LIVE copy новый кодировщик AAC и его начальная задержка не появляются. Короткие интеграции рабочих Go/UDS/Supervisor/fMP4 проверяют преобразование видео, временные метки и соответствующую обработку аудио. Отдельный локальный VideoToolbox-сценарий использует `-allow_sw 0` и проверяет ту же сетку. Он не подтверждает NVDEC/NVENC, которые остаются целевой аппаратной приёмкой.

Число декодированных сэмплов AAC AU и контейнерная длительность проверяются отдельно. [MOV/fMP4 FFmpeg 7.1.5](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavformat/movenc.c#L1137-L1155) рассчитывает длительность образца по разнице DTS либо концу дорожки. При миллисекундной шкале RTMP она может отличаться от `1024 / sampleRate` без изменения числа сэмплов. Это не отменяет независимую проверку временной шкалы, A/V, начальной задержки и хвоста кодирования.

Ошибки валидации `core` распознаются через `errors.Is`: некорректная дробь/описание формата — `ErrInvalidFormat`, настройки кодирования/группы — `ErrInvalidProfile`. Ошибка содержит контекст поля; проверка не требует сравнения полного текста.

### SDR-матрица

Полная [матрица кодировщиков, профилей, пиксельных форматов, глубины и качества](api-contracts.md#sdr-форматы-цвет-и-кодировщики) является частью медиаконтракта. SVT использует AV1 Main с 4:2:0 и глубиной 8/10 бит. AOM дополнительно поддерживает настоящий серый формат 8 бит, High с 4:4:4 и Professional с 4:2:2. X264 предоставляет соответствующие профили H.264 для 4:2:0, 4:2:2 и 4:4:4; NVENC добавляет только 8-битный high444 к прежним профилям. Точные пары заданы таблицей: более широкий теоретический профиль кодека не разрешает другие сочетания автоматически.

Для SDR-источника и цели используются отдельные таблицы CICP: primaries — 1/4/5/6/7/8/9, transfer — 1/4/5/6/7/8/13/14/15, matrix — 1/4/5/6/7/9/10. Матрица BT2020c с постоянной яркостью требует цветного формата и transfer 1/6/14/15. Неизвестные необходимые характеристики источника, включая `unspecified`, вызывают отказ до запуска кодировщика; желаемые теги не подставляются вместо них. Zscale выполняет реальное преобразование между проверенными исходными и целевыми характеристиками без промежуточного целочисленного BT.709. Свойства выходных кадров и флаги кодировщика согласуются с целью; одних цветовых тегов недостаточно.

Для gray исходная Y сохраняется, U/V заполняются 128 и собираются в YUV444; целевой gray извлекается после преобразования. Неявный scale для gray не используется, поскольку меняет limited-значения. Yuvj420p/422p/444p приводятся к соответствующим плоскостям только с подтверждённым pc/full, без изменения размеров/данных. Ограниченный SDR-рендер изображения и неизвестного SDR-видео описан выше и не считается измерением source CICP. HDR имеет отдельные условия.

X264/AOM имеют фиксированные рецепты без новых публичных блоков настроек и дополнительных custom-параметров. CRF хранится целыми сотыми, исходный JSON проверяется точно. SVT сохраняет целое качество 1…63; x264 добавляет QP 0…51 и CRF 0…51 с шагом 0.01; NVENC — QP 0…51; AOM — целый CRF 0…63. Чистое качество не получает скрытого битрейтного ограничения или VBV. Для него H.264 требует пустого уровня либо `auto`; нулевое качество x264 доступно только для high444 с 4:4:4. До запуска проверяется точная представимость битрейта и буфера в единицах выбранного кодировщика.

H.264 6.0/6.1/6.2 требуют CBR/VBR, нулевого числа B-кадров, одного опорного кадра и проверки FS/MBPS/DPB/BR/CPB; NVENC использует `dpb_size=1`. SVT high tier требует CBR, явного уровня 4.0/4.1/5.0–5.3/6.0–6.3, точного буфера 20…1000 мс, бюджета уровня и согласованной внутренней сетки плиток. Реальные sequence headers и av1C подтверждают уровень и tier; неподтверждённое общее управление уровнем AOM не публикуется. Целевой битрейт SVT остаётся запросом управления кодированием, а не универсальным жёстким ограничением. Полное соответствие любых будущих внешних потоков Annex A/E не обещается.

NVENC lossless требует P4, high444, yuv444p/8-bit, CQP0, B0 и CAVLC без дополнительных AQ/lookahead/multipass/custom настроек. Режим кодировщика `lossless` включает обход преобразования. Сохранность относится ко входу кодировщика после фильтров. Фактические флаги preset, пиксели и производительность GPU требуют отдельного аппаратного наблюдения.

Парсеры AV1/H.264 проверяют реальные профиль, цветовую субдискретизацию, монохромность, глубину, цвет, уровень/tier и согласованность конфигурационных записей с заголовками. Неизвестные CICP-коды сохраняются в исходных заголовках, публично проецируются как UNKNOWN; наблюдение не расширяет допустимые настройки. FMP4 проверяет имеющийся colr/nclx, но прежняя структура контейнера не получает безусловно новый блок: при av1C с Sequence Header colr рекомендован, а не обязателен. Копируемые заголовки и AU остаются неизменными; знаковые метки времени, эпохи источника и независимый старт сохраняют прежние гарантии.

Профиль имеет одну полную строгую форму без корневого или вложенного поля версии возможностей. CRF хранится целыми сотыми с признаком присутствия; каноническое представление включает все влияющие настройки. MetadataVersion=1 и генератор имеют самостоятельные обязанности.

### HEVC, VP9 и HDR

Точные сочетания задаёт [единая матрица HEVC/VP9/HDR](api-contracts.md#hevc-vp9-и-hdr). HEVC Main/Main10 — 4:2:0, 8/10 бит, libx265 либо hevc_nvenc; VP9 profile0/profile2 — 4:2:0, 8/10 бит, libvpx-vp9. Оба допускают LIVE copy/transcode. Их SDR-цели ограничены BT.709; прочие AV1/H.264 SDR-пары заданы общей матрицей. HEVC/VP9 desired level пустой/auto, HEVC tier пустой/main, VP9 tier пустой. Наблюдаемые level/tier не подменяют настройки.

HDR требует 10 бит, BT.2020 primaries, PQ либо HLG, матрицу bt2020nc и известный диапазон. Допустимы HEVC Main10 и VP9 profile2, AV1 Main/SVT либо применимые Main/High/Professional AOM и 10-битные профили x264. AV1 LIVE остаётся copy; H.264 copy и AV1 LIVE transcode не добавляются. Преобразование сохраняет исходные CICP, диапазон и глубину; разрешены FPS, масштабирование и применимое преобразование 10-битных плоскостей. Tone mapping, SDR↔HDR, PQ↔HLG и преобразование диапазона или цветового охвата не выполняются. Перед HEVC NVENC 10-битные плоскости явно упаковываются в P010; измеренный выход остаётся yuv420p10le.

X265 использует medium, закрытый GOP, B0, один опорный кадр, выключенные scenecut/open GOP. HEVC NVENC использует P4/HQ, B0, один опорный кадр, отключённые lookahead/AQ/multipass; публичный блок nvenc по-прежнему относится только к h264_nvenc. VP9 использует один проход good/cpu-used=8, row-mt, нулевые lag/alt-ref и фиксированный GOP. CBR/VBR и QP/CRF имеют отдельные точные пределы и единицы каждого кодировщика; чистое качество требует нулевые target/max/buffer. Нулевое качество не обещает lossless. Произвольные custom и дополнительные публичные настройки не добавляются.

`CodecConfigInfo.HDR` — сравнимый неизменяемый снимок MDCV/CLL и происхождения внешнего ColorConfig. Он хранит присутствие, известность, исходные кодовые значения, сетку и источник; в нём нет maps, slices или указателей. Значения CICP находятся в VideoFormat; provenance разрешает внешнему ColorConfig восполнить только действительно unspecified оси заголовка. Известные coded CICP, диапазон, глубина, chroma и профиль должны совпасть; reserved/UNKNOWN не становятся wildcard. Старые AV1/H.264 SDR-проверки сохраняют строгую семантику. Audio не может содержать HDR.

MDCV/CLL передаются как утверждения исходного источника. Масштабирование не создаёт нового mastering и не подтверждает измеренные максимумы декодированного результата. SEI использует сетки xy/50000 и luminance/10000 с порядком GBR; AV1/VP9 используют RGB, UQ0.16 и отдельные сетки яркости; AMF сохраняет точные биты binary64. Проекция направлена от доказанного источника, округляется к ближайшему значению с половиной от нуля и не использует epsilon, clamp или типовые значения. Неполный неизвестный блок не превращается в нулевой либо положительный mastering. Непредставимая проекция означает неподдержанный порт.

In-band SEI/OBU и Enhanced RTMP ColorInfo имеют разные правила времени жизни. H.264 MDCV/CLL проверяются с первого IDR кодированной последовательности; HEVC MDCV — с первого CLVS, CLL может появиться позднее. При отсутствии подходящей независимой точки такой вход может быть корректным, но неподдержанным для старта. RTMP metadata полностью заменяет предыдущее внешнее описание; Undefined либо пустой объект сбрасывает его, SequenceStart сам по себе не сбрасывает. Изменение snapshot создаёт границу конфигурации до следующего видео, аннулирует прежнюю подачу и требует повторного независимого старта.

FMP4 восстанавливает HDR из стандартных блоков контейнера, заголовков и AU также при UUID-метаданных. Исходные сведения и выходные дескрипторы сверяются на собственных сетках. Только у свежего собственного результата допускается согласование двух независимо правильных проекций источника в контейнере и сжатом потоке, затем нормализация контейнера по фактическому AV1 OBU. Обе проекции сначала проверяются от источника; обратное округление это не заменяет. Copy и произвольные файлы не исправляются, AU не переписываются.

HEVC проверяет hvcC/VPS/SPS/PPS, реальные PTL/VUI, ссылки и IDR, пригодный для холодного старта. Собственный mux использует hev1 с сохранением допустимых in-band parameter sets; hvc1 имеет отдельные правила полноты и размещения. VP9 проверяет configuration record и stateful reference state. Show-existing, alt-ref, superframe, отдельный render size и несколько presentation units не объявляются ключевым кадром: выбранный порт их не поддерживает. Неполное описание нового HEVC/VP9 допускает ограниченное уточнение по первому независимому AU и точной длительности/FPS; прочитанный префикс возвращается через Next. Прежний NewDemuxer не начинает безусловное чтение медиаданных.

Для выбранного MOV/MP4-источника новой HDR-подготовки выполняется один ограниченный проход сжатых пакетов, доказывающий статичный snapshot на всё поколение. Он проходит вне транзакции БД, до публикации; изменение metadata отклоняет подготовку с сохранением прежнего рабочего комплекта. Desired не заменяет фактические record/nclx/SEI/OBU. Общего сканирования загрузок или БД, фонового ремонта и сохранения HDR в history нет.

Исходный LIVE и fallback могут иметь разные корректные MDCV/CLL при одинаковом desired формате. Switcher переносит snapshot выбранного источника. Один RTMP serializer отправляет актуальные metadata либо reset, затем headers, затем независимый AU; устаревшая Delivery не начинает запись, частичная ошибка закрывает соединение. HDR H.264 использует Enhanced AVC. HEVC binding передаёт четырёхбайтовые длины NAL и signed SI24 composition offset; вариант без offset допустим только при нуле. Прежние SDR wire bytes сохраняются.

Полная текущая форма используется во всех самостоятельных копиях и идентичности. Нужны проверки CPU-кодировщиков, normalization/reopen, AU/времени, петель, переключений и ошибок; наличие контракта не является аппаратной приёмкой или подтверждением реальных получателей.

### Конечные аудиопривязки

AAC LC и четыре конечные привязки используют общую видеоматрицу AV1/HEVC/VP9 и HDR. H.264-вход и LIVE AV1 transcode не поддерживаются. [Таблица API](api-contracts.md#opus-flac-mp3-и-ac-3) задаёт codec/profile/encoder/target. Четыре конечных выхода имеют 48000 Hz, 2/stereo и пустой custom; AAC сохраняет собственные частоты/раскладки. Transcode явно преобразует частоту/каналы, copy требует фактической совместимости. FLAC требует явных video/аудио transcode.

| Кодек | Фактический заголовок и AU | fMP4 и Enhanced Audio |
| --- | --- | --- |
| Opus | Head version1/stereo/mapping0/gain0; pre-skip0 либо120; одна CELT frame120 с корректным RFC framing/padding. InputSampleRate advisory, decoder clock48000. | `Opus`/`dOps`, отдельная endian-конверсия; FourCC `Opus`, нормативный19-byte Head little-endian. |
| FLAC | STREAMINFO PCM16/48000/stereo; минимальный корректный encoded number, block size, header/footer CRC. Продолжаемый port48…4608, prepared только4608. | `fLaC`/`dfLa`; FourCC `fLaC`, body42bytes: signature `fLaC` + metadata header `80 00 00 22` + STREAMINFO34. Дополнительные metadata blocks вне начального port. |
| MP3 | MPEG-1 Layer III/48000/128k/stereo либо joint-stereo, full1152, main_data_begin0; unprotected, без free-format/MPEG-2/2.5/mono/dual-channel. Непустой internal descriptor — actual первые4bytes frame header. | `mp4a`/`esds` с OTI0x6B, без AAC ASC/DecoderSpecificInfo; FourCC `.mp3`, пустой SequenceStart body после FourCC. |
| AC-3 | bsid8/acmod2/noLFE/48000/192k, full1536; actual BSI/dac3 согласованы, обе CRC проверяются. | `ac-3`/`dac3`; FourCC `ac-3`, пустой SequenceStart body после FourCC. |

Пустые wire headers MP3/AC-3 и профиль Opus уточняются по ограниченному первому фактическому AU до публикации config. Действуют прежние packet/byte/deadline budgets; retained prefix не теряется сверх прежних правил готовности и среза. Прежний demux не получает безусловного lookahead. Runtime headers остаются непустыми. Standard records и actual AU проверяются и при UUID Metadata1; UUID не заменяет authority заголовков.

Началом Opus владеет source adapter: при pre-skip120 он проверяет и потребляет ровно первую целиком пропускаемую AU120 до любых video-ready/drop gates, затем выдаёт Head0. При skip0 ничего не удаляется. Остальные payload, PTS/DTS и durations сохраняются; положительный origin, смена только видео, resync и reconnect не создают decoder start. Настоящий audio SequenceStart создаёт новую последовательность. FMP4 demux выполняет это один раз до Init/prefix, group не повторяет drop; RTMP source adapter обрабатывает свою границу. Больший skip, multi-frame, другая длительность и partial tail вне привязки. PCM identity холодного lossy-декодера с непрерывным не обещается; общих trim/preroll fields или очередей нет.

Продолжаемый FLAC использует variable strategy со счётчиком сэмплов на физический поток. STREAMINFO имеет min48/max4608, неизвестные frame sizes/totalSamples/MD5, counter0 только при новом физическом потоке. Source switch, resync и повтор headers на исправном соединении счётчик не сбрасывают; новый Publisher начинает собственный поток. Кодируемый номер, рост заголовка, бюджеты и сложение до36-bit предела проверяются до I/O; counter/clock фиксируются после полной записи. Partial write закрывает транспорт. Переполнение возвращает прежнюю ошибку порта, без modulo, авторолловера или нового retry owner.

Публичная FLAC-перенумерация требует `FLACOwned` от доверенного собственного encoder attempt либо выбранного verified artifact. Это не доказательство тишины и не право исправлять subframes. Внешние headers/UUID/JSON и совпадение desired права не дают. Отдельный explicit private input mux для audio transcode клонирует внешний FLAC, переводит headers в variable/unknown и начинает свой counter0, сохраняя subframes/PTS/DTS/actual duration и исходный Packet для других подписчиков. Новая UDS attempt имеет counter0, прежний строгий validator времени не ослабляется. FLAC1…47 вызывает явный failure/cut до publication, без padding или успешного скрытого discard.

Каждый новый processed sample имеет положительную длительность, согласованную с actual frame/block и container. Приоритет trun > tfhd > trex сохраняется, включая явный ноль. Отсутствие поля в ffprobe не означает нулевую fMP4 duration; desired и произвольный TOC не восполняют её. Общий Packet.Validate и прежний AAC не ужесточаются. Узкие `FreshSilentOpus`/`FreshSilentMP3` читают только собственный свежий результат для последующей нормализации: actual полная AU обязательна, raw timing не исправляется внутри demux, arbitrary/file/history/player эти flags не используют. Opus допускает raw0…120, MP3 только1…1152; caller доказывает целевой период и допустимую native форму до пересборки положительных длительностей и проверки.

Raw single-track Enhanced Audio использует types0/1/2 для SequenceStart/CodedFrames/SequenceEnd, один actual AU на coded message. Ошибочные typed Opus endian/FLAC layout и legacy MP3 writer SDK обходятся узко с сохранением единственного reader, causal I/O ошибок, ACK и control messages. Старые legacy/Enhanced AAC/config12 bytes сохраняются. Multi-track, EAC3 и ModEx не добавляются. AMF `audiocodecid` — numeric UI32 FourCC: Opus1332770163, fLaC1716281667, .mp3 778924083, ac-3 1633889587; AAC10 прежний. Rate/channels отражают actual; неизвестные bitrate/depth не выводятся из desired. Один serializer пишет metadata/reset, headers и AU с прежними stale Delivery, общим origin, nearest-ms округлением и commit после полной записи.

Единый компилятор настроек выбирает аудиорецепт отдельно от видеокодировщика без фиктивного AAC-профиля. Собственный Opus — libopus 128k/lowdelay/2,5ms/VBR/FECoff/mapping0; MP3 — libmp3lame 128k/reservoir0/ABRoff; FLAC — native/s16; AC-3 — native 192k. Coupling/rematrix0 AC-3 применяется только к собственной подготовленной тишине. Свежий собственный AAC 7.1 сохраняет ограниченную коррекцию ASC7→12; HDR-подготовка проверяет выбранный MOV/MP4-источник.

Подготовка создаёт собственный `anullsrc`, игнорируя исходный звук. LCM использует AAC1024/Opus120/FLAC4608/MP31152/AC31536, точные микросекунды и предел длительности до процесса. Fresh MP3 доказывает N+1 полных AU и допустимый единственный terminal container tail, удаляет initial AU и размещает N на j×1152 с origin0; это не равенство delay1105 и1152. AC-3 разбирает все6blocks, reuse/exponents/bit allocation/grouped mantissas и доказывает нулевые переданные coefficients; снимает actual dithflags для BAP0 и пересчитывает обе CRC. Hardcoded offsets, almost-zero и доверие только исходному WAV0 недопустимы. Эти corrections не применяются к tone/LIVE/copy или произвольным файлам.

Prepared FLAC остаётся самостоятельным fixed stream полных4608blocks с последовательными номерами от0. FDPlayer использует прежнего Supervisor/FD/UDS, копирует видео и декодирует→кодирует native FLAC/s16 одним потоком на всю attempt; отдельный Go player не вводится. Так counters продолжаются через loops. Все новые файлы и несколько петель должны декодироваться в точное число цифровых нулей; decoder residual при переходе рассматривается отдельно. Failure до publication сохраняет прежний current и прежних владельцев cleanup/holds.

Все эти возможности входят в единую строгую модель без прежних версий. SourceFormat остаётся открытым. MetadataVersion=1, физический контракт генератора, CAS, набор требуемых профилей, атомарная публикация, история, holds и cleanup сохраняют самостоятельные обязанности. Счётчики, доверенное происхождение и начало декодера не сериализуются. Проверки всех данных при запуске, исправление или массовое преобразование, новые настройки/команды/состояния, автоматический rebuild и выбранному кодировщику fallback не добавляются.

## Дорожка, конфигурация и пакет

В `media` определены:

| Тип или операция | Контракт |
| --- | --- |
| `Track` | `TrackVideo = "video"`, `TrackAudio = "audio"`. |
| `TimeBase` | `Numerator`, `Denominator uint32`: секунд на tick; обе части положительны. `Validate() error` и математическое `Equal(TimeBase) bool`, возвращающее `false` для некорректных значений. |
| `CodecConfigInfo` | `Track Track`; `SourceEpoch`, `Revision uint64`; `TimeBase TimeBase`; `Video core.VideoFormat`; `Audio core.AudioFormat`; `HDR HDRMetadata`; `FLACOwned bool`. Активен только формат выбранной дорожки, второй должен быть нулевым; для аудио HDR всегда нулевой. FLACOwned по умолчанию false, true допустим только для audio FLAC с доверенным происхождением. |
| `NewCodecConfig(info CodecConfigInfo, headers []byte) (CodecConfig, error)` | Проверяет описание и непустые headers, копирует байты. Epoch и revision положительны. Кодек выводится из активного формата. |
| `CodecConfig` | Закрытые данные; `Info()` возвращает описание по значению, `Headers()` — копию, `StoredBytes() uint64` — длину headers. `Validate() error` отклоняет нулевое/некорректное значение. |
| `PacketInfo` | `PTS`, `DTS`, `DurationTicks int64`; `Keyframe bool`. |
| `NewPacket(info PacketInfo, config CodecConfig, payload []byte) (Packet, error)` | Принимает корректную неизменяемую config, проверяет описание и непустой payload, копирует payload. |
| `Packet` | `Info()`, `Config()` возвращают значения; `Payload()` — копию. `StoredBytes() uint64` учитывает payload и headers. `Validate() error` отклоняет нулевое/некорректное значение. |

Пакет представляет один сжатый access unit. Его дорожка, формат, epoch, revision и единица времени однозначно определяются config. Отрицательные PTS/DTS допустимы; условия `PTS >= DTS` нет. `DurationTicks >= 0`, ноль означает неизвестную длительность. Аудиопакет не помечается `Keyframe`. Для видео этот признак означает заявленную адаптером пригодность независимого старта; конструктор не проверяет битовый поток.

Нулевые `Packet` и `CodecConfig` не готовы к обработке; их getters безопасны и возвращают нулевые значения/пустые данные. `Validate` и конструкторы возвращают обёрнутые `ErrInvalidPacket`, `ErrInvalidConfig` или `ErrInvalidTimeBase` соответственно. Некорректная config в `NewPacket` распознаётся как `ErrInvalidPacket`; проверка самой config — как `ErrInvalidConfig`. Ошибки вложенных полей могут сохраняться в цепочке, но корневая категория обязательна.

Описание формата связывается с headers в одном неизменяемом значении. Соответствие описания содержимому headers, правильность access unit, настоящая random-access точка и декодируемость проверяются адаптером и интеграцией. Синтетические bytes и успешный конструктор этого не подтверждают.

## Владение памятью и учёт размеров

После конструирования Packet и CodecConfig неизменяемы; их можно передавать по значению и читать совместно. Изменение исходных slices либо результата `Payload()`/`Headers()` не меняет объект или уже переданные копии. Конфигурацию можно разделять между пакетами; байтовые массивы наружу не выдаются. Пулы, заимствованные буферы, refcount и `Release` не вводятся.

Это явная граница копирования: в Go копирование slice само по себе сохраняет общий backing array. Основание — [спецификация Go 1.27.3](https://github.com/golang/go/blob/go1.27.3/doc/go_spec.html#Representation_of_values); доступная локальная документация `bytes.Clone` подтверждает копирование байтов.

`StoredBytes` — логический вес сжатых данных: payload + headers, для одной config — только headers. Общая config консервативно учитывается в каждом пакете. Это не размер heap/RSS. Количество объектов ограничивается отдельно; адаптеры также ограничивают входное описание и отдельные хранилища metadata.

## Поколения источника и временная шкала

Идентичность feed задаётся владельцем входного слота вне Packet. LIVE и FALLBACK имеют независимые текущие состояния; epoch не сравниваются глобально между ними или между группами. Владелец feed назначает `SourceEpoch` при новой инкарнации источника, Override, перезапуске producer либо разрыве входной временной шкалы. Значения не переиспользуются и не переполняются с переходом к нулю.

Обе дорожки одного текущего экземпляра feed принадлежат одной epoch. `Revision` локальна для `(feed, epoch, track)` и меняется при изменении headers, наблюдаемого формата, HDR/ColorConfig metadata или TimeBase. Номера аудио- и видеоревизий могут различаться. Один ключ `(feed, epoch, track, revision)` всегда обозначает одну config. Владелец публикует согласованный снимок текущих A/V-конфигураций; новые данные принимаются только относительно этого снимка. Запоздалые пакеты прежней epoch или прежней текущей revision отбрасываются.

Внутри непрерывного сегмента дорожки DTS не убывает; PTS может менять порядок при перестановке кадров. Конструктор одного пакета не может проверить последовательность. Изменение единиц, сброс и переполнение внешних timestamps обрабатываются на границе адаптера. Обычная петля с непрерывными timestamps не требует новой epoch; обнаруженный сброс при петле требует новой границы непрерывности.

Выходной timeline строится отдельно от входных epoch. Переключение, Override и граница петли сохраняют согласованную A/V-шкалу и композиционное смещение `PTS − DTS`; аудио начинается с согласованного полного access unit. Рескейлинг и offsets реализуются в рабочих адаптерах/Switcher: они обязаны явно определить округление и проверять переполнение до арифметической операции. Signed overflow в Go не вызывает panic, поэтому одного типа `int64` недостаточно для такой проверки.

PTS/DTS не являются временем получения пакета, wall clock либо временем сохраняемого Event. Watchdog использует локальные монотонные часы и прогресс валидных данных обеих дорожек.

## Контейнер и конкретная граница FFmpeg

Для T03 выбран fMP4. NUT не передаёт независимый DTS каждого пакета: локальный контрпример FFmpeg 7.1.5 сохранил payload, но изменил `PTS−DTS` с `12/30` до `2/30` секунды. Успешное декодирование не доказывает сохранение времени.

Go fMP4 передаёт codec headers как полный `av1C`, `avcC`, `hvcC`, VP9 configuration record либо AAC ASC. Полезная нагрузка VP9 record не содержит FullBox; MP4 `vpcC` имеет version 1 и flags 0. Общий обратимый сдвиг origin одинаков для обеих меток обеих дорожек; самостоятельное обнуление каждой дорожки запрещено. Time bases, movie timescale, durations, offsets и диапазоны проверяются до сериализации. Точное представление не заменяется молчаливым округлением. Непредставимое значение даёт явную ошибку.

H.264 и HEVC используют независимые PTS/DTS и signed composition offsets в поддержанном диапазоне. VP9 в выбранной привязке требует PTS=DTS. AV1 ISOBMFF v1.2 определяет sample как temporal unit и запрещает composition-offset fields для AV1. Поэтому AV1 mux не записывает такие поля даже с нулевым значением, а AV1 Packet с различающимися PTS/DTS отклоняет как неподдержанный этой codec binding. Это не сужает общий Packet или Router.

В Enhanced RTMP AV1 имеется единственная wire-метка TU без отдельного composition offset. Контракт входного адаптера представляет её точно в обоих полях Packet как TU transport/presentation schedule, сохраняет порядок TU и проверяет неубывание; wrap/reset получает явную границу либо ошибку. Восстановление отсутствующего исходного encoder DTS не обещается. Hidden frames внутри TU сами по себе не запрещены; single-layer и фактическая random-access пригодность проверяются по bitstream. Допустимые SDR profile/chroma/depth определяются полным профилем, а не одним именем Main. Конкретная версия OBS/encoder подтверждается отдельно в T11.

Проверенный output profile FFmpeg 7.1.5: `delay_moov+default_base_moof+frag_every_frame`, `-min_frag_duration 1`, `-use_editlist 1`, точный общий `-movie_timescale`, `-avoid_negative_ts disabled`; положение `-copyts` и `-fps_mode` определяется командой. Минимальная длительность исключает обнаруженный flush пустого трека, портивший AAC DTS. Значение movie timescale `48000` относится к проверенному 30 FPS/48 kHz fixture, а не ко всем источникам. `empty_moov` и `negative_cts_offsets` не являются универсальными defaults: в проверках они меняли origins/композиционные смещения.

MP4-вход FFmpeg задаётся как `-f mp4 -fflags +ignidx -flags2:a +skip_manual -i async:unix:<path>`; выход остаётся `unix:<path>`. Физический транспорт в обоих направлениях — UDS. В FFmpeg 7.1.5 прямой Unix-вход ошибочно отмечен как seekable: кроме полного прохода до EOF, MOV выполняет обратные чтения заголовков, которые при дробном recv могут потерять исходный буфер. `ignidx` ограничивает предварительное сканирование текущим `mdat`, а `async` сохраняет конечное окно для чтения назад. В проверенной версии это фиксированный FIFO 8 MiB с history до 4 MiB и одним дополнительным потоком FFmpeg; CLI-размеры не настраиваются. Стоимость учитывается на каждый worker, завершение FFmpeg освобождает поток, FIFO и внутренний Unix-сокет. Рабочий FFmpeg должен включать протокол `async`.

Для транспорта полных AAC AU из Go общий обратимый origin не означает, что первые сэмплы нужно отбросить. Однако [MOV FFmpeg 7.1.5](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavformat/mov.c) при пустом `stts` воспринимает положительный `elst.media_time` как AAC `skip_samples`, хотя временные метки отдельно корректирует правильно. Входной аудиодекодер с [настройкой skip_manual](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/decode.c) сохраняет все переданные сэмплы и их знаковые метки, предотвращая потерю короткой дорожки при ненулевом транспортном сдвиге. Он не заменяет обработку начальной задержки нового AAC encoder. Контрольное декодирование полных AU со знаковыми метками также использует явный `skip_manual`; обычное воспроизведение MP4 может намеренно обрезать начало до нуля. Эти результаты имеют разное назначение; пакетные и A/V-ожидания остаются точными.

Проверка через настоящие сокеты с чтениями по 5 и записями по 7 bytes покрывает AV1/AAC → H.264/AAC и H.264/AAC copy, положительные и отрицательные origins; временные метки, extradata и декодируемость сравниваются независимо. Один успешный запуск либо успех через pipe не заменяют полную приёмку сокетной границы.

Конкретный FFmpeg CLI-порт явно отклоняет `PTS<DTS`, недопустимые равные DTS и непредставимые значения до сериализации нарушающего пакета. Общий signed Packet/Router и Go fMP4 сохраняют более широкий контракт. Отрицательные origins и обычные H.264 B-кадры остаются поддержанными. Принятая портом шкала сохраняет обе метки; guessed DTS недопустим. Exit 0 и `-xerror` не заменяют сравнение самих временных меток, поскольку FFmpeg способен переписать DTS лишь с предупреждением.

Framing UDS проверяется дробными чтениями/записями, ограничениями box/sample/extradata до allocation и разрывами соединения. Codec description сверяется с headers/sample entry; неизвестный FPS/цвет не подставляется из профиля группы. Реальная CPU-интеграция проверяет отдельно рациональные PTS/DTS, A/V origins, extradata и декодируемость.

Первичные источники: [FFmpeg n7.1.5 NUT](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavformat/nutenc.c), [MOV muxer](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavformat/movenc.c), [CLI timestamps](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/fftools/ffmpeg_mux.c#L166), [AV1 ISOBMFF v1.2](https://aomediacodec.github.io/av1-isobmff/v1.2.0.html#av1-sample-format), [Enhanced RTMP v2](https://github.com/veovera/enhanced-rtmp/blob/main/docs/enhanced/enhanced-rtmp-v2.md#enhanced-video).

## Ограничения очередей и восстановление потребителя

`QueueLimits` содержит `MaxPackets uint32`, `MaxBytes`, `MaxPacketBytes`, `MaxConfigBytes uint64` и `ResyncTimeout time.Duration`. `Validate() error` требует положительных значений и `MaxConfigBytes <= MaxPacketBytes <= MaxBytes`; ошибка распознаётся как `ErrInvalidQueueLimits`. `MaxPacketBytes` относится к тому же логическому весу payload + headers, что `Packet.StoredBytes`.

Численные defaults здесь не назначаются; их задаёт [конфигурация приложения](application-contracts.md). Значения учитывают размеры пакетов, число потребителей, удерживаемую память и допустимое ожидание; границы проверяются до запуска. Интервалы `time.Duration` выражены в наносекундах. Валидация настроек сама по себе не ограничивает вход: адаптер проверяет размер до чтения/выделения полной копии, очередь проверяет вес и количество при добавлении.

Переполнение или oversized packet затрагивают только данного потребителя. Его устаревший backlog очищается; зависимые кадры отбрасываются, текущие headers сохраняются только в пределах бюджета. Восстановление начинается с актуальной config и следующей пригодной независимой video-точки; аудио до согласованного начала не выпускается. Ожидание ограничено `ResyncTimeout`. Дальнейшие reconnect/окончательный отказ относятся к владельцу потребителя. Router не ждёт медленный Publisher и не отменяет остальные выходы.

## Контракт независимого Publisher

`internal/media/publisher` владеет выполнением одного назначения: подпиской стабильного выходного Router группы, соединением, переподключениями, счётчиками и завершением. `internal/media/rtmp` отвечает за исходящий протокол, TLS и представление сжатых данных. В этих пакетах нет SQL и запуска FFmpeg на назначение. Общим кодированием и переключением источников владеет Group/Switcher; ссылку на группу освобождает вызывающий код отдельно от Publisher.

Запуск разделён на локальную подготовку и сетевую активацию. Вызывающий код выполняет `Claim → MarkIssued → BindExecutionOwner → Prepare → Complete(true) → OpenOutputObserver → Activate`. `Prepare` проверяет точный сохранённый снимок, совместимость назначения, ограничения и эксклюзивность выполнения, не открывая соединений. `Complete(true)` подтверждает подготовленное локальное выполнение. `Activate` получает долгоживущий контекст выхода и точный `OutputObserver`; контекст запроса подготовки не становится временем жизни передачи. Состояние `PUBLISHING` допустимо только после `NetStream.Publish.Start` и полной отправки начальных видео- и аудиопакетов. Оно не подтверждает декодирование или изображение у зрителя.

Отказ подготовки оформляет вызывающий код через `Complete(false)`. Ошибка после успешного `Complete`, до сетевой активации, требует отдельной остановки точного прежнего исполнения. SessionManager использует атомарный `CompensateOutputStart`: проверка fence и принятие stop находятся в одной транзакции, выигравший пользовательский stop и новое исполнение сохраняются. Окончательный отказ работающего Publisher возвращается вызывающему коду для `FailOutput`; сам компонент не закрывает пригодный OutputObserver ради обхода этой операции. Неоднозначный исход управляющей записи разрешается по точным сохранённым данным, без повторного сетевого выполнения. Отдельное удержание и освобождение физического исполнения описаны в [доменном контракте](domain-storage-contracts.md#физическое-выполнение-выхода).

Одна Subscription является единственной очередью назначения. Каждая очистка при переполнении или смене источника/конфигурации меняет непереиспользуемое поколение доставки. `Delivery.IsCurrent` проверяет и это поколение: прежняя выдача становится устаревшей даже при неизменных заголовках. Повторная очистка во время восстановления не продлевает уже начатый `ResyncTimeout`. При новом соединении подписка создаётся после подтверждения публикации и начинает свежую синхронизацию. На исправном соединении смена источника, конфигурации или восстановление очереди повторяет актуальные заголовки перед независимым видеокадром и согласованным AAC, сохраняя соединение и общее начало отсчёта времени. Уже допущенное полное RTMP-сообщение завершается целиком либо соединение отбрасывается при ошибке записи; записанные байты отозвать нельзя.

Временные DNS/TCP/TLS-транспортные ошибки, EOF, сброс и отказ соединения, истечение сетевых сроков повторяются до остановки выхода. Положительная задержка увеличивается экспоненциально с заданным верхним пределом; её сброс требует полной фактической начальной A/V-отправки. Некорректные настройки, неподдержанный формат/протокол, непредставимое время, явный отказ авторизации/публикации и ошибка проверки сертификата окончательны. Ожидания подключения, TLS, общего запуска RTMP и полной записи сообщения ограничены явно. После подтверждения публикации отсутствие входящих управляющих сообщений допустимо; начатое сообщение имеет конечный срок завершения, который фрагменты и чередование сообщений не продлевают. Отмена прерывает сеть и ожидает принадлежащие компоненту операции, включая позднее завершение подключения.

Встроенное назначение принимает `Endpoint` как URL приложения и `StreamKey` как отдельное точное имя AMF-публикации. Сохраняются исходное экранирование пути и строка запроса; ключ не преобразуется в путь. Userinfo и любой разделитель fragment `#` явно отклоняются до сети. Контракт `OutboundResolver` допускает адаптеры площадок без закрытого enum и без подстановки параметров кодирования по имени площадки. RTMPS проверяет цепочку сертификата, hostname и SNI; тестовый центр доверия задаётся явно.

Выходной адаптер использует публичные примитивы закреплённой `gortmplib v1.0.1` и собственное обрамление сообщений: fmt0 в начале, fmt3 для продолжений, little-endian MessageStreamID и повторение расширенной временной метки. Высокоуровневый SDK Writer не используется для преобразования конфигураций и пакетов. Настоящие `av1C`, `avcC`, `hvcC`, VP9 configuration record, ASC и полезная нагрузка AV1 TU/H.264 AVCC/HEVC NAL/VP9 frame/AAC AU передаются побайтно после проверки существующим codec-портом; temporal delimiter не добавляется. Один читатель принимает управляющие сообщения, целые исходящие медиаданные, команды и управляющие ответы сериализуются одним владельцем записи.

Преобразование времени на RTMP-границе задаётся `Q(t)`: точные рациональные миллисекунды округляются до ближайшего целого, половина — от нуля. PTS и DTS округляются независимо; H.264/HEVC composition offset равен `Q(PTS) − Q(DTS)` и проверяется на signed24. Отдельное округление разности, промежуточный float/`time.Duration` и искусственный шаг `+1 ms` не применяются. На новом соединении первый независимый видеокадр задаёт общий `O = min(Q(PTS), Q(DTS))`; обе дорожки используют `Q(t) − O`. AAC, AV1 и VP9 требуют исходного `PTS == DTS`; общий Packet со знаковыми временными метками сохраняет более широкий контракт. Начальный AAC начинается не раньше PTS видео, поэтому дополнительная очередь для выбора начала отсчёта не нужна. Это начало не меняется при восстановлении на исправном соединении. Проверяются неотрицательный транспортный DTS, неубывание каждой дорожки, представимость и однозначность последовательных значений; логическое время хранится без сворачивания, временная метка сетевого сообщения вычисляется явным modulo `2³²`.

Счётчики очереди учитывают потерянные AU до передачи через `Next`, Publisher — оставленные после получения: устаревшие, прерванные сетью, отменой или окончательным отказом. Каждый AU получает одну причину потери; успешно полностью записанный AU позднее потерей не становится. Заголовки и управляющие сообщения не являются AU. Положительный результат `Write n` учитывается и при частичной ошибке; для RTMPS это незашифрованные байты RTMP, принятые `tls.Conn.Write`, а не число байтов NIC или подтверждение получателя. Счётчики полностью отправленных полезных данных, AU и видеокадров растут лишь после полной записи сообщения. При замене подписки её окончательные потери переносятся один раз; согласованный снимок не суммирует одновременно перенесённый итог и прежнюю активную подписку. Накопительные `uint64` насыщаются с явным признаком; идентичности и поколения не насыщаются. Очередь, ожидающее аудио, конфигурации, выданный AU и сетевые буферы имеют отдельный логический учёт; это не heap/RSS/TLS/OS-память. Окна скоростей и сборщики описаны в [контракте мониторинга](monitoring-contracts.md).

### Входящие ACK и достоверность диагностики

Входящие ACK не управляют разрешением отправки. Отсутствие ACK, числовое опережение, дубликат, устаревшее либо неоднозначное значение не закрывают соединение и не вызывают reconnect или `FAILED`. Срок полной TCP/TLS-записи, отмена, очереди и изоляция назначений сохраняются. Адресация, длина и обрамление управляющих сообщений по-прежнему проверяются; собственные ACK по `WindowAcknowledgementSize` и ответы ping продолжают работать. `SetPeerBandwidth` сохраняет правила управляющего ответа для hard/soft/dynamic, но его окно не ограничивает Write. Прежний предел окна `MaxInt32` для разрешения отправки снят.

Диагностика использует единственный локальный `WrittenBytes` конкретного соединения: сумму фактических положительных `Write n` до TLS-шифрования, включая 3073 байта согласования RTMP, обрамление, управляющие сообщения и частичную запись с ошибкой. Потенциально записываемые байты к этому счётчику не прибавляются. Обработчик чтения не ждёт завершения записи ради диагностики и продолжает разбирать управляющий поток.

Для сопоставления `uint32` хранится абсолютная опорная величина `A`, изначально нулевая, и `H=2³¹`. При локальном счётчике `W` условие `W>A && W-A>=H` означает потерю однозначной эпохи до нового соединения. Фактическое переполнение самого `W` также прекращает достоверное сопоставление, сохраняя передачу. Ближайший оборот по локальному счётчику не угадывается.

Пока эпоха известна, разность `d=uint32(raw-uint32(A))` равная нулю обозначает дубликат; `d>=H` игнорируется. При `0<d<H` сумма `X=A+d` принимается только без переполнения и при расстоянии до `W` меньше `H`. Изолированный непредставимый или далёкий ACK не продвигает опорную величину и сам по себе не делает всё соединение неопределённым. Принятый `X` продвигает `A`, в том числе при числовом опережении и во время записи.

Событие опережения создаётся только для нового принятого `X>W`, когда физический `Write` не выполняется; его размер точно равен `X-W`. Каждое такое подтверждение считается отдельно. Во время незавершённого `Write` точный принятый объём неизвестен: метрики не меняются и ACK позднее не переигрывается. Повтор принятого подтверждения также не становится новым событием. Нижняя оценка, основанная на полном размере незавершённой записи, не подставляется вместо размера опережения.

Четыре значения `ack_ahead_events_total`, `ack_ahead_bytes_last`, `ack_ahead_bytes_max`, `ack_last_anomaly_at` описаны в [контракте мониторинга](monitoring-contracts.md#диагностика-опережения-ack). Обработчик чтения синхронно передаёт подтверждённое событие короткому обработчику Publisher после освобождения блокировки транспорта. Обработчик обновляет только локальные RAM-счётчики, без ввода-вывода, обращения к `RuntimeAuthority`, журналирования и повторного входа в соединение. Он установлен до `DialOutbound`, поэтому сохраняет события неудачного согласования и коротких попыток. Опрос снимка не суммирует те же события повторно. Завершение `Wait` предшествует следующей попытке; новое соединение получает собственную опорную величину, накопления Publisher сохраняются до нового запуска выхода.

Это ограниченное правило числовой диагностики, а не доказательство ошибки площадки. Пропущенные наблюдения во время записи и после потери эпохи не означают отсутствия расхождений. Отдельного допуска `+4` и исключений по имени площадки нет. Причина исходного расхождения остаётся неизвестной; результаты локальной приёмки T13 учитываются отдельно от прежней T05 и целевого эфира T11.

Первичные протокольные источники: [RTMP December 2012](https://rtmp.veriskope.com/pdf/rtmp_specification_1.0.pdf), [авторские уточнения RTMP](https://zenomt.github.io/rtmp-errata-addenda/rtmp-errata-addenda.html), [Enhanced RTMP v2](https://veovera.org/docs/enhanced/enhanced-rtmp-v2.html). Независимая локальная проверка прежней отправки описана в [результате приёмки](#результат-локальной-приёмки-отправки).

## Watchdog и условия LIVE/fallback

`core.WatchdogPolicy` содержит положительные `VideoTimeout`, `AudioTimeout`, `RecoveryWindow`, `KeyframeTimeout time.Duration`. `media.WatchdogPolicy` остаётся псевдонимом типа; обе прежние категории ссылаются на одну ошибку для `errors.Is`. `Validate() error` возвращает категорию `ErrInvalidWatchdogPolicy`. Порядок соотношений этих интервалов и значения по умолчанию не навязываются без проверки компонента.

Предварительные условия допуска источника: обе обязательные дорожки, подтверждённое адаптером соответствие выходному формату группы, актуальные headers, пригодная точка независимого старта и согласуемая временная шкала. Побайтовое равенство headers независимых кодирований не требуется. Равенство заявленных MediaFormat не доказывает пригодности: codec-aware проверка и интеграционные результаты принадлежат T03/T04. Пока пригодность неизвестна, группа остаётся на пригодном fallback.

| Событие | Поведение группы и Switcher |
| --- | --- |
| До первого OBS | Подготовленный и проверенный fallback; выходной профиль `copy` уже известен. |
| Пропала любая обязательная дорожка либо данные перестали продвигаться | Fallback соответствующей группы. Headers, дубликаты и открытое соединение не восстанавливают здоровье. |
| Источник восстановился | Обе дорожки здоровы непрерывно в течение `RecoveryWindow`; затем требуется актуальная пригодная video-точка в пределах `KeyframeTimeout`. Нарушение сбрасывает стабилизацию. |
| Изменилась metadata/config | Новая revision, повторная проверка пригодности и точки синхронизации; старые queued packets исключаются. |
| Несовместимый LIVE | Профиль и исправные выходы сохраняются; источник не становится LIVE. |
| Ручная пауза | Fallback сохраняется независимо от продолжающегося OBS. |
| Override | Старый вход OBS заменён после проверки ключа Stream и активной Session; группы, fallback и исправные Publishers сохраняются. |
| Отказ fallback без пригодного LIVE | Явное отсутствие подачи и причина ошибки; успешная передача не объявляется. |

Переход режима сам по себе не закрывает исправные исходящие соединения. Постоянство соединений проверяется на настоящих локальных RTMP/RTMPS-границах в T05; сохранение картинки/звука у зрителя — отдельно в T11.

## Группы и подготовленные файлы

`internal/media/group.Registry` принадлежит выданному владельцу Session. Ключ группы включает точное разрешение родительской Session, настроенный `GroupID`, полный канонический профиль, точный manifest поколения/варианта и правила fallback. Выходы с одинаковым снимком разделяют Router и результат кодирования; разные настроенные группы или профили получают независимых работников. Выход держит ссылку, общие ресурсы принадлежат Session. Последняя ссылка отзывает группу и ждёт полного завершения; запись об останавливающейся группе запрещает параллельную замену до join. Чисто завершённая группа освобождает бюджет и для другого ключа; неподтверждённая или ошибочная очистка сохраняет блокировку.

У группы стабильный выходной Router, отдельные источники LIVE/fallback и Switcher с ограниченными очередями. Терминальная LIVE-подписка после длительного отсутствия OBS переподключается с конечной задержкой, сохраняя группу и fallback. Override заменяет только входную попытку и зависимый transcode worker. `copy` не запускает кодировщик. Группа наблюдает `DesiredPaused`, а потеря пригодного fallback при отсутствии LIVE означает явное отсутствие подачи с причиной.

`Group.Ready` и `WaitReady(ctx)` проверяют пригодность текущей fallback-попытки: обе дорожки, подтверждённую независимую video-точку и условия A/V/timing Switcher. Старый успех, process/UDS и выбранный LIVE этого доказательства не заменяют. Новая попытка, EOF, отказ или просроченная дорожка отзывают готовность. Registry применяет desired-control с монотонной ревизией; новая группа получает актуальное желание, старый poll не откатывает его.

Проигрыватель использует отдельную топологию Supervisor: независимо открытый обычный файл, проверенный по размеру/хешу, передаётся через FD в FFmpeg, затем через выходной UDS/fMP4 в Go. Команда FFmpeg 7.1.5 использует `-fd 3 -i fd:`, `-stream_loop -1`, `-re`, `-c copy`. Дескрипторы принадлежат попытке до её полного завершения; `dup` общего reader не подменяет независимое открытие с позицией 0. Дополнительная предварительная проверка ffprobe при запуске проигрывателя не выполняется. Новый FLAC binding копирует видео и непрерывно перекодирует аудио одним native encoder на всю попытку; прежние команды сохраняют `-c copy`.

Подготовка использует anullsrc с параметрами выбранного AAC/Opus/FLAC/MP3/AC-3, игнорируя исходный звук. Контракт генератора — fallback-fmp4-silent-v2; пригодность полного профиля, фактического формата и генератора проверяется до привязки/повторного использования и каждого открытия файла. Новый комплект готовится явно до эфира без подмены закреплённых снимков. Файл и петли содержат цифровую тишину; остаток декодера после LIVE рассматривается отдельно без универсальной длительности.

Проверки полного профиля, канонических байтов/ключа, фактического формата и генератора обязательны до binding, получения группы и OpenVerified, включая повторное открытие проигрывателя. Совпадающий исходный формат не доказывает полный рецепт.

Switcher сериализует пакеты и управляющие события, учитывает монотонный прогресс обеих дорожек и собственные выходные epoch/revisions. Задержанное событие не переводит часы проверки назад. Новый сегмент начинается с действительной точки независимого старта и полного audio AU выбранной привязки; один точный рациональный сдвиг обеих дорожек сохраняет `PTS−DTS` и исходное A/V-смещение. Границы декодирования и максимальная уже опубликованная presentation-метка сохраняются между источниками и попытками. Неизвестная длительность требует ограниченного lookahead; хвост не получает выдуманное значение. Непредставимый пересчёт времени, переполнение, несовместимый кодек и невозможный переход отклоняются явно. `MaxAVSkew` и `MaxTransitionGap` задаются вызывающим; нулевой разрыв при переходе не обещается.

Подготовка ограничивает загрузку/результат, ffprobe/заголовки/диагностику, размеры/длительность, очередь и сроки. Кодировщик выбирается явно из матрицы API. SVT CBR требует max=target и точного буфера 20…10000 мс, high tier сужает его до 1000 мс; VBR требует max=buffer=0. VBR использует rc1/random-access/hierarchical0, CBR —rc2/low-delay, native mbr0. CQP/CRF используют rc0 с явным качеством и AQ без ограничений битрейта. Внутренние prediction/overlays/DG/TF/SCD закрыты для custom. Неизвестный источник не подменяется желаемым форматом; узкая подготовка SDR-изображений описана отдельно. Аппаратный NVENC проверяется в целевой среде.

EffectiveLoopDuration сохраняет исходную длительность и вычисляет петлю округлением вверх до общей сетки полных видеокадров, audio AU и точных микросекунд CLI. Кванты AAC — 1024, Opus — 120, FLAC — 4608, MP3 — 1152, AC-3 — 1536 сэмплов. Tpad повторяет последний кадр, apad добавляет тишину, -t задаёт точный период. При 30 FPS/48 kHz одна секунда с AAC становится 1,6 с: 48 кадров/75 AU. MaxDuration проверяется после округления до запуска; непредставимая или слишком большая сетка отклоняется.

AAC-путь NormalizePrepared обрабатывает только собственный свежий результат Manager. Фактические метаданные ffprobe и каждая AU fMP4 сверяются. Удаляется только целая первая AU с Skip Samples=1024, discard_padding=0, подтверждённой длительностью и концом в нуле. Остальные payload/PTS/DTS/duration сохраняются. AV1-заголовок берётся из первого независимого TU. При отрицательном H.264 decode origin используется один общий точно представимый сдвиг OriginMapping и согласованная edit list, без произвольного секундного сдвига. Затем проверяются полные дорожки, непрерывный период и точная длина. Контекст AAC влияет на первые декодированные сэмплы; неизменность PCM после удаления priming не обещается.

Подготовленный файл имеет presentation origin 0. Пусть `F=FPS.den/FPS.num`, `A=1024/sample_rate`, `T=N·F=M·A`. Сохраняемый AAC имеет `PTS=DTS=j·A`, H.264 в неизменном decode order — `DTS=d0+i·F`, где `d0≤0`, а его PTS образуют точную перестановку кадров от 0 до `N−1`. Первый видеокадр — подтверждённый IDR с PTS 0. Presentation-покрытие обеих дорожек равно `[0,T)`; decode-интервалы имеют одинаковую длину, но их абсолютные концы при B-кадрах различаются. Signed CTS сохраняется; сортировка payload по PTS, замена PTS на DTS и принудительное отключение B-кадров не выполняются.

Общий контейнерный сдвиг не меньше `−d0` и точно представим в обеих шкалах. Для шкал `1/tv` и `1/ta` он выбирается на сетке `1/gcd(tv,ta)` с проверкой переполнения; одного `S=−d0` при рациональном FPS может быть недостаточно. Повтор k добавляет ровно `k·T` к обеим дорожкам, без priming или decode lead в периоде. AV1 сохраняет PTS=DTS. Неподтверждённый/частичный padding, разрывы/дубликаты presentation coverage, переставленные decode DTS и непредставимые смещения отклоняются. Общие fMP4/Switcher и существующие A/V-бюджеты не ослабляются. Дополнительный нормализованный staging заранее регистрируется; исходный и нормализованный файлы каждый ограничены `MaxOutputBytes`, поэтому временно требуется до двух таких бюджетов на вариант. После проверки исходный staging удаляется с барьером долговечности.

Пригодность H.264 с B-кадрами зависит также от действующего `MaxTransitionGap`: задержка декодирования не получает дополнительного бюджета автоматически. Например, две кадровые длительности при `25/2` FPS равны 160 мс и не помещаются в бюджет 100 мс. Сохранённый профиль не означает готовность конкретной группы; проверка её фактической готовности остаётся обязательной.

Пакетная проверка подготовки отключает синтетическое заполнение временных полей ffprobe через `+nofillin`. При отсутствующей duration видео ожидаемый шаг сетки затем обязательно сравнивается с настоящей duration каждой единицы доступа fMP4; для AAC сохраняется доказательство полной AU. Выдуманное ffprobe значение не подменяет содержимое файла, а отсутствие или расхождение duration в самом fMP4 остаётся ошибкой.

Шкала подготовленного видео сохраняет сокращённый числитель FPS N при N≥1000, иначе использует уже вычисленный movie timescale — LCM числителя и частоты аудио. Шаг кадра должен быть положительным, точным и не больше INT_MAX; проверяется до сохранения и перед процессом. Точная шкала исключает подтверждённую ветку FFmpeg 7.1.5, которая при CTTS/грубой шкале подставляет 1 tick вместо длительности кадра. Безусловное увеличение достаточной шкалы не применяется.

FilePlayer сохраняет обычное копирование сжатых AU для прежних привязок; исключение нового FLAC описано отдельно. `noparse` не гарантирует сохранность временных меток, а `nofillin` лишает native loop нужных длительностей и нарушает период; эти флаги не используются как исправление проигрывателя. Проверка проходит по настоящим `tfdt/trun` через Go demux для каждой AU: один средний FPS, общая длительность или вывод ffprobe могут скрыть повреждение границ фрагментов.

AAC-проверка разбирает полный ограниченный ASC/PCE, частоту, LC/1024 и карту элементов/каналов, а также обязательный префикс SCE/CPE/LFE, длины предшествующих FIL/DSE, ICS и запрещённые поля. Простой блок без спектральных полос и инструментов проверяется до настоящего `ID_END`. Границу и длительность AU предоставляет адаптер; спектральный Huffman-поток целиком не декодируется этой проверкой. Это не обещание обнаружить любое повреждение битового потока. Декодируемость рабочих источников подтверждается отдельно реальным FFmpeg; одного конструктора пакета или поиска завершающих битов недостаточно.

Нормативный ASC configuration 7 — 7.1(wide-back), configuration 12 — обычный 7.1; допускается соответствующий полный PCE. В FFmpeg 7.1.5 forced PCE для 7.1 ошибочен, поэтому собственный кодировщик использует -aac_pce 0. Только свежий собственный native AAC при подготовке либо явном LIVE transcode с полным профилем допускает проверенную коррекцию ASC7→12 до строгого fMP4 ResolveConfig. Меняются четыре бита configuration; AU/PTS/DTS/duration сохраняются, ASC повторно разбирается. Нормативные 12/PCE не меняются; приём, LIVE copy и готовый файл не исправляются.

Pinned SDK не разбирает configuration 12. Узкий RTMP bridge сохраняет единственный SDK reader, ACK, управляющие ответы и исходные сетевые байты. Он восстанавливает реальный descriptor 12/8 только после точной ASC-ошибки и новой полностью выданной текущей конфигурации, подтверждённой общим parser; частичное/устаревшее сообщение и причинные ошибки Read/Write/ACK/deadline не маскируются. Повторная сериализация descriptor через pinned Marshal запрещена: она вернула бы configuration 7. Многоканальный выход использует Enhanced Audio `mp4a`. Декодирование этой RTMP-формы напрямую FFmpeg 7.1.5 не поддерживает; проверка PCM через замену одной лишь FLV-оболочки с сохранением ASC/AU/времени не подтверждает совместимость конкретного получателя.

## Тестовые данные и измеримые критерии

Unit-тесты находятся рядом с пакетами. Маленькие синтетические наборы в `internal/media/testdata/` имеют описание происхождения и заранее заданные ожидаемые свойства: дорожки, конфигурации, epoch/revision, единицы, timestamps, ключевые кадры и логические размеры. Они создаются для структурных проверок; payload/headers явно условные и не заявляются декодируемыми. Файлы прежнего GPU-замера не используются.

Исполняемая основа проверяется положительными, отрицательными и граничными сценариями валидации, математического равенства дробей/профилей и отсутствия aliasing. Отрицательные PTS/DTS и перестановка PTS допустимы. Числа в небольших fixtures — тестовые входы, а не эксплуатационные defaults или SLO.

| Проверка | Измеряемый результат и ожидаемое свойство | Контракт и граница приёмки |
| --- | --- | --- |
| Преобразование timestamps | DTS отдельно по дорожке, PTS/DTS и `PTS − DTS` в точной time base; явный результат округления, отсутствие молчаливого overflow. | T03: известные входы и единицы реального адаптера. |
| Преобразование разрешения/FPS | Наблюдаемые размеры и рациональный FPS, длительности кадров, выходные PTS/DTS и A/V-согласование; независимые ожидаемые значения. | T12: контракт преобразования и CPU-интеграция; T04: профили LIVE/fallback; T11: NVDEC/NVENC. |
| A/V и переходы | Междорожечный сдвиг, gap/overlap, длительность перехода по монотонным часам; согласованный cut-point и независимая точка старта. | T04/T05: подготовленные источники и действующие настройки до прогона. |
| Очередь и resync | Вес, число элементов, oversized packets, срок ожидания и продвижение исправных потребителей. | T03/T05: действующие бюджеты и контролируемый медленный потребитель. |
| Локальный медиатракт | Настоящие ingest/UDS/Publisher, metadata и временная шкала; декодируемость отдельно короткой CPU-интеграцией FFmpeg. | T03–T05; FFmpeg не требуется обязательному CI. |
| Целевой эфир | Фактическое воспроизведение, A/V, переходы, GPU и длительная устойчивость. | T11: разрешённая целевая среда и заранее согласованные критерии. |

Unit-проверки этих значений не подтверждают runtime-очередь, авторизацию публикаций OBS, декодируемость, отсутствие артефактов AV1-переключения или аппаратную/live-совместимость. Обязательный `make check` включает форматирование, модули, vet, lint, тесты с порогом покрытия 85%, race и сборку. Каждая приёмка относится к своему стабильному снимку исходников, fixtures и значимой конфигурации.

Проверены fallback до LIVE, возвраты, пауза, Override, отказ работника, медленный TCP-выход, переполнение и reconnect при постоянстве здоровых соединений.

Отдельные короткие CPU-сценарии 128×128/60 проводят настоящее AV1/H.264/AAC через ingest→Group/Switcher, FFmpeg/UDS и нативные RTMP/RTMPS-выходы. Независимый FLV, ffprobe и framemd5 подтверждают декодирование и число AU, а подписка выходного Router группы — соответствие каждой метки точному `Q(t)−O` при одном origin. Счётчики сравниваются с принятыми байтами и полными медиасообщениями после EOF получателя. Выполнены и прежние CPU-регрессии fallback/fMP4; аппаратные проверки этим запуском не подменяются.

Независимые граничные проверки покрывают little-endian, расширенные временные метки и фрагментацию, дробные/частичные записи, округление и CTS/signed24/сворачивание меток, строгую проверку ответов/URL/ключа/TLS, отсутствие управляющего трафика и сроки частичных сообщений, фактическое завершение и изоляцию. ACK-нумерация обеих сторон включает 3073 байта согласования RTMP; это сверено с созданием счётчиков закреплённой библиотеки до согласования и отдельным принимающим эталоном. AV1 `videocodecid` в метаданных — числовой FOURCC `0x61763031`. Отдельная регрессия публичных API проверяет отказ observer/Activate после успешного Complete и компенсацию вызывающим кодом без единой попытки подключения.

Конкретный исходящий порт ограничен 8-bit yuv420p SDR BT.709 и AAC-LC mono/stereo, фактическими форматами существующего codec-порта. Непустые `Endpoint`/`StreamKey` ограничены 65535 байтами, сообщения/блоки — 10 MiB, одновременные потоки блоков — 62 при поддержке полных CSID, глубина AMF — 64, очередь управляющих ответов — 65536 сообщений, окно отправленных, но пока не подтверждённых байтов — MaxInt32. Рабочие значения всех бюджетов и сроков задаются явно; эти верхние границы не являются значениями по умолчанию. Userinfo/fragment и Adobe challenge authentication не поддержаны. Сохраняемые снимки не переписываются ради совместимости.

Указанное здесь ограничение неподтверждённых байтов окном `MaxInt32` относится к принятому прежнему снимку T05. Текущий [контракт обработки ACK](#входящие-ack-и-достоверность-диагностики) снимает зависимость отправки от этого окна; прежние проверки не являются приёмкой нового поведения.

Схема и зависимости не менялись. Этот результат подтверждает рабочие компоненты на macOS/arm64 и короткие CPU-границы. NVIDIA, Debian, реальные OBS/площадки, полноценное высокоразрешающее декодирование и длительная устойчивость не входили в эту локальную приёмку. SessionManager, сборщики, REST/SSE и исполняемый сервис приняты позднее в своих областях; результаты основного прогона VM и оставшиеся границы описаны в [целевой приёмке](#target-acceptance).
