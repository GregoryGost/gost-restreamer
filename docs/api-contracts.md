# Управляющий HTTP API

Документ описывает публичный контракт API. Результаты проверки реализации приведены отдельно в конце документа. Сборка исполняемого сервиса и подключение общих зависимостей принадлежат composition root.

## Доступ и представление данных

Все маршруты имеют префикс `/api/v1`. REST, SSE, OpenAPI, документация, схемы и health доступны без авторизации и токенов доступа в личном локальном контуре владельца. Отдельный приём OBS проверяет постоянный ключ Stream и готовую Session; управляющий API этот допуск не заменяет.

HTTP DTO отделены от доменных и ORM-представлений. Ключ публикации Stream принимается при создании и затем не редактируется. Ключ назначения и **весь** Endpoint принимаются только на запись: URL может содержать секрет в любом компоненте. GET, SSE и ошибки не возвращают эти значения, файловые пути, внутренние fences/tokens, identity команд и исходную диагностику. Исторические разрешённые сведения берутся из сохранённых снимков запуска, независимо от удаления текущих настроек.

Полные диагностические значения в выбранных локальных событиях журнала сохраняют режим `full`. Эта политика не переносится на публичные HTTP-ответы.

Идентификаторы непрозрачны для клиента. Все 64-битные целые, включая ревизии, байты и счётчики, передаются десятичными JSON-строками. Длительности выражены точными наносекундами в строках; небольшие целые остаются JSON numbers. FPS сохраняет исходные `numerator` и `denominator`. Время представлено в UTC; отсутствующее время — `null`.

Строковые байты полного профиля представлены локальным `ProfileText`: обычное UTF-8 значение — JSON-строка, непредставимые в UTF-8 байты — объект следующего вида:

```json
{"encoding":"base64","value":"/w=="}
```

Это сохраняет существующий точный профиль без нормализации и потери байтов. Весь профиль при редактировании заменяется целиком; произвольного рекурсивного слияния его полей нет.

## Полный профиль кодирования

Настройки назначения задаются через его `TranscodeGroup` и выбранный `TranscodeProfile`. Два назначения одной группы используют один результат кодирования. Для разных полных настроек создаются отдельные профили и группы; название площадки не выбирает параметры автоматически.

`profile` содержит `mode`, `format`, `video_encoding`, `audio_encoding`, независимый `live_audio_mode` и блок `encoding` с `version: 2`.

`mode` выбирает обработку видео. `live_audio_mode` принимает `copy` либо `transcode`: при создании профиля отсутствие поля означает `copy`, в том числе при отсутствующем/null `encoding` и при `encoding.version: 2`. Сервер материализует выбор при создании и возвращает его в GET. Явные `null`, пустая строка и неизвестное значение отклоняются. Для видео `mode: "copy"` допускается только копирование LIVE-аудио.

При `live_audio_mode: "copy"` соответствующие переданные AAC-пакеты OBS сохраняются без повторного сжатия, изменения частоты, каналов и битрейта. Действующие правила среза, синхронизации и отбрасывания устаревших пакетов сохраняются. Фактический поддержанный AAC должен совпадать с `format.audio`; несовместимый LIVE не допускается в эту группу, пригодный fallback продолжает работать, причина доступна в журнале. Перехода к перекодированию без явного выбора нет.

Настройки `audio_encoding`, `encoding.audio_encoder` и `encoding.audio_custom` всегда задают кодирование тишины заглушки. При LIVE `transcode` они задают также его AAC-кодирование. При LIVE `copy` они не меняют звук OBS и не ограничивают его фактический битрейт; `format.audio` остаётся ожидаемым совместимым форматом.

У сохранённых прежних профилей поле отсутствует: видео `copy` сохраняет AAC, видео `transcode` сохраняет прежнее перекодирование. Чтение и PATCH только имени не включают новое поведение. Полная замена прежнего профиля без поля сохраняет прежнюю обработку; явное поле включает новый контракт. После этого каждая полная замена `profile` требует явного `live_audio_mode`, чтобы не удалить его при работе старого клиента. Совместимое чтение профилей v1/v2, истории и манифестов не переписывает их байты и ключи. Версия 3 сохраняемого профиля независима от `encoding.version: 2` и не является дополнительным полем HTTP-запроса.

| Поле | Значения и действие |
| --- | --- |
| `video_encoder` | Обязательный `h264_nvenc` для H.264 `transcode` либо `libsvtav1` для AV1-заглушки группы `copy`. |
| `audio_encoder` | `aac`, значение по умолчанию — `aac`. |
| `rate_control` | Обязательный `cbr` либо `vbr`. Равные битрейты сами по себе не выбирают CBR. |
| `rescale_output` | Разрешение масштабирования LIVE в размеры `format.video`; по умолчанию `true` для `transcode`, `false` для `copy`. При `false` размеры входа и выхода `transcode` должны совпадать. FPS задаётся независимо. |
| `video_custom`, `audio_custom` | Дополнительные параметры выбранного кодировщика; по умолчанию пустые строки. |
| `nvenc`, `svt_av1` | Только применимый блок настроек выбранного видеокодировщика. |

В новом объекте обязательны `version`, `video_encoder` и `rate_control`. Остальные новые поля получают документированные значения по умолчанию один раз при создании или полной замене. GET возвращает полный материализованный блок с применимыми настройками. Отсутствие поля отличается от явно заданных `false`, `0` и `-1`; `null` внутри нового блока запрещён. Неприменимый блок кодировщика передавать нельзя, даже пустым объектом.

Прежний видеорецепт возвращается с `encoding: null`, без приписанных значений неизвестных настроек драйвера. POST без `encoding` или с `null` сохраняет этот видеорецепт, но новый профиль получает `live_audio_mode: "copy"`. Для перехода к расширенным видеонастройкам передайте полный `profile` с явным блоком версии 2. PATCH только имени не меняет режим или идентичность профиля. Полная замена уже обновлённого профиля не может удалить блок версии 2. Переключение обратно на VBR выполняется явным `rate_control: "vbr"`.

| Настройка `nvenc` | Диапазон | По умолчанию |
| --- | --- | --- |
| `preset` | `p1`…`p7` | `p4` |
| `tuning` | `hq`, `ll`, `ull` | `hq` |
| `multipass` | `disabled`, `qres`, `fullres` | `disabled` |
| `lookahead_frames` | 0…31; положительное значение плюс `max_b_frames` не больше 31 | 0 |
| `enable_spatial_aq`, `enable_temporal_aq` | bool | `false` |
| `aq_strength` | 1…15; при `enable_spatial_aq: false` только 8 | 8 |

Нулевой NVENC lookahead оставляет выбор native preset; это не обещание выключенного анализа. AQ `false` не включает функцию дополнительно к preset и не гарантирует очистку его внутренних флагов. Сохранённые поля описывают запрос кодировщику, а не измеренное состояние GPU.

| Настройка `svt_av1` | Диапазон | По умолчанию |
| --- | --- | --- |
| `preset` | 0…13 | 8 |
| `tuning` | `psnr`, `vq`; CBR допускает только `psnr` | `psnr` |
| `aq_mode` | 2 | 2 |
| `lookahead_frames` | Для CBR только 0; для VBR `-1` (native auto) либо 6…120 | CBR: 0; VBR: `-1` |

SVT VBR lookahead 0…5 отклоняется: выбранный native режим способен принудительно изменить такой запрос. Внутреннее планирование mini-GOP остаётся квантованным; положительное поле задаёт native запрос дистанции анализа. Параметры NVENC не переносятся на SVT автоматически.

Набор настроек сверён с FFmpeg 7.1.5 и SVT-AV1 4.3.0. Фактические версии, возможности NVIDIA и применимость параметров целевого сервера проверяются отдельно при аппаратной приёмке; успешное сохранение профиля их не измеряет.

Битрейты и буфер остаются точными десятичными строками. Для H.264: `1 ≤ target_bitrate_bps ≤ max_bitrate_bps ≤ 4294967295`, `buffer_bits` от 1 до 2147483647; CBR требует равных битрейтов. Для AV1 target от 1 до 100000000; CBR требует `max = target` и буфер, точно соответствующий целым 20…10000 мс. AV1 VBR требует `max_bitrate_bps: "0"` и `buffer_bits: "0"`: эти значения явно обозначают отсутствие неподдерживаемого ограничения, а ненулевой запрос отклоняется.

Новые профили используют чётные размеры, yuv420p/8-bit SDR BT.709 и закрытый GOP. H.264 имеет размеры не больше 65534, GOP от 1 до 2147483647, B-кадры 0…4 и меньше GOP; baseline требует 0. AV1 имеет размеры 64…16384 × 64…8704, FPS не выше 240, GOP от 2 до 2147483647 и B-кадры 0. AAC — LC mono/stereo с согласованным layout; частоты 7350, 8000, 11025, 12000, 16000, 22050, 24000, 32000, 44100, 48000, 64000 Гц; положительный битрейт не выше `6 × sample_rate_hz × channels`. Дополнительно действуют проверки точной представимости FPS и контейнера. Аппаратная исполнимость проверяется при запуске кодировщика.

Фактическая готовность группы проверяется отдельно. В частности, задержка H.264 при B-кадрах должна укладываться в настроенный `MaxTransitionGap`; снижение FPS не увеличивает этот бюджет автоматически. Сохранение профиля не подтверждает готовность файлов, GPU или группы к эфиру.

Custom имеет вид `name=value name=value`: разделитель — ASCII-пробел, без кавычек, экранирования, управляющих символов и вложенных списков. На строку допускается до 4096 байт и 32 пар, имя до 64 байт, значение до 128. Поддержаны NVENC `nonref_p=0|1`, `strict_gop=0|1`; SVT `lp=0…6`; AAC `aac_coder=twoloop|fast`. `lp=0` означает native выбор уровня параллелизма. Нулевые NVENC custom-флаги также не гарантируют очистку preset. Пары сортируются, числа нормализуются; GET возвращает сохранённую нормализованную строку.

Дубликат, неизвестная опция и конфликт с обычным полем или внутренним рецептом отклоняются. Например, `rc=vbr` в custom конфликтует с полем режима независимо от совпадения значений. Ответ `422` содержит доверенные код, путь поля и понятное объяснение; произвольные значения запроса и диагностика FFmpeg в него не включаются.

Для `copy` до подготовки заглушки вручную задаются ожидаемые выходные формат, CBR/VBR и битрейты OBS. `libsvtav1` и его дополнительные поля описывают серверную подготовку заглушки, а не encoder игрового ПК. `rescale_output` остаётся `false`: сервер не меняет копируемый LIVE. Сам asset заглушки всегда приводится к выходным размерам. [Примеры JSON для Postman](obs-client-guide.md#профили-кодирования-в-postman) показывают создание и изменение профиля.

Изменение полного профиля, включая `live_audio_mode`, требует новых подходящих fallback-вариантов до эфира. Текущие Session/Output используют прежние самостоятельные снимки; горячей перенастройки нет. Совместимое чтение старых данных не означает поддержку запуска старого бинарника после сохранения профилей версии 3.

## Маршруты

Пути в таблице указаны без общего префикса.

| Область | Операции |
| --- | --- |
| Streams | `GET/POST /streams`, `GET/PATCH/DELETE /streams/{id}` |
| Связи и история Stream | `GET /streams/{id}/destinations`, `GET /streams/{id}/sessions` |
| Профили, группы, назначения | `GET/POST` коллекции и `GET/PATCH/DELETE` элемента для `/transcode-profiles`, `/transcode-groups`, `/destinations` |
| Запуск | `POST /streams/{id}/start` |
| История Session | `GET /sessions`, `GET /sessions/{id}` |
| Управление Session | `POST /sessions/{id}/stop`, `/pause`, `/resume` |
| Выходы Session | `GET/POST /sessions/{id}/outputs`, `GET /sessions/{id}/outputs/{outputId}` |
| Управление выходом | `POST /sessions/{id}/outputs/{outputId}/start`, `/stop`, `/detach` |
| Результат команды | `GET /commands/{commandId}` |
| Текущие измерения | `GET /sessions/{id}/metrics` |
| Заглушки | `GET/POST /fallback-assets`, `GET/DELETE /fallback-assets/{id}` |
| Содержимое заглушки | `PUT /fallback-assets/{id}/content` |
| Подготовка | `POST /fallback-assets/{id}/rebuild`, `GET /fallback-assets/{id}/generations/{generationId}` |
| Варианты | `GET /fallback-assets/{id}/variants` |
| Политика Stream | `GET/PUT /streams/{id}/fallback-policy` |
| Текущий общий снимок | `GET /events/snapshot` |
| Изменения | `GET /events` — SSE |
| Возможности и здоровье | `GET /system/capabilities`, `/health/live`, `/health/ready` |

Вложенный ресурс проверяется относительно указанного родителя. Выход другой Session или поколение другой заглушки даёт `404`, без выполнения команды над чужим объектом. Маршрута `/sessions/{id}/events` и долговечной истории телеметрии нет.

## Редактирование и списки

Изменения и удаления требуют `expected_revision`: десятичную строку в JSON PATCH, PUT политики и rebuild; одноимённый query parameter при DELETE и PUT содержимого. Несовпадающая ревизия даёт `409`. Чтение текущей сущности перед изменением не заменяет атомарную проверку ревизии.

PATCH различает отсутствующее поле, `null`, `false` и пустую строку. Отсутствие сохраняет значение, переданные `false` и `""` применяются. `null` допускается только для явно nullable полей; политика fallback может быть явно очищена. Обычное редактирование действует со следующего запуска, текущая Session использует свой самостоятельный снимок.

Списки ограничены `limit` от 1 до 499 и имеют `cursor`. Порядок возрастающий по `(created_at, id)`; диапазоны дат имеют границы `[from, to)`. Курсор связан с видом списка и фильтрами. Применимые фильтры объявлены в OpenAPI; неподдерживаемый фильтр не означает молчаливое чтение всех объектов. Наблюдаемое состояние Output не хранится в SQL, поэтому фильтр `state` для сохраняемого списка выходов не поддерживается.

Пагинация не обещает неизменяемого набора при изменении состояния объектов между запросами.

## Команды и действующий эфир

Команды принимают пользовательский `request_id`. После долговечного принятия сервер возвращает `202 Accepted`, безопасную квитанцию и `Location` точного результата `/api/v1/commands/{commandId}`. Этот ответ подтверждает принятие, а не завершение операции. GET квитанции работает независимо от SSE.

Повтор того же смыслового запроса с тем же `request_id` возвращает прежнюю квитанцию, включая терминальный результат. Другой запрос с тем же идентификатором конфликтует. Изменение конфигурации или возможностей после принятия не превращает повтор в новый запуск.

При старте пустой список выбранных назначений использует включённые назначения текущего Stream по существующему доменному контракту. Backend самостоятельно выбирает и проверяет закрепляемые варианты; клиент не передаёт внутренние bindings.

Действия над текущим выходом различаются:

- `POST` коллекции выходов явно подключает назначение с новым снимком.
- `stop` останавливает выход, сохраняя его прикрепление и возможность повторного запуска с прежним снимком.
- `start` повторно запускает прикреплённый выход с его закреплёнными настройками.
- `detach` отсоединяет выход и прекращает возможность запуска старого выхода; зависимости освобождаются после подтверждённой очистки.

Эти действия не пересоздают исправные соседние соединения. Отсутствие возможности создать новый FFmpeg worker само по себе не запрещает присоединение к уже работающей общей группе. Проверки ресурсов и выполнение принадлежат существующим владельцам операций; отдельного общего HTTP-запрета медиакоманд нет.

## Загрузка, замена и rebuild

Создание и передача разделены:

1. `POST /fallback-assets` с JSON создаёт именованный Asset и возвращает `201`. Его ID можно использовать при настройке политики и групп.
2. `PUT /fallback-assets/{id}/content?kind=video&expected_revision=...` передаёт непустой файл с `Content-Type: application/octet-stream`. Допустимые `kind` — `image` и `video`. Путь сервера и имя конечного файла клиент не выбирает.
3. Допуск и резервирование выполняются до чтения тела. Байты, длительность чтения и очередь ограничены. Файл не копируется заранее во второй HTTP-каталог.
4. `202` возвращается после полного сохранения оригинала и закрытия reader, до inspection и генерации вариантов. Ответ содержит AssetID, GenerationID и `Location` точного поколения.
5. Клиент читает `GET /fallback-assets/{id}/generations/{generationId}` до результата подготовки.

Отмена до завершения передачи отменяет задание и закрывает reader, включая ожидание очереди. После успешного подтверждения передачи отключение клиента не отменяет подготовку: ею владеет FallbackManager с собственным сроком. Возобновление частично переданной загрузки и долговечный replay загрузок не обещаются.

Новая передача всегда создаёт новое поколение, даже при одинаковых байтах. Прежняя рабочая версия и остальные заглушки сохраняются до успешной проверки и атомарной публикации всего нового комплекта. Ошибка подготовки после `202` доступна в результате поколения и не отменяет успешный факт передачи.

`rebuild` принимает ожидаемую ревизию и возвращает `202` после резервирования: исходный файл уже хранится на сервере, повторная HTTP-передача не нужна. Генерация и rebuild запрещены во время эфира, включая ручную паузу, по существующему общему протоколу подготовки.

Подготовка всегда создаёт AAC с цифровой тишиной по аудиоформату группы, в том числе для видео с собственной аудиодорожкой. Исходный звук не используется; готовый вариант и его петли беззвучны. При переходе с LIVE допускается короткий остаток предыдущего звука декодера, длительность которого не определяется одним универсальным значением для всех получателей.

Варианты прежнего генератора сохраняют метаданные и историю, но не допускаются к новому воспроизведению. После обновления выполните существующий `rebuild` до эфира и дождитесь успешной подготовки всего комплекта. Отказ сохраняет прежний текущий комплект, но не делает его старую версию пригодной. Проверка применяется также к закреплённому снимку при повторном запуске выхода; свежий вариант не подставляется в старый OutputSnapshot автоматически.

| Сохраняемое состояние поколения | Публичный статус |
| --- | --- |
| `QUEUED` | `queued` |
| `CLAIMED`, `ISSUED` | `preparing` |
| `PUBLISHED` | `ready` |
| `FAILED`, `INTERRUPTED` | `error` |

Current и pending Asset имеют разные назначения. Ошибка новой подготовки не делает готовый current ошибочным. Результат конкретного Generation остаётся доступным после очистки pending. Список variants по умолчанию относится к current; явный `generation_id` проверяется относительно Asset. Наличие metadata `READY` не заменяет фактическую проверку файла при запуске.

## Текущие измерения и SSE

История запусков и результаты управления читаются из SQLite. Наблюдаемые состояния, счётчики, progress, ошибки медиатракта и GPU-измерения — из RAM. Они не восстанавливаются из истории после завершения Session или рестарта.

Неизвестная Session даёт `404`. Известная Session без текущих измерений даёт `200` с явной недоступностью и `null` вместо runtime-снимка; причины завершённой и ещё не наблюдаемой Session различаются. Недоступное или устаревшее численное измерение не подменяется нулём. Для недоступного FFmpeg-отчёта `progress` равен `null`; статус, причина, известные времена и счётчики потерь сохраняются. Измеренный ноль после полноценного окна остаётся допустимым значением. Единицы, окна и источники описаны в [контракте мониторинга](monitoring-contracts.md).

Метрики выхода содержат четыре явных поля непосредственно в `metrics`, одинаковых для REST и payload SSE:

| Поле | Представление |
| --- | --- |
| `ack_ahead_events_total` | Десятичная строка `uint64`, число новых достоверно измеренных опережающих подтверждений. |
| `ack_ahead_bytes_last` | Десятичная строка `uint64`, размер последнего измеренного опережения в RTMP-байтах. |
| `ack_ahead_bytes_max` | Десятичная строка `uint64`, максимальный измеренный размер за запуск выхода. |
| `ack_last_anomaly_at` | Время UTC либо `null` до первого события. |

Начальные целые значения равны `"0"`. В `metrics.counters` эти поля не дублируются. Переподключение текущего запуска сохраняет накопления; новый запуск выхода начинает их заново. Насыщение обозначается существующим общим `metrics.media.saturated`, без сворачивания целых. Последнее и максимальное опережение и время продолжают обновляться после насыщения числа событий. Поля и их типы входят в генерируемый OpenAPI/JSON Schema.

Каждый новый измеримый опережающий ACK увеличивает число событий отдельно; дубликаты и неоднозначные наблюдения не считаются. При незавершённом `Write` и после потери однозначной эпохи счётчика часть наблюдений не измеряется. Нулевое число событий не является подтверждением отсутствия расхождений. Подробные пределы и единицы заданы в [контракте мониторинга](monitoring-contracts.md#диагностика-опережения-ack); сами показатели не влияют на отправку.

Для согласованного начала и восстановления клиент:

1. Получает `GET /events/snapshot`: все текущие Session/GPU и cursor сняты одной authority-границей.
2. Открывает `GET /events?cursor=...` и применяет следующие события.
3. При переподключении может передать `Last-Event-ID`; разные значения одновременно в header и query дают `400`.
4. При `resync_required` закрывает прежнюю подписку, получает новый снимок и открывает SSE с новой границы.

Курсор — ограниченная непрозрачная позиция оперативного потока, не токен доступа. Старый epoch, пропуск или очистка событий требуют нового снимка. События неполного диапазона не выдаются за непрерывную историю. Без cursor поток начинается с текущей границы и не заменяет первоначальный REST-снимок.

Клиенты, размер страницы и кадра, heartbeat и время записи ограничены. Deadline действует до первой записи и flush. Неподдерживаемый transport не допускает неограниченную запись; медленный клиент отключается. Сеть не удерживает authority и не блокирует медиатракт. Отмена запроса и закрытие API завершают принадлежащие им streams. После начала SSE нельзя изменить HTTP status; допустимы безопасный control frame и закрытие.

RAM-снимок не является общей транзакцией с историей SQLite. Квитанции команд клиент при необходимости читает отдельно.

## Возможности, готовность и ошибки

`/system/capabilities` сообщает фактически проверенные сведения и их время. Доступность настроенного executable не подтверждает наличие нужных codecs/filters или работоспособность NVENC/NVDEC. Непроверенная аппаратная возможность остаётся `unverified`; недоступная NVML-статистика не является доказательством отказа медиатракта. Проверка не запускает процессы, аппаратный самотест, сканирование или фоновые probes.

`/health/live` описывает работоспособность процесса. `/health/ready` проверяет открытое управление и ограниченное чтение хранилища, полученного после bootstrap. Недоступные FFmpeg/NVIDIA и GPU-статистика сами по себе не снимают готовность управления. Недоступная управляющая зависимость даёт `503`. Готовность не требует соединения со всеми площадками и завершения старого терминального cleanup.

Ошибки возвращаются как `application/problem+json`; исходные диагностические сообщения, отклонённые значения и query не раскрываются, включая автоматическую валидацию Huma. Для ошибок полного профиля допускаются только подготовленные сервером объяснение, код и публичный путь поля, описанные выше.

| HTTP status | Значение |
| --- | --- |
| `400` | Некорректная структура запроса или cursor |
| `404` | Неизвестный объект или неподходящий родитель |
| `408` | Истёк срок чтения upload |
| `409` | Конфликт ревизии, использования или состояния |
| `413` | Превышен допустимый размер |
| `415` | Неподдерживаемый Content-Type |
| `422` | Недопустимые значения |
| `503` | Недоступна требуемая зависимость или приём операций |
| `500` | Неожиданная внутренняя ошибка |

Точные operation IDs, DTO и применимые параметры опубликованы в OpenAPI. Спецификации JSON/YAML формируются после регистрации и затем неизменяемы. Дополнительные downgrade-маршруты не публикуются. Документация и schemas используют тот же префикс и не требуют Authorization.

## Локальная приёмка 6 ноября 2026 года

T08 принята локально на стабильном снимке `t08-frozen-v3`: 386 проверяемых исходников, тестов и файлов конфигурации, включая новые файлы. Все их хеши совпали до и после проверок. Среда — Go 1.27.3, macOS/arm64, CGO=1; настоящие временная SQLite/Goose, локальные RTMP-приёмники и process helper.

- Полный `make check` прошёл: форматирование, согласованность и целостность модулей, vet, тесты всех `./...`, race, закреплённый линтер и сборка. Покрыто **13 689 из 15 852 инструкций — 86,355034%**; автоматический точный порог 85% пройден без исключений пакетов. Учтены данные покрытия действительно исполненного helper; временные профили удалены штатной командой после расчёта.
- Независимые свежие `go test -count=1 -json ./...` и `go test -race -count=1 -json ./...` прошли без диагностик data race. Каждый запуск: 18 успешных пакетов, 1876 успешных тестов и подтестов; два пакета без тестовых файлов. Десять пропусков относятся к отдельным медиапроверкам с FFmpeg/VideoToolbox; проверки T08 не пропускались.
- Проверены REST/OpenAPI, CAS и присутствие полей, точность данных и безопасные ошибки, настоящие команды SessionManager и квитанции, передача и независимая подготовка заглушек, RAM/SSE, возможности и готовность управления. Независимое итоговое ревью не выявило неисправленных замечаний или необоснованного расширения задачи.

При проверке исправлена выдача устаревшего FFmpeg progress: недоступный отчёт теперь `null`, актуальные нули и частично доступные поля сохраняются. Независимая регрессия сначала воспроизвела ошибку через REST и SSE, затем прошла обычный и race-запуски.

Первый общий race-прогон также выявил некорректную границу нового интеграционного теста: один приёмник смешивал основной выход и намеренно закрываемый дополнительный. Контролируемый диагностический опыт подтвердил ложный отказ общего ожидания при продолжающейся передаче основного потока. Приёмники разделены; сохранение основного соединения и передача следующих пакетов проверяются отдельно. Конкретное соединение первоначального `EOF` не было записано и осталось неизвестным; ему не приписывается недоказанная причина. Первое падение и диагностика сохранены. Финальные полные проверки выполнялись без диагностических overlays, подавления ошибок, новых задержек или изменения `GORACE`.

Предоставленная владельцем AV1/AAC-запись в этой приёмке не использовалась. FFmpeg, GPU, Debian/NVIDIA, настоящий OBS, реальные площадки и длительный эфир в эту локальную приёмку не входили. Общая точка входа и подключение зависимостей реализованы в T09 и описаны в [контракте приложения](application-contracts.md). Последующий основной прогон на VM и отложенные сценарии приведены в [целевой приёмке](media-contracts.md#target-acceptance).
