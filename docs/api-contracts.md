# Управляющий HTTP API

Документ описывает публичный контракт API. Результаты проверки реализации приведены отдельно в конце документа. Сборка исполняемого сервиса и подключение общих зависимостей принадлежат composition root.

## Доступ и представление данных

Все маршруты имеют префикс `/api/v1`. REST, SSE, OpenAPI, документация, схемы и health доступны без авторизации и токенов доступа в личном локальном контуре владельца. Отдельный приём OBS проверяет постоянный ключ Stream и готовую Session; управляющий API этот допуск не заменяет.

HTTP DTO отделены от доменных и ORM-представлений. Ключ публикации Stream принимается при создании и затем не редактируется. Ответы создания, чтения и изменения Stream возвращают сохранённый `publication_key`; ответы Destination возвращают полный `endpoint` и `stream_key`, включая пустую строку ключа назначения. URL возвращается целиком, в том числе с учётными данными, путём и параметрами запроса. Эти поля входят также в общие и вложенные списки. Флаги `publication_key_configured`, `endpoint_configured` и `stream_key_configured` не используются.

В Session поле `stream` берётся из сохранённого снимка запуска, в Output поле `destination` — из собственного сохранённого снимка выхода. Изменение или допустимое удаление текущих настроек не меняет исторические ключи и адреса. Уже записанные значения доступны без повторного ввода или миграции БД. SSE и ошибки не возвращают ключи и адреса; файловые пути, внутренние fences/tokens, identity команд и исходная диагностика исключены из публичных DTO.

Полные диагностические значения в выбранных локальных событиях журнала сохраняют режим `full`. Эта политика не переносится на публичные HTTP-ответы.

Все значения с числовым назначением принимаются и передаются JSON-числами: целые описаны как `integer`, вещественные — как `number`. Ревизии, байты, счётчики и длительности сохраняют полный применимый диапазон и точность 64-битных целых без преобразования через `float64` на границе JSON. Строка вместо числа отклоняется. Математически целые записи `1.0` и `1e0` принимаются целочисленными полями; настоящие дроби и переполнение отклоняются. Длительности передаются целыми наносекундами, `out_time_us` FFmpeg — знаковыми микросекундами. FPS сохраняет исходные `numerator` и `denominator`. Идентификаторы, ключи, cursor и даты остаются строками. Время представлено в UTC; отсутствующее время — `null`. [Полный реестр числовых полей](numeric-json-contracts.md) задаёт маршруты, единицы, диапазоны и правила отсутствия, `null` и нуля.

Настройки полного профиля передаются обычными корректными UTF-8 строками из закрытых наборов. Base64-объекты, неподдерживаемые строки, неверный регистр и несовместимые сочетания отклоняются безопасной ошибкой `422`, в том числе без `encoding` или с `encoding: null`. [Реестр строковых полей](string-json-contracts.md) задаёт все пути REST/SSE, наборы, зависимости, правила пустоты и отсутствия. Весь профиль при редактировании заменяется целиком; произвольного рекурсивного слияния его полей нет.

Измеренный Variant.format имеет отдельный каталог: неизвестное непустое обозначение возвращается как UNKNOWN, не меняя внутреннее измерение. Объект format сохраняется также до проверки и у FAILED.

## Полный профиль кодирования

Настройки назначения задаются через его `TranscodeGroup` и выбранный `TranscodeProfile`. Два назначения одной группы используют один результат кодирования. Для разных полных настроек создаются отдельные профили и группы; название площадки не выбирает параметры автоматически.

`profile` содержит `mode`, `format`, `video_encoding`, `audio_encoding`, независимый `live_audio_mode` и полный `encoding`. Модель одна: полей версии профиля и `encoding.version` нет. Допустимые сочетания определяются кодеком, выбранным кодировщиком и параметрами.

`mode` выбирает обработку видео. `live_audio_mode` принимает `copy` либо `transcode`; при создании отсутствие поля означает `copy`. Сервер материализует выбор и возвращает его в GET. Явные null, пустая строка и неизвестное значение отклоняются. Для видео copy допускается только копирование LIVE-аудио.

При `live_audio_mode: "copy"` переданные поддержанные аудиопакеты OBS сохраняются без повторного сжатия, изменения частоты, каналов и битрейта. Действующие правила среза, синхронизации и отбрасывания устаревших пакетов сохраняются. Фактическая привязка должна совпадать с `format.audio`; несовместимый LIVE не допускается в группу, пригодная заглушка продолжает работать, причина доступна в журнале. Перехода к перекодированию без явного выбора нет.

Настройки `audio_encoding`, `encoding.audio_encoder` и `encoding.audio_custom` всегда задают кодирование тишины заглушки. При LIVE `transcode` они задают также его аудиокодирование. При LIVE `copy` они не меняют звук OBS; `format.audio` остаётся ожидаемым совместимым форматом. Target Opus не является измеренным VBR-битрейтом копируемого потока; конечные MP3/AC-3 требуют фактического битрейта из своей привязки.

Сохранённый профиль всегда имеет явный LIVE-селектор и полный Encoding. Чтение и PATCH только имени не назначают значения по умолчанию. Полная замена профиля требует явного live_audio_mode после CAS; PATCH без profile сохраняет профиль. Сравнения и запрета понижения версий нет, поскольку версии возможностей отсутствуют.

| Поле | Значения и действие |
| --- | --- |
| `video_encoder` | `h264_nvenc`/`libx264` для H.264 transcode, `libsvtav1`/`libaom-av1` для AV1-заглушки группы copy, `libx265`/`hevc_nvenc` для HEVC либо `libvpx-vp9` для VP9 по матрице ниже. |
| `audio_encoder` | `aac` по умолчанию; явные `libopus`, `flac`, `libmp3lame`, `ac3` только с соответствующим аудиоформатом. |
| `rate_control` | Явный `cbr`, `vbr`, `cqp` либо `crf` по матрице кодировщика. Равные битрейты сами по себе не выбирают CBR. |
| `rescale_output` | Разрешение масштабирования LIVE в размеры `format.video`; по умолчанию `true` для `transcode`, `false` для `copy`. При `false` размеры входа и выхода `transcode` должны совпадать. FPS задаётся независимо. |
| `video_custom`, `audio_custom` | Дополнительные параметры выбранного кодировщика; по умолчанию пустые строки. |
| `nvenc`, `svt_av1` | Только применимый блок настроек выбранного видеокодировщика. |

В явном encoding обязательны video_encoder и rate_control; CQP/CRF требуют соответствующее поле качества. Применимые необязательные настройки получают единственные текущие значения по умолчанию при создании или полной замене. GET возвращает полный объект Encoding с применимыми настройками. Отсутствие отличается от явных false, 0 и -1; null внутри объекта запрещён. Неприменимый блок кодировщика нельзя передавать даже как пустой объект.

Отсутствующий или null encoding — только сокращённый вход для H.264/transcode → NVENC/VBR либо AV1/copy → SVT/CBR. Он немедленно материализуется в тот же полный объект до проверки домена. Для HEVC/VP9 и новых аудиокодеков такого неявного выбора нет: задайте кодировщик и режим явно. Нулевой Encoding не хранится и не исполняется. Чтение и переименование материализацию не выполняют.

| Настройка `nvenc` | Диапазон | По умолчанию |
| --- | --- | --- |
| `preset` | `p1`…`p7` | `p4` |
| `tuning` | `hq`, `ll`, `ull`; `lossless` только в узком H.264 binding ниже | `hq` |
| `multipass` | `disabled`, `qres`, `fullres` | `disabled` |
| `lookahead_frames` | 0…31; положительное значение плюс `max_b_frames` не больше 31 | 0 |
| `enable_spatial_aq`, `enable_temporal_aq` | bool | `false` |
| `aq_strength` | 1…15; при `enable_spatial_aq: false` только 8 | 8 |

Нулевой NVENC lookahead оставляет выбор native preset; это не обещание выключенного анализа. AQ `false` не включает функцию дополнительно к preset и не гарантирует очистку его внутренних флагов. Сохранённые поля описывают запрос кодировщику, а не измеренное состояние GPU.

| Настройка `svt_av1` | Диапазон | По умолчанию |
| --- | --- | --- |
| `preset` | 0…13 | 8 |
| `tuning` | `psnr`, `vq`; CBR допускает только `psnr` | `psnr` |
| `aq_mode` | 2 | 2 |
| `lookahead_frames` | Для CBR только 0; для VBR `-1` (native auto) либо 6…120 | CBR: 0; VBR: `-1` |

SVT VBR lookahead 0…5 отклоняется: выбранный native режим способен принудительно изменить такой запрос. Внутреннее планирование mini-GOP остаётся квантованным; положительное поле задаёт native запрос дистанции анализа. Параметры NVENC не переносятся на SVT автоматически.

Набор настроек сверён с FFmpeg 7.1.5 и SVT-AV1 4.3.0. Фактические версии, возможности NVIDIA и применимость параметров целевого сервера проверяются отдельно при аппаратной приёмке; успешное сохранение профиля их не измеряет.

Битрейты и буфер передаются точными целыми JSON-числами. В CBR/VBR H.264 действуют `1 ≤ target_bitrate_bps ≤ max_bitrate_bps ≤ 4294967295`, buffer_bits от 1 до 2147483647; CBR требует равных битрейтов. Для SVT target от 1 до 100000000; CBR требует max=target и буфер, точно соответствующий целым 20…10000 мс. SVT VBR требует max_bitrate_bps=0 и buffer_bits=0: ненулевой запрос неподдерживаемого ограничения отклоняется. Чистые режимы качества и другие кодировщики имеют правила ниже. Независимые числа не исправляются, не округляются и не заменяются значения по умолчанию.

Размеры чётные, GOP закрытый. H.264 имеет размеры не больше 65534, GOP от 1 до 2147483647, B-кадры 0…4 и меньше GOP; baseline требует 0. AV1 имеет размеры 64…16384 × 64…8704, FPS не выше 240, GOP от 2 до 2147483647 и B0. AAC — LC с раскладками из следующего раздела; частоты 7350, 8000, 11025, 12000, 16000, 22050, 24000, 32000, 44100, 48000, 64000 Гц, положительный битрейт не выше `6 × sample_rate_hz × channels`. Проверяется точная представимость FPS и контейнера. Аппаратная исполнимость подтверждается отдельно.

Фактическая готовность группы проверяется отдельно. В частности, задержка H.264 при B-кадрах должна укладываться в настроенный `MaxTransitionGap`; снижение FPS не увеличивает этот бюджет автоматически. Сохранение профиля не подтверждает готовность файлов, GPU или группы к эфиру.

Custom имеет вид `name=value name=value`: разделитель — ASCII-пробел, без кавычек, экранирования, управляющих символов и вложенных списков. На строку допускается до 4096 байт и 32 пар, имя до 64 байт, значение до 128. Поддержаны NVENC `nonref_p=0|1`, `strict_gop=0|1`; SVT `lp=0…6`; AAC `aac_coder=twoloop|fast`. `lp=0` означает native выбор уровня параллелизма. Нулевые NVENC custom-флаги также не гарантируют очистку preset. Пары сортируются, числа нормализуются; GET возвращает сохранённую нормализованную строку.

Дубликат, неизвестная опция и конфликт с обычным полем или внутренним рецептом отклоняются. Например, `rc=vbr` в custom конфликтует с полем режима независимо от совпадения значений. Ответ `422` содержит доверенные код, путь поля и понятное объяснение; произвольные значения запроса и диагностика FFmpeg в него не включаются.

Для `copy` до подготовки заглушки вручную задаются ожидаемые выходные формат, CBR/VBR и битрейты OBS. `libsvtav1` и его дополнительные поля описывают серверную подготовку заглушки, а не encoder игрового ПК. `rescale_output` остаётся `false`: сервер не меняет копируемый LIVE. Сам asset заглушки всегда приводится к выходным размерам. [Примеры JSON для Postman](obs-client-guide.md#профили-кодирования-в-postman) показывают создание и изменение профиля.

Изменение полного профиля, включая live_audio_mode, требует подходящих fallback-вариантов до эфира. Текущие Session/Output используют самостоятельные снимки; горячей перенастройки нет. Прежние сохраняемые формы не читаются.

### Качество SVT и многоканальный AAC LC

Качество SVT и многоканальный AAC LC входят в общую модель. SVT готовит AV1-заглушки группы copy, NVENC кодирует H.264 transcode. LIVE AV1 сохраняется без перекодирования.

| Поле или сочетание | Правило |
| --- | --- |
| SVT `rate_control: "cqp"` | Обязателен `encoding.qp`: целое JSON-число 1…63. `encoding.crf` запрещён. `svt_av1.aq_mode` равен 0, tuning — `psnr`. |
| SVT `rate_control: "crf"` | Обязателен `encoding.crf`: JSON-число с математически целым значением 1…63. `encoding.qp` запрещён. `svt_av1.aq_mode` равен 2. |
| SVT CRF tuning | `psnr`, `vq`, `ssim`, `ms_ssim`, `vmaf`; последние три отображаются точно в native `tune=2`, `4`, `5` и запрещены с CBR/VBR/CQP. `iq` не поддерживается. |
| Общие битрейты в CQP/CRF | `target_bitrate_bps`, `max_bitrate_bps`, `buffer_bits` обязательны и равны 0. Они не создают скрытого ограничения битрейта или VBV. |
| SVT CQP/CRF lookahead | `-1` либо 6…120, по умолчанию `-1`; используется random-access рецепт. |
| CBR/VBR | Действуют ограничения битрейтов; оба quality-поля запрещены. Качество NVENC определяется отдельной матрицей ниже. |

Поля `qp` и `crf` нельзя передавать как `null` или строки. Ноль не означает отсутствие и отвергается выбранным SVT binding. Настоящая дробь, включая число, которое округлилось бы до целого при разборе через `float64`, отклоняется. Математически целые записи вроде `35.0` и `35e0` допустимы. Ответ возвращает только применимое присутствующее quality-поле.

| `format.audio.channel_layout` | `format.audio.channels` |
| --- | --- |
| `mono` | 1 |
| `stereo` | 2 |
| `2.1`, `3.0` | 3 |
| `4.0` | 4 |
| `5.0` | 5 |
| `5.1` | 6 |
| `7.1` | 8 |

Разные раскладки с одинаковым числом каналов не взаимозаменяемы. Поддерживается AAC LC с единицами по 1024 сэмпла. ASC и PCE определяют фактическую карту каналов; исходные байты конфигурации и копируемых AU сохраняются. Нормативный AAC `channel_configuration=7` означает `7.1(wide-back)`, несовместимый с желаемым `7.1`; обычный `7.1` обозначается configuration 12 либо соответствующим PCE. Сервер не угадывает раскладку по числу каналов или желаемому профилю. HE, HEv2, LD и ELD не включены.

Для собственного кодирования AAC 7.1 с FFmpeg 7.1.5 используется `-aac_pce 0`: принудительный PCE этой версии неверно описывает карту. Только свежий результат подготовки либо явного LIVE AAC transcode проходит проверку известного native ASC и замену configuration 7 на 12 до строгой проверки fMP4. AU и время сохраняются. Приём, LIVE copy и готовые файлы коррекции не получают. Многоканальный выход использует Enhanced Audio `mp4a`; поддержка получателя проверяется отдельно. FFmpeg 7.1.5 напрямую эту форму RTMP не декодирует.

### SDR-форматы, цвет и кодировщики

Допустимые SDR-сочетания входят в единую модель. AV1 LIVE копируется, H.264 LIVE перекодируется; выбор кодировщика AV1 задаёт подготовку заглушки.

| Кодировщик | Профиль | Пиксельный формат / глубина |
| --- | --- | --- |
| `libsvtav1` | `main` | `yuv420p` / 8; `yuv420p10le` / 10 |
| `libaom-av1` | `main` | `yuv420p` / 8; `yuv420p10le` / 10; `gray` / 8 |
| `libaom-av1` | `high` | `yuv444p` / 8; `yuv444p10le` / 10 |
| `libaom-av1` | `professional` | `yuv422p` / 8; `yuv422p10le` / 10 |
| `libx264` | `constrained-baseline`, `main`, `high` | `yuv420p` / 8 |
| `libx264` | `high10` | `yuv420p10le` / 10 |
| `libx264` | `high422` | `yuv422p` / 8; `yuv422p10le` / 10 |
| `libx264` | `high444` | `yuv444p` / 8; `yuv444p10le` / 10 |
| `h264_nvenc` | `baseline`, `main`, `high` | `yuv420p` / 8 |
| `h264_nvenc` | `high444` | `yuv444p` / 8 |

Размеры остаются чётными, GOP закрытым. Constrained Baseline требует нулевого числа B-кадров. Неподдержанное сочетание не исправляется повышением профиля или заменой кодировщика. H.264 `extended` остаётся распознаваемым наблюдением, но выбранные кодировщики не предоставляют его как настройку.

X264 и AOM используют фиксированные рецепты: video_custom пустой, блоки nvenc и svt_av1 отсутствуют, включая пустые объекты. Дополнительных блоков x264/AOM нет. У NVENC/SVT остаются применимые поля. Физический путь обработки выбирается до запуска по фактическому входу и выбранному кодировщику, без автоматической замены кодировщика.

| Кодировщик | CQP | CRF |
| --- | --- | --- |
| SVT | Целое 1…63 | Математически целое 1…63 |
| x264 | Целое 0…51 | 0…51 с точным шагом 0.01 |
| NVENC | Целое 0…51 | Не поддерживается |
| AOM | Не поддерживается | Математически целое 0…63 |

В чистых CQP/CRF целевой битрейт, максимальный битрейт и буфер равны нулю, присутствует только одно применимое поле качества. В CBR/VBR оба поля качества запрещены. `23.5`, `23.50` и `2.35e1` означают одно качество; лишняя ненулевая дробь не округляется. Явный 0 не считается отсутствием. X264 QP/CRF 0 разрешён только для high444 с 4:4:4, чистое качество H.264 требует пустого уровня или `auto`. X264 CBR/VBR требуют кратности 1000 для обоих битрейтов и буфера; целевой битрейт AOM также кратен 1000, его VBR требует нулевых максимума и буфера, CBR — равных битрейтов и точно представимого буфера в миллисекундах. [Числовой реестр](numeric-json-contracts.md#полный-профиль-и-медиаформат) содержит единицы и полные числовые зависимости.

NVENC CQP имеет фиксированный P4, tuning `hq` либо узкий `lossless`, multipass `disabled`, lookahead 0, оба AQ `false`, strength 8 и пустой custom. Lossless дополнительно требует high444/yuv444p/8-bit, QP0, B0 и CAVLC. Используется режим кодировщика `lossless`, включающий обход преобразования; одного QP0 недостаточно. Сохранность относится ко входу кодировщика после изменения размера/цвета/глубины. Фактические флаги preset и результат на GPU проверяются отдельно; сохранённые запросы не являются аппаратным измерением.

| Ось цвета | Допустимые значения |
| --- | --- |
| `primaries` | `bt709`, `bt470m`, `bt470bg`, `smpte170m`, `smpte240m`, `film`, `bt2020` |
| `transfer` | `bt709`, `gamma22`, `gamma28`, `smpte170m`, `smpte240m`, `linear`, `iec61966-2-1`, `bt2020-10`, `bt2020-12` |
| `matrix` | `bt709`, `fcc`, `bt470bg`, `smpte170m`, `smpte240m`, `bt2020nc`, `bt2020c` |
| `range` | `limited`, `full`, прежние `tv`, `pc` |

`bt2020c` допускается для цветного формата с transfer bt709, smpte170m, bt2020-10 либо bt2020-12. Для известного цвета выполняется реальное преобразование пикселей; rescale_output ограничивает только размеры LIVE, заглушка приводится к выходным размерам независимо от него. Gray сохраняет Y и диапазон явно. PNG/JPEG и SDR8/yuv420p-видео с неполными CICP допускаются только в ограниченную подготовку SDR BT.709/8-bit/4:2:0 через SVT AV1/H.264 NVENC с AAC. SourceFormat остаётся неизвестным; желаемые теги не считаются исходным измерением. HDR описан отдельно ниже.

H.264 6.0/6.1/6.2 требуют CBR/VBR, B0 и одного опорного кадра; до процесса проверяются геометрия в макроблоках, точная частота, DPB и профильные BR/CPB. SVT high tier допускается только с CBR и явным уровнем 4.0, 4.1, 5.0–5.3 либо 6.0–6.3. Буфер — точные 20…1000 мс, целевой битрейт не выше серверного предела 100 Мбит/с и бюджета уровня, максимум равен целевому. AOM использует пустой уровень/`auto` и пустой tier/`main`; неподтверждённое общее управление уровнем не публикуется. Проверка запрошенной конфигурации и фактических заголовков не обещает жёсткий предел каждого пакета или полное соответствие стандарту любого внешнего потока.

Измеренный формат использует отдельные таблицы CICP, реальные профиль, глубину, субдискретизацию, уровень и tier из заголовков. `unspecified` и `UNKNOWN` не становятся допустимыми настройками. Псевдонимы ffprobe `bt470m`/`bt470bg` в поле transfer обозначают соответственно `gamma22`/`gamma28`; это преобразование относится только к оси transfer. Копируемые AU и исходные заголовки сохраняются.

### HEVC, VP9 и HDR

HEVC/VP9 и HDR входят в единую матрицу вместе с SDR. Для HEVC/VP9 SDR-целей primaries, transfer и matrix равны bt709, диапазон — известный limited/full либо точный alias tv/pc.

| Кодек и encoder | LIVE mode | Профиль и пиксели | HDR |
| --- | --- | --- | --- |
| `hevc`, `libx265` или `hevc_nvenc` | `copy` либо `transcode` | `main` / `yuv420p` / 8; `main10` / `yuv420p10le` / 10 | Только Main10 |
| `vp9`, `libvpx-vp9` | `copy` либо `transcode` | `profile0` / `yuv420p` / 8; `profile2` / `yuv420p10le` / 10 | Только profile2 |
| `av1`, `libsvtav1` | `copy` | `main` / `yuv420p10le` / 10 | Да |
| `av1`, `libaom-av1` | `copy` | `main` / `yuv420p10le`, `high` / `yuv444p10le`, `professional` / `yuv422p10le`; 10 бит | Да |
| `h264`, `libx264` | `transcode` | `high10` / `yuv420p10le`, `high422` / `yuv422p10le`, `high444` / `yuv444p10le`; 10 бит | Да |

В `copy` выбранный encoder создаёт только заглушку; LIVE сохраняет кодированные AU. AV1 LIVE transcode и H.264 copy не добавляются. Для HEVC/VP9 допустимы только пустой `level` либо `auto`; HEVC tier — пустой/`main`, VP9 tier — пустой. Наблюдаемые уровни и известные неподдержанные профили имеют отдельный каталог и не становятся desired-настройками. VP9 `profile0`/`profile2` соответствуют native 0/2; числовые строки не являются дополнительными aliases.

Новые HEVC/VP9-рецепты используют закрытый GOP и B0. X265 имеет фиксированный `medium`, один опорный кадр, выключенные open GOP и scene cut. HEVC NVENC использует внутренние P4/HQ, отключённые multipass/lookahead/AQ и один опорный кадр. Его `nvenc`-блок неприменим: его нельзя передать даже как `{}`; этот публичный блок остаётся у `h264_nvenc`. Для всех трёх новых encoders `video_custom` пустой, `svt_av1` отсутствует. HEVC NVENC 10-bit получает явную P010-перепаковку; описание выходных пикселей остаётся `yuv420p10le`. Аппаратная исполнимость проверяется отдельно.

| Encoder | Режимы качества | Битрейты и буфер |
| --- | --- | --- |
| `libx265` | CQP: целое число 0…51; CRF: 0…51 с шагом 0,01 | CBR/VBR: `0 < target ≤ max ≤ 4294967295`, `0 < buffer ≤ 2147483647`; все три кратны 1000. CBR требует `max=target` и включает native strict CBR с VBV. |
| `hevc_nvenc` | CQP: целое число 0…51; CRF отсутствует | CBR/VBR: те же границы без требования кратности 1000; CBR `max=target`. CQP задаёт одинаковые I/P/B QP. |
| `libvpx-vp9` | CRF: математически целое число 0…63; CQP отсутствует | Target кратен 1000, не выше 1 000 000 000 бит/с. VBR: `max=buffer=0`. CBR: `max=target`, положительный buffer до 2147483647 бит с точным положительным целым числом миллисекунд. |

Чистые CQP/CRF требуют нулевых target/max/buffer и единственного применимого quality-поля; CRF VP9 задаётся с нулевым bitrate. Нулевое качество x265/VP9 не обещает lossless. Новый HEVC lossless не включён. VP9 использует один проход, нулевые lag/altref и равные GOP min/max. X265 CBR описывает управление средним потоком и буфером; одинаковые байты каждого кадра или жёсткий предел каждого короткого интервала не обещаются. VBR VP9 не получает фиктивного hard max. Остальные зависимости качества у SVT/x264/AOM/H.264 NVENC сохраняются.

HDR требует `primaries: "bt2020"`, `transfer: "smpte2084"` либо `"arib-std-b67"`, `matrix: "bt2020nc"`, известный диапазон и 10 бит. Фактический HDR-источник должен совпадать по этим характеристикам. Разрешены FPS, масштабирование и применимые преобразования 10-битных YUV-плоскостей; `rescale_output` по-прежнему ограничивает только изменение размера LIVE. SDR↔HDR, PQ↔HLG, tone mapping, gamut, смена диапазона и глубины не выполняются. Неизвестный источник не ретегируется желаемыми значениями.

MDCV/CLL поступают из реальных заголовков, AU и контейнера. Пользовательских полей для них в профиле нет. Переносятся исходные авторские сведения, без нового mastering или измерения яркостных максимумов результата; PQ/HLG сам по себе не создаёт отсутствующих metadata. Форматы разных границ имеют разные единицы, известность и область действия. Непредставимая известная часть даёт явную несовместимость соответствующего порта, неизвестное не заполняется типовыми числами.

HDR-источник подготовки ограничен MOV/MP4-видео с проверенным единым набором сведений. Один ограниченный проход по его сжатым metadata выполняется перед новой HDR-подготовкой, поскольку encoder/container фиксируют их при init. Изменяющийся источник и неподдержанные HDR-изображения отклоняются до публикации комплекта. Предыдущий рабочий комплект сохраняется. Сведения восстанавливаются при повторном открытии файла и переключении; устаревшее `colorInfo` не переносится на другой источник. Реальные pixels/metadata/получатель проверяются отдельно от успешного REST-сохранения.

Например, блок `profile.encoding` для HEVC Main10/PQ с x265 и качеством CRF можно передать так:

```json
{
  "video_encoder": "libx265",
  "rate_control": "crf",
  "crf": 23.51
}
```

Это фрагмент полного профиля: в `format.video` нужны `codec: "hevc"`, `codec_profile: "main10"`, `pixel_format: "yuv420p10le"`, `bit_depth: 10` и согласованный цвет BT.2020/PQ/bt2020nc. `video_encoding` задаёт нулевые target/max/buffer, закрытый GOP и B0. Размеры, FPS, аудио и LIVE-аудиорежим остаются явной частью полного запроса. Для VP9 profile2 вместо этого выбираются `video_encoder: "libvpx-vp9"`, `codec: "vp9"`, `codec_profile: "profile2"` и целый CRF; остальные зависимости проверяются по таблице выше.

### Opus, FLAC, MP3 и AC-3

AAC LC и четыре конечные аудиопривязки доступны в одной модели с общей видеоматрицей и HDR-ограничениями. H.264 LIVE — выход transcode, AV1 LIVE — copy. Аудиокодировщик задаётся явно для выбранной привязки; автоматического выбора по codec нет.

| `format.audio.codec` | `format.audio.codec_profile` | `encoding.audio_encoder` | `audio_encoding.bitrate_bps` | Конечная привязка |
| --- | --- | --- | ---: | --- |
| `opus` | `celt` | `libopus` | 128000 | 48000 Hz, 2/stereo, одна CELT AU 120 сэмплов, mapping 0, gain 0; собственный encoder использует lowdelay, 2,5 ms и VBR. |
| `flac` | `s16` | `flac` | 0 | 48000 Hz, 2/stereo, PCM16; ноль означает неприменимый target, а не PCM-битрейт. |
| `mp3` | `mpeg1-layer3` | `libmp3lame` | 128000 | MPEG-1 Layer III, 48000 Hz, stereo/joint-stereo, одна AU 1152, reservoir 0; без CRC-protected, free-format и MPEG-2/2.5. |
| `ac3` | `ac3` | `ac3` | 192000 | 48000 Hz, 2/stereo, bsid 8, acmod 2, без LFE, одна AU 1536; обе CRC проверяются. |

Для всех четырёх новых выходов `channel_layout: "stereo"`, `channels: 2`, `sample_rate_hz: 48000` и пустой `audio_custom` обязательны. Имена чувствительны к регистру; дополнительных aliases и пользовательских настроек encoder нет. Пустой либо чужой audio encoder не выбирается автоматически по имени кодека.

Opus/MP3/AC-3 допускают `live_audio_mode: "copy"` либо `"transcode"` с прежними ограничениями video mode. FLAC требует одновременно `mode: "transcode"` и явного `live_audio_mode: "transcode"`. Отсутствующий селектор нового профиля по-прежнему материализуется в `copy`, поэтому неполный запрос FLAC отклоняется. Автоматической смены режима или кодека нет.

Перекодирование принимает поддержанный AAC LC и четыре конечные входные привязки. Для новых выходов частота и каналы преобразуются явно. Copy проверяет фактические заголовки и AU без resample/downmix. У Opus target 128000 относится к собственному encoder; VBR копируемого потока не подгоняется к нему. MP3/AC-3 подтверждают 128000/192000 по фактическим frame headers.

Начальная привязка Opus принимает pre-skip 0 либо 120 и полные AU 120. Адаптер потребляет единственную полностью пропускаемую начальную AU до ожидания видео; последующие payload/PTS/DTS сохраняются. Частичный хвост или больший skip не поддержаны. FLAC в продолжаемом тракте принимает 48…4608 сэмплов/AU; блок 1…47 завершает затронутую попытку до публикации. Подготовленный FLAC содержит только полные блоки 4608. Ограничения не заменяются дополнением нулями или скрытым успешным удалением.

Новые выходы используют Enhanced Audio `Opus`/`fLaC`/`.mp3`/`ac-3`; получатель должен поддерживать соответствующую привязку. Точная работа приложения, цифровая тишина, петли и сохранность времени проверяются отдельно от поддержки названия кодека FFmpeg. Совместимость реальной площадки этим контрактом не подтверждается.

Например, фрагмент полного профиля для FLAC с H.264/x264:

```json
{
  "mode": "transcode",
  "live_audio_mode": "transcode",
  "audio_encoding": {"bitrate_bps": 0},
  "encoding": {
    "video_encoder": "libx264",
    "audio_encoder": "flac",
    "rate_control": "crf",
    "crf": 23.5
  }
}
```

В полном запросе также обязательны `format.audio` с `codec: "flac"`, `codec_profile: "s16"`, частотой 48000, двумя каналами и `stereo`, совместимый `format.video` и полный `video_encoding`. Для показанного чистого CRF target/max/buffer видео равны нулю. Это фрагмент, остальные обязательные поля он не отменяет.

Все аудиопараметры входят в полную идентичность профиля и требуют соответствующего подготовленного варианта. Начальные состояния декодеров, физические счётчики и право перезаписи FLAC не являются полями REST/SSE, истории или manifest.

## Редактирование и списки

Изменения и удаления требуют `expected_revision`: положительное целое JSON-число в PATCH, PUT политики и rebuild; одноимённый текстовый query parameter при DELETE и PUT содержимого. Строка в JSON, отсутствие поля, `null`, ноль, дробь и переполнение отклоняются. Несовпадающая ревизия даёт `409`. Чтение текущей сущности перед изменением не заменяет атомарную проверку ревизии.

PATCH различает отсутствующее поле, `null`, `false` и пустую строку. Отсутствие сохраняет значение, переданные `false` и `""` применяются. `null` допускается только для явно nullable полей; политика fallback может быть явно очищена. Обычное редактирование действует со следующего запуска, текущая Session использует свой самостоятельный снимок.

Списки ограничены `limit` от 1 до 499 и имеют `cursor`. Порядок возрастающий по `(created_at, id)`; диапазоны дат имеют границы `[from, to)`. Курсор связан с видом списка и фильтрами. Применимые фильтры объявлены в OpenAPI; неподдерживаемый фильтр не означает молчаливое чтение всех объектов. Наблюдаемое состояние Output не хранится в SQL, поэтому фильтр `state` для сохраняемого списка выходов не поддерживается.

Пагинация не обещает неизменяемого набора при изменении состояния объектов между запросами.

## Команды и действующий эфир

Команды принимают пользовательский `request_id`. После долговечного принятия сервер возвращает `202 Accepted`, безопасную квитанцию и `Location` точного результата `/api/v1/commands/{commandId}`. Этот ответ подтверждает принятие, а не завершение операции. GET квитанции работает независимо от SSE.

Повтор того же смыслового запроса с тем же `request_id` возвращает прежнюю квитанцию, включая терминальный результат. Другой запрос с тем же идентификатором конфликтует. Изменение конфигурации или возможностей после принятия не превращает повтор в новый запуск.

Отказ уже принятой команды читается в `failure` её квитанции: `code` задаёт причину, `message` объясняет её по-русски, отдельное необязательное `action` подсказывает следующий шаг. При достоверно известных сведениях присутствуют `field` и `context`. Успешный GET такой квитанции возвращает `200`, даже если её `status` равен `FAILED` или `INTERRUPTED`. Причина сохраняется вместе с результатом; повтор и чтение после перезапуска не выводят её заново из текущих настроек. Старый результат без предметной причины получает общее безопасное объяснение.

При старте пустой список выбранных назначений использует включённые назначения текущего Stream по существующему доменному контракту. Backend самостоятельно выбирает и проверяет закрепляемые варианты; клиент не передаёт внутренние bindings.

Действия над текущим выходом различаются:

- `POST` коллекции выходов явно подключает назначение с новым снимком.
- `stop` останавливает выход, сохраняя его прикрепление и возможность повторного запуска с прежним снимком.
- `start` повторно запускает прикреплённый выход с его закреплёнными настройками.
- `detach` отсоединяет выход и прекращает возможность запуска старого выхода; зависимости освобождаются после подтверждённой очистки.

Эти действия не пересоздают исправные соседние соединения. Отсутствие возможности создать новый FFmpeg worker само по себе не запрещает присоединение к уже работающей общей группе. Проверки ресурсов и выполнение принадлежат существующим владельцам операций; отдельного общего HTTP-запрета медиакоманд нет.

## Загрузка, замена и rebuild

Создание и передача разделены:

1. `POST /fallback-assets` с JSON создаёт именованный Asset и возвращает `201`. Его ID можно использовать при настройке политики и групп.
2. `PUT /fallback-assets/{id}/content?kind=video&expected_revision=...` передаёт непустой файл с `Content-Type: application/octet-stream`. Допустимые `kind` — `image` и `video`. Путь сервера и имя конечного файла клиент не выбирает.
3. Допуск и резервирование выполняются до чтения тела. Байты, длительность чтения и очередь ограничены. Файл не копируется заранее во второй HTTP-каталог.
4. `202` возвращается после полного сохранения оригинала и закрытия reader, до inspection и генерации вариантов. Ответ содержит AssetID, GenerationID и `Location` точного поколения.
5. Клиент читает `GET /fallback-assets/{id}/generations/{generationId}` до результата подготовки.

Отмена до завершения передачи отменяет задание и закрывает reader, включая ожидание очереди. После успешного подтверждения передачи отключение клиента не отменяет подготовку: ею владеет FallbackManager с собственным сроком. Возобновление частично переданной загрузки и долговечный replay загрузок не обещаются.

Новая передача всегда создаёт новое поколение, даже при одинаковых байтах. Прежняя рабочая версия и остальные заглушки сохраняются до успешной проверки и атомарной публикации всего нового комплекта. Ошибка подготовки после `202` доступна в результате поколения и не отменяет успешный факт передачи.

`rebuild` принимает ожидаемую ревизию и возвращает `202` после резервирования: исходный файл уже хранится на сервере, повторная HTTP-передача не нужна. Генерация и rebuild запрещены во время эфира, включая ручную паузу, по существующему общему протоколу подготовки.

Подготовка создаёт цифровую тишину выбранного AAC/Opus/FLAC/MP3/AC-3, в том числе для видео с собственной аудиодорожкой. Исходный звук не используется; файл и петли беззвучны. При переходе с LIVE возможен короткий остаток прежнего звука декодера без универсальной длительности для всех получателей.

Пригодность варианта требует полного профиля, фактического формата, canonical/key и текущего контракта генератора. Проверка действует также для закреплённого снимка повторного запуска; свежий вариант не подставляется в старый OutputSnapshot. Отказ новой подготовки сохраняет прежний текущий комплект. Прежние базы и их манифесты автоматически не импортируются.

| Сохраняемое состояние поколения | Публичный статус |
| --- | --- |
| `QUEUED` | `queued` |
| `CLAIMED`, `ISSUED` | `preparing` |
| `PUBLISHED` | `ready` |
| `FAILED`, `INTERRUPTED` | `error` |

Current и pending Asset имеют разные назначения. Ошибка новой подготовки не делает готовый current ошибочным. Результат конкретного Generation остаётся доступным после очистки pending. Список variants по умолчанию относится к current; явный `generation_id` проверяется относительно Asset. Наличие metadata `READY` не заменяет фактическую проверку файла при запуске.

## Текущие измерения и SSE

История запусков и результаты управления читаются из SQLite. Наблюдаемые состояния, счётчики, progress, ошибки медиатракта и GPU-измерения — из RAM. Они не восстанавливаются из истории после завершения Session или рестарта.

Неизвестная Session даёт `404`. Известная Session без текущих измерений даёт `200` с явной недоступностью и `null` вместо runtime-снимка; причины завершённой и ещё не наблюдаемой Session различаются. Недоступное или устаревшее численное измерение не подменяется нулём. Для недоступного FFmpeg-отчёта `progress` равен `null`; статус, причина, известные времена и счётчики потерь сохраняются. Измеренный ноль после полноценного окна остаётся допустимым значением. Единицы, окна и источники описаны в [контракте мониторинга](monitoring-contracts.md).

Метрики выхода содержат четыре явных поля непосредственно в `metrics`, одинаковых для REST и payload SSE:

| Поле | Представление |
| --- | --- |
| `ack_ahead_events_total` | Целое JSON-число `uint64`, число новых достоверно измеренных опережающих подтверждений. |
| `ack_ahead_bytes_last` | Целое JSON-число `uint64`, размер последнего измеренного опережения в RTMP-байтах. |
| `ack_ahead_bytes_max` | Целое JSON-число `uint64`, максимальный измеренный размер за запуск выхода. |
| `ack_last_anomaly_at` | Время UTC либо `null` до первого события. |

Начальные целые значения равны `0`. В `metrics.counters` эти поля не дублируются. Переподключение текущего запуска сохраняет накопления; новый запуск выхода начинает их заново. Насыщение обозначается существующим общим `metrics.media.saturated`, без сворачивания целых. Последнее и максимальное опережение и время продолжают обновляться после насыщения числа событий. Поля и их типы входят в генерируемый OpenAPI/JSON Schema.

Каждый новый измеримый опережающий ACK увеличивает число событий отдельно; дубликаты и неоднозначные наблюдения не считаются. При незавершённом `Write` и после потери однозначной эпохи счётчика часть наблюдений не измеряется. Нулевое число событий не является подтверждением отсутствия расхождений. Подробные пределы и единицы заданы в [контракте мониторинга](monitoring-contracts.md#диагностика-опережения-ack); сами показатели не влияют на отправку.

Для согласованного начала и восстановления клиент:

1. Получает `GET /events/snapshot`: все текущие Session/GPU и cursor сняты одной authority-границей.
2. Открывает `GET /events?cursor=...` и применяет следующие события.
3. При переподключении может передать `Last-Event-ID`; разные значения одновременно в header и query дают `400`.
4. При `resync_required` закрывает прежнюю подписку, получает новый снимок и открывает SSE с новой границы.

Курсор — ограниченная непрозрачная позиция оперативного потока, не токен доступа. Старый epoch, пропуск или очистка событий требуют нового снимка. События неполного диапазона не выдаются за непрерывную историю. Без cursor поток начинается с текущей границы и не заменяет первоначальный REST-снимок.

Клиенты, размер страницы и кадра, heartbeat и время записи ограничены. Deadline действует до первой записи и flush. Неподдерживаемый transport не допускает неограниченную запись; медленный клиент отключается. Сеть не удерживает authority и не блокирует медиатракт. Отмена запроса и закрытие API завершают принадлежащие им streams. После начала SSE нельзя изменить HTTP status; допустимы безопасный control frame и закрытие.

RAM-снимок не является общей транзакцией с историей SQLite. Квитанции команд клиент при необходимости читает отдельно.

## Возможности, готовность и ошибки

`/system/capabilities` сообщает фактически проверенные сведения и их время. Доступность настроенного executable не подтверждает наличие нужных codecs/filters или работоспособность NVENC/NVDEC. Непроверенная аппаратная возможность остаётся `unverified`; недоступная NVML-статистика не является доказательством отказа медиатракта. Проверка не запускает процессы, аппаратный самотест, сканирование или фоновые probes.

`/health/live` описывает работоспособность процесса. `/health/ready` проверяет открытое управление и ограниченное чтение хранилища, полученного после bootstrap. Недоступные FFmpeg/NVIDIA и GPU-статистика сами по себе не снимают готовность управления. Недоступная управляющая зависимость даёт `503`. Готовность не требует соединения со всеми площадками и завершения старого терминального cleanup.

Ошибки возвращаются как `application/problem+json`. Стандартные поля Problem Details `type`, `title`, `status`, `detail` и необязательное `instance` сохраняют своё назначение. `code` — стабильная машинная причина; `detail` — подготовленное русское объяснение. Отдельное необязательное `action` содержит понятный следующий шаг. Когда сервер не знает достоверного действия, поле отсутствует. Клиент выбирает обработку по `code`, а тексты показывает пользователю; подсказка не запускает исправление автоматически.

Необязательное `field` указывает известное публичное поле. Необязательный `context` содержит только известные идентификаторы `stream_id`, `session_id`, `output_id`, `group_id`, `profile_id`, `asset_id`, `generation_id`, `variant_id`, `destination_id`, `command_id`. Неизвестные поля и идентификаторы отсутствуют; идентификатор из запроса сам по себе не считается подтверждённым объектом. Значения ключей, URL, путей, `request_id`, служебных токенов и признаков владения, отклонённые значения и произвольная диагностика в объяснения не копируются. Это действует также для ошибок разбора и автоматической валидации Huma. Подробные ошибки полного профиля сохраняют прежние `code`, `field` и `detail`.

HTTP-статус выбирается по прежним правилам до выбора предметной причины. Если объединённая ошибка не позволяет однозначно указать одну причину выбранного класса, возвращается общий безопасный код и текст этого статуса. Неожиданный `500` всегда остаётся общим. [Каталог причин](api-error-contracts.md) задаёт различия ошибок и результатов команд. До открытия SSE применяется тот же контракт; после начала потока возможны только предусмотренный управляющий кадр и закрытие.

| HTTP status | Значение |
| --- | --- |
| `400` | Некорректная структура запроса или cursor |
| `404` | Неизвестный объект или неподходящий родитель |
| `405` | Метод не поддерживается маршрутом |
| `408` | Истёк срок чтения тела либо прервана передача заглушки |
| `409` | Конфликт ревизии, использования или состояния |
| `413` | Превышен допустимый размер либо иной применимый лимит подготовки; точное различие задаёт `code` |
| `415` | Неподдерживаемый Content-Type |
| `422` | Недопустимые значения |
| `503` | Недоступна требуемая зависимость или приём операций |
| `500` | Неожиданная внутренняя ошибка |

Точные operation IDs, DTO и применимые параметры опубликованы в OpenAPI. Спецификации JSON/YAML формируются после регистрации и затем неизменяемы. Дополнительные downgrade-маршруты не публикуются. Документация и schemas используют тот же префикс и не требуют Authorization.

## Локальная приёмка 6 ноября 2026 года

T08 принята локально на стабильном снимке `t08-frozen-v3`: 386 проверяемых исходников, тестов и файлов конфигурации, включая новые файлы. Все их хеши совпали до и после проверок. Среда — Go 1.27.3, macOS/arm64, CGO=1; настоящие временная SQLite/Goose, локальные RTMP-приёмники и process helper.

- Полный `make check` прошёл: форматирование, согласованность и целостность модулей, vet, тесты всех `./...`, race, закреплённый линтер и сборка. Покрыто **13 689 из 15 852 инструкций — 86,355034%**; автоматический точный порог 85% пройден без исключений пакетов. Учтены данные покрытия действительно исполненного helper; временные профили удалены штатной командой после расчёта.
- Независимые свежие `go test -count=1 -json ./...` и `go test -race -count=1 -json ./...` прошли без диагностик data race. Каждый запуск: 18 успешных пакетов, 1876 успешных тестов и подтестов; два пакета без тестовых файлов. Десять пропусков относятся к отдельным медиапроверкам с FFmpeg/VideoToolbox; проверки T08 не пропускались.
- Проверены REST/OpenAPI, CAS и присутствие полей, точность данных и безопасные ошибки, настоящие команды SessionManager и квитанции, передача и независимая подготовка заглушек, RAM/SSE, возможности и готовность управления. Независимое итоговое ревью не выявило неисправленных замечаний или необоснованного расширения задачи.

При проверке исправлена выдача устаревшего FFmpeg progress: недоступный отчёт теперь `null`, актуальные нули и частично доступные поля сохраняются. Независимая регрессия сначала воспроизвела ошибку через REST и SSE, затем прошла обычный и race-запуски.

Первый общий race-прогон также выявил некорректную границу нового интеграционного теста: один приёмник смешивал основной выход и намеренно закрываемый дополнительный. Контролируемый диагностический опыт подтвердил ложный отказ общего ожидания при продолжающейся передаче основного потока. Приёмники разделены; сохранение основного соединения и передача следующих пакетов проверяются отдельно. Конкретное соединение первоначального `EOF` не было записано и осталось неизвестным; ему не приписывается недоказанная причина. Первое падение и диагностика сохранены. Финальные полные проверки выполнялись без диагностических overlays, подавления ошибок, новых задержек или изменения `GORACE`.

Предоставленная владельцем AV1/AAC-запись в этой приёмке не использовалась. FFmpeg, GPU, Debian/NVIDIA, настоящий OBS, реальные площадки и длительный эфир в эту локальную приёмку не входили. Общая точка входа и подключение зависимостей реализованы в T09 и описаны в [контракте приложения](application-contracts.md). Последующий основной прогон на VM и отложенные сценарии приведены в [целевой приёмке](media-contracts.md#target-acceptance).
