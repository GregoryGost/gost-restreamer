# Версии приложения и происхождение сборки

## Назначение версии

Первый выпуск приложения — `v0.1.0`. Новая версия назначается в существующем workflow после фактического слияния pull request в `main` или `develop`. Исходником служит точный commit слияния. Обычно следующий выпуск повышает minor: `v0.1.0` → `v0.2.0` → `v0.3.0`.

`develop` подготавливает следующий выпуск. Каждое новое слияние получает возрастающий номер в пределах базовой версии и короткий commit в метаданных SemVer. При смене базы счётчик начинается с `1`:

| Этап | Пример версии |
| --- | --- |
| Подготовка первого выпуска | `v0.1.0-dev.1+a1b2c3d4e5f6`, затем `v0.1.0-dev.2+b2c3d4e5f6a1` |
| Первый выпуск `main` | `v0.1.0` |
| Следующий цикл `develop` | `v0.2.0-dev.1+c3d4e5f6a1b2` |
| Следующий выпуск `main` | `v0.2.0` |

Префикс `v` входит в Git-теги, вывод CLI, поле версии журнала и имена архивов. Commit после `+` обозначает происхождение dev-сборки; порядок внутри цикла задаёт счётчик. Версия приложения не повышает автоматически версию REST API, схемы SQLite или внутреннего протокола helper.

## Сведения в бинарнике

Одна версия передаётся обеим целям Makefile и обеим сборкам GoReleaser через `VERSION` и внедряется в `internal/buildinfo.version` посредством `-ldflags -X`. Это сохраняет точное обозначение, выбранное CI, включая dev-счётчик и метаданные commit. Полный commit, признак изменений дерева и версия Go читаются из встроенных сведений Go; GoReleaser явно использует `-buildvcs=true` и `-trimpath`.

При обычном `go build` или `make binary process-helper` без `VERSION` используется версия главного модуля из `runtime/debug.ReadBuildInfo()`. Она может быть версией тега, псевдоверсией между тегами или содержать `+dirty`. При отсутствии версии используется `devel`; отсутствующие commit и признак изменений показываются как `unknown`. Неизвестное состояние не объявляется чистым деревом.

Для сборки исходников из ZIP без Git точная версия пока не требуется. `-buildvcs=false` также отключает сведения VCS; явно переданный `VERSION` при этом сохраняется. Git, рабочая конфигурация и переменные окружения не нужны уже собранному бинарнику для чтения своей версии.

## CLI и журнал

Оба исполняемых файла поддерживают `--version`: одна строка в stdout и успешное завершение. Например:

```text
v0.2.0-dev.1+a1b2c3d4e5f6 commit=a1b2c3d4e5f6000000000000000000000000000000 dirty=false go=go1.27.3
```

Чтение версии не загружает YAML, не открывает SQLite, не запускает FFmpeg, слушатели или внутренний протокол helper. Ошибка записи stdout возвращает ненулевой результат.

Событие `application_started` содержит поля `version`, `commit`, `dirty`, `go_version` из того же `buildinfo.Current()`. Это обычная запись INFO, подчиняющаяся настроенному уровню журнала. Обязательное предупреждение о приоритете конфигурационных файлов сохраняет прежние правила.

## CI и проверка

Для вычисления версии используется закреплённая ревизия [GregoryGost/version-tagger v1.2.0](https://github.com/GregoryGost/version-tagger/releases/tag/v1.2.0). Go-проект передаёт начальную версию явно; `package.json` не требуется. Сборки сериализуют назначение версии, повторный запуск для того же commit сохраняет ранее назначенную версию. Тег относится к проверенным бинарникам; изменение исходных тегов не разрешает заменить встроенный номер другим при публикации.

Подробности workflow и ограничение очереди описаны в [документации CI](../.github/CI.md). Независимые локальные проверки, результаты обязательных команд и ещё не проверенные удалённые операции приводятся в итоговом отчёте реализации отдельно; наличие конфигурации workflow не подтверждает запуск GitHub Actions или публикацию тегов.

## Debian-версии и каналы поставки

Git-тег и версия внутри обоих бинарников остаются одинаковыми. Для поля `Version` в `.deb` убирается `v`, а `-dev.` преобразуется в `~dev.`:

| Git и бинарник | Debian package version |
| --- | --- |
| `v0.2.0-dev.1+abc123` | `0.2.0~dev.1+abc123` |
| `v0.2.0-dev.2+def456` | `0.2.0~dev.2+def456` |
| `v0.2.0` | `0.2.0` |
| `v0.3.0-dev.1+123abc` | `0.3.0~dev.1+123abc` |

Встроенный nFPM GoReleaser переводит prerelease SemVer в Debian `~`; `verify-packages.sh` сверяет фактическое поле пакета с ожидаемой строкой. В Debian-контейнере CI выполняются `dpkg --compare-versions`: `dev.1 < dev.2`, `dev.10 < stable`, `dev.N < stable` и `stable < dev` следующего minor. Метаданные commit сохраняются после `+`, а порядок внутри цикла задаёт числовой счётчик. Планировщик запрещает два тега с одной семантической версией, даже если metadata различаются.

`develop` использует snapshot GoReleaser с явным `snapshot.version_template`, равным назначенной версии без `v`. Автоматический snapshot-суффикс не добавляется; `VERSION` в `ldflags` содержит полную Git-версию. Публикация отключена одновременно флагом `--skip=publish`, snapshot-режимом и `release.disable: true`. Пакеты доступны через Actions Artifacts 14 дней, Git-тег сохраняется независимо от истечения артефакта.

`main` формирует стабильные пакеты без публикации, проверяет их, публикует тег и отдельным запуском GoReleaser создаёт **Draft Release**: `draft: true`, `prerelease: false`. Отдельная конфигурация публикации прикрепляет уже проверенные файлы через `release.extra_files`, без повторной компиляции. Pro-функции `continue` и `before_publish` не используются.

Повтор того же commit сохраняет Git-версию и Debian-версию; номер попытки входит только в имя Actions Artifact. Время записей архива задаётся датой commit; CI повторяет упаковку с другими датами файлов checkout и сверяет прежние SHA256. Существующий draft проверяется по именам, размерам и SHA256: совпадающие файлы сохраняются, отсутствующие дозагружаются, несовпадение останавливает workflow до записи. CI не заменяет и не удаляет файлы релиза. Уже опубликованный владельцем релиз пропускается без изменений. Ручную публикацию нужно выполнять после успешного workflow и вне его повторного запуска: GitHub API не предоставляет атомарной операции «загрузить файл только если релиз ещё draft».

Тег отправляется через `GITHUB_TOKEN` в том же workflow. Его push не используется как триггер нового workflow. Владелец вручную открывает Releases → нужный Draft → Publish release; CI этой операции не выполняет.

## Локальная приёмка 6 ноября 2026 года

Проверен стабильный `f01-frozen-v1`: 342 исполняемых входа, SHA256 манифеста `c7f7ac5e6dabb62303cad4ea917c113175889254a90d29ecc6b907bbe4d2bf84`. Среда — Go `1.27.3`, Darwin/arm64, CGO=1; зависимости и toolchain не менялись.

- Полный `make check` прошёл: форматирование, модули, vet, lint, покрытие, race и сборка. Покрыто **14 347/16 589 инструкций — 86,485020%**, точный порог 85% пройден без исключений.
- Отдельный свежий независимый `go test -count=1 ./...` прошёл; входы до и после проверки совпадают. Независимые тестирование и ревью приняты для локальной области.
- Настоящие оба бинарника проверены со встроенной версией и без неё, с native VCS и `-buildvcs=false`; вывод сверялся с `debug/buildinfo.ReadFile` и действительным HEAD. Makefile также собрал оба локальных бинарника с одинаковой явной версией и `dirty=true`, соответствующим незакоммиченному дереву.
- Проверены ранний выход CLI, ошибка stdout, отсутствие загрузки конфигурации и входа в lifeline helper, точные поля настоящего JSON-журнала и уровень INFO/ERROR.
- Планировщик проверен на временных Git-репозиториях. Извлечённый настоящий shell публикации проверен с локальным bare remote: успех, повтор, изменение ссылок и конкурирующий конфликт после предварительной проверки. Подтверждено сохранение существующего тега и недостижимость загрузки артефакта при конфликте.
- Финальный `gopls v0.24.0 check -severity=warning` 14 изменённых Go-файлов не сообщил предупреждений или ошибок. Использован разрешённый CLI fallback после ошибки метаданных нового теста во встроенном MCP.

Первоначальные отказы TCP bind и записи стандартных кэшей были ограничениями sandbox. Требующие слушателей тесты и итоговые команды выполнены с разрешённым выходом из sandbox; подтверждённых необъяснённых отказов на итоговом снимке нет.

Фактический GitHub Actions, исполнение закреплённого Action, Linux/Debian-контейнер, реальные права и очередь GitHub, удалённая публикация и загрузка артефактов остаются **непроверенными**. Они не подменяются локальной приёмкой и проверяются при итоговой поставке. В этой сессии не было коммитов, запусков удалённого CI, публикаций тегов или GitHub Releases. [Локальные отчёты](../.agent-handoffs/f01-versioning-20261106/index.md) сохранены вне Git.
